People, groups and agents are resources of the built-in `sanoma` connector, declared in a [data file](/workflows/resources/#data-files) (`resources/people.ts` by convention), loaded as any other:

```ts
import { sanoma } from "sanoma/resources";

export const ada = sanoma.person({ id: "ada", name: "Ada Ortiz", email: "ada@acme.test", github: "ada-ortiz" });
export const bo = sanoma.person({ id: "bo" });
export const refundBot = sanoma.agent({ id: "refund-bot", onBehalfOf: bo });
export const claudeCode = sanoma.agent({ id: "claude-code", client: "claude-code" });
export const finance = sanoma.group({ name: "finance", members: [ada] });
```

A membership is written on the group alone. An agent is in the group `agents` besides its own, with `onBehalfOf` the person whose instruction it carries; the runtime's own agents (`scenarios`, `host-check`, `schedule`, `wakeup`, which registers a wakeup, `login`, which sends sign-in codes, `renewal`, which renews OAuth grants when due, and `sanoma-chat`, which the app's chat acts as for the person chatting) are declared by no file, and no file may give a person or an agent one of their ids. They have no vendor object: no driver, no drift. `readPeople(root)` loads them from the files that may declare them (`mayDeclarePeople`: those importing `sanoma` from `sanoma/resources`), again only when one of them changed, so a request costs a `stat` per file, and `principalOf(id, people)` is who an id is: its groups, by inverting the members, and its `onBehalfOf`. Once a person is declared, `SanomaClient.start`, `call`, `decide`, `setCredential`, `setSecret`, `clearCredential` and `clearSecret` admit only a declared id (`not_admitted`, "<id> is not declared in resources/people.ts"), as the app's login admits only a declared person; while none is, any id is taken as given; while the people files have problems, nobody is admitted but the runtime's agents.

An agent may also act for whoever uses it. `client` names the OAuth client it stands for, one word such as `claude-code` (a client's id, not necessarily a URL), and `agentOfClient(client, people)` finds the agent of a client: none when no agent declares it, or when two do, which `sanoma check` reports as a problem (`clientClashes`) without keeping anyone from being admitted, since nothing reads a client at run time yet. `agentActing(agentId, person, readPeople(root))`, from `sanoma/workflows/describe`, is the principal of a declared agent acting for a declared person, `{ id, groups, onBehalfOf: person }`, with the agent's own groups and `agents`; it refuses (`not_admitted`) while the people files have problems, an id that is not a declared `sanoma.agent` (a person's, a runtime agent's, anyone undeclared), a person who is not a declared `sanoma.person`, and an agent whose `onBehalfOf` names someone else. `admit`, and so `start`, `call` and the other client methods, apply the same check to an agent named with an `onBehalfOf` and keep it; a person's `onBehalfOf` is dropped, and an agent named without one is its declared self. The app makes this principal for a call through `/mcp` that names an agent ([the app's README](https://github.com/Sanoma-AI/sanoma/blob/main/packages/sanoma/app/README.md#agents-over-mcp)).

**A declared agent acting for a person may do no more than that person.** The policy is asked twice about each of its calls and starts: once as the agent (its id, its groups and `agents`, `onBehalfOf` the person) and once as the person alone (their id and declared groups), and the stricter answer stands: a deny over a hold over an allow. When both hold, both are waited for, one after the other: the agent's hold first, then, once it is approved and the policy is asked again, the person's. In the person's question an `@hold("on-behalf-of")` is addressed to the person, as in the agent's, rather than refused for want of whom they act for. So a `forbid` or `@hold` naming the person or one of their groups reaches their agent, and a rule naming `agents` still reaches the agent and not the person. So is `sanoma-chat`, the runtime's agent the app's chat acts as, and never acting for no one (`admit` refuses it bare): the app's worker makes it acting for the person whose chat turn it is (`chatAgentActing`), never a request (`x-sanoma-agent` refuses it), and a company's policy reaches it by `principal in Sanoma::Group::"agents"` or `principal == Sanoma::Principal::"sanoma-chat"`. Anyone else, the runtime's other agents and an agent acting for no one among them, is asked once, as before. The agent's groups still apply to it: a rule on one of them reaches the agent, and an `unless` it would pass lets it through only where the person passes too; `sanoma check` warns of an agent with no fixed `onBehalfOf` in a declared group (`peopleWarnings`), since whoever names it acts in that group through it. A person may approve a hold on a run their own agent started for them, since the run's actor is the agent (see [Approvals](/workflows/approvals/)). Today the connections a call may use and a direct write's `updated_by` are keyed on the actor's id, the agent's, not the person's.

A visitor of a public site is a principal too, which no data file declares: `visitorPrincipal(login, subject)` is one signed in through a visitor login (`visitor:<login>:<subject>`, in the group `visitors`), and `ANONYMOUS_PRINCIPAL` the one a page with nobody signed in runs as (`anonymous`, in no group); `isVisitor(principal)` tells either by its id. `admit` takes a visitor's id whatever the files say and stamps its groups, never the ones given; the staff logins (a sign-in) admit none, and a visitor sets no credential and decides no approval. So `visitors` and `anonymous` are no group's name, and `anonymous` and the `visitor:…` form no person's or agent's id (`readPeople` reports them, as it does `agents`).

A script or another service acts through an API token: `client.tokens.mint({ subject, groups })` makes one, `sca_` and 32 random bytes in base64url, and returns `{ id, token }`, the token shown this once (only its SHA-256 is kept, in `sanoma_api_tokens`); `subject` is whom it acts for (`visitor:better-auth:<id>`, say). A public site's host takes it as `Authorization: Bearer <token>`, and the request acts as `token:<id>` in the token's `groups` (admission keeps them, where a visitor's are stamped `visitors`), with no email; `client.tokens.revoke({ id })` ends it, and an unknown or revoked token is a 401.

## Signing in on a host

The app on a host signs people in by an email code, an invite link, or GitHub ([the app's README](https://github.com/Sanoma-AI/sanoma/blob/main/packages/sanoma/app/README.md#staff-sign-in-on-a-host)). The code goes out through the operation the config names as `login.sender`, a connector's send that takes `{ from, to, subject, text }`, from the address it names as `login.from` (`login@acme.example` or `Acme <login@acme.example>`), on a domain the sender's vendor has verified ([`resend.domain`](https://www.npmjs.com/package/@sanoma-ai/connector-resend#sending-domain) declares one):

```ts
import { resend } from "@sanoma-ai/connector-resend";

export default defineConfig({
  connectors: [resend],
  login: { sender: resend.emails.send, from: "Acme <login@acme.example>" },
  // …
});
```

With one, the runtime registers the built-in workflow `login-code` (so a company workflow may not be named that), which the app starts as the agent `login` with the code sealed under `SANOMA_SIGNING_KEY` together with the email it is for (`sealLoginCode(to, code)`, so a copy of a run's input mails it to nobody else); its one call mails "Your <company> sign-in code", under the policy and in the ledger like any send, the mail's `text` recorded as `<text>`. A policy that holds sends exempts it (`unless { … || principal == Sanoma::Principal::"login" }`): otherwise `describeConfig` reports a problem on `policies`, naming the policy and the fix. `resolveConfig` refuses a sender that is no connector's operation, does not send, has no driver, or takes no email from `login.from`, and a `login.from` that is missing or no email address. Each sign-in and each invite is a ledger record outside any run (`signin.recorded { person, method }` under `signin:<person>`, `invite.minted { person, by, expiresAt }` under `invite:<person>`), written by `client.recordSignIn(person, method)` and `client.recordInvite(person, { by, expiresAt })`; `client.lastSignIns(people)` reads when each last signed in and how, and `client.lastInvite(person)` who minted their latest invite, when and until when (`{ by, at, expiresAt }`, undefined while none was), which the invite's landing page names. `sealInvite({ email })` seals an invite request for five minutes under `SANOMA_SIGNING_KEY` (`openInvite` opens one), which an instance holding the same key answers with a one-use invite link at `POST /auth/invite`.
