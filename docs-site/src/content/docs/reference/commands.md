Exit codes: 2 for a mistake in the call or the repo (no `sanoma.config.ts`, an unknown command or option, a bad argument, an option of another command), printed with the usage where it helps; 1 for failed checks and failures while running, and for a call `sanoma call` or `sanoma describe` sends that the app refuses or that fails, or that nothing answers; 0 otherwise. `SANOMA_APP_PORT` is the app's port (default 3000; 0 for any free port, which the printed address reports). `SANOMA_APP_HOST` is its address (default 127.0.0.1); `SANOMA_DOMAINS` gives a [public site](/sites/public-sites/) its domain, `<site>=<hostname>[,<site>=<hostname>…]` (`www=sanoma.example`, which a host resource's `domains` sets), and a malformed one exits 2; any other address signs people in with the [staff sign-in](/sites/login/#staff-sign-in-on-a-host) (an email code through the config's `login.sender`, invite links, and GitHub once `SANOMA_GITHUB_CLIENT_ID` and `SANOMA_GITHUB_CLIENT_SECRET` are both set, in the environment or stored by the app's Connect page (under Hosting) when it created the GitHub App; the public sites' logins then offer visitors GitHub too, for which the App's callback URLs need `https://<site host>/auth/better-auth/callback/github`), which needs `SANOMA_SIGNING_KEY`; a missing key, or one of the GitHub pair without the other, exits 2 before anything starts, as does a problem in the policies. There too, `SANOMA_HOSTNAME` is the hostname the app is served at over HTTPS (`app.sanoma.example`: no scheme, port or path), as a host resource's `hostname` sets it on the Cloudflare host. It is the instance's one [agent address](/start/agents-over-mcp/): agents sign in at `https://<hostname>/mcp`. An instance reached any other way (a port, an IP address, plain http) gives its own URL in `SANOMA_HOST_URL` instead (`http://10.0.0.7:3000`, with no path), which is read when there is no hostname. A value of either that names no address exits 2. With neither, people still sign in but no agent can: `sanoma` says so once on stderr when it starts, and `/mcp` says which variables to set. On SIGINT or SIGTERM the app, then the worker, then the Postgres it started, stop, and the process exits 0.

## From a terminal or an agent

`sanoma describe` and `sanoma call` reach a `sanoma` that is already running, over HTTP: they start no worker and need no database, only the app. An agent with a shell uses them as a person at a terminal does: `sanoma describe` says what there is, then `sanoma call hello --input '{"title":"Hi"}'` starts a run and `sanoma call hello.result --input '{"runId":"…"}'` waits for its output. The answer is the one thing on stdout, as JSON (indented at a terminal, on one line otherwise); a refused or failed call exits 1 with the app's message on stderr, its `code`, the run it names and, for an input that does not fit, each field's problem. A call the policy holds (409, `approval_pending`) exits 1 too, with its run's id on stderr and nothing on stdout.

- **Once:** each invocation of a start or an operation's call is a new run or call. `--id <id>` (letters, digits, `_` and `-`) names it instead: the same `--id` again is the same call, not a second one, and with another input it is refused. When a request times out or its connection breaks after it was sent, the error names the id it used, to run the command again with.
- **Which company:** the nearest directory from the working one up that holds `sanoma.config.ts` (short of a `node_modules`), then the company it is in (an app in `apps/<app>/` that kept its own config is its company's), each as the main checkout has it (from a draft in `.sanoma/drafts/<id>`, the company's own directory). The first of those with a running app is the one whose app the commands ask and whose `.env` and people they read; with none running, the company's. Outside any, they exit 2, unless `--url` names the app; then `--as` is needed.
- **Which app:** `--url`; else the one the company's `.sanoma/app.json` names while its process runs, when that is an http(s) address on this machine (`sanoma`, `sanoma serve` and `sanoma app` write it, `{"url","pid"}` and `"signIn":true` for an app that listens beyond this machine, once the app listens, and remove it when they stop; one whose process is gone is ignored); else `SANOMA_APP_HOST` (default 127.0.0.1) and `SANOMA_APP_PORT` (default 3000), after `.env`. A `--url` with a user or a password in it is refused (exit 2). With `SANOMA_APP_PORT` empty or 0 and no running app to say where, name it with `--url` (exit 2). Two `sanoma` started on port 0 in one directory share one discovery file, the last one's: name the address with `--url` then. When nothing answers, the command exits 1 naming the address it tried and where it came from.
- **Who asks:** `--as`, a declared person's id, else one's email, else one's GitHub login (an id always wins: `--as sam` is the person `sam`, whoever's GitHub login is `sam`); else the one person `resources/` declares, as the app's picker takes them; else the person git's `user.email` names. Otherwise it exits 2 listing the people. A company that declares nobody needs `--as`.
- **For an agent:** `--agent <id>` names a declared agent (`sanoma.agent`) that makes the call on that person's behalf, as `x-sanoma-agent` does on [`/mcp`](/start/agents-over-mcp/): the policy and the ledger see the agent for the person.
- **Where:** an app on this machine, listening on this machine alone. An app on any other address (a host, or `SANOMA_APP_HOST=0.0.0.0`) asks its staff sign-in who is asking, which these commands do not give: they say so when it refuses them. Their stdout holds the answer alone, `SANOMA_EVENTS=1` or not: a failure is on stderr, never an `error` event.
- **Waiting:** `<api>.result` asks again while the run is running, a second apart at least, for up to 10 minutes; ctrl-c stops waiting (exit 130), and the run goes on.

## For a parent process

A parent process, such as a desktop shell, runs `sanoma` with `SANOMA_EVENTS=1` and reads its stdout line by line: beside the lines a person reads, each event is one JSON object on a line of its own, `{"sanoma":1,"event":…}`; logs stay on stderr.

- `{"sanoma":1,"event":"ready","url":"http://127.0.0.1:3000","sites":{"www":"http://www.localhost:3000"}}`: the app listens, right after the `at <url>; ctrl-c to stop` line, each time it starts (in [dev mode](/reference/dev-mode/), after each restart); `url` is where the app listens, on the port `SANOMA_APP_PORT` names (the free one it took, for 0), and `sites` is `{}` without public sites. `sanoma worker` has no address and prints none.
- `{"sanoma":1,"event":"error","message":"…"}`: the launcher cannot start or stop, with the message it printed on stderr, then exits 2 for a mistake in the call or the config, 1 for a failure. In dev mode a child that fails prints it too, and the launcher waits for the next build to start it again.
- `{"sanoma":1,"event":"checked","ok":false,"problems":["…"],"warnings":[]}`: `sanoma check`'s result, the lines it printed as two lists, before it exits; a check that cannot read the config ends with `error` instead. Read it rather than the printed lines: DBOS logs on stdout too.
- `{"sanoma":1,"event":"stage","stage":"template","status":"start"}`, then `"status":"done"`: a stage of starting a company (`sanoma init`, or `sanoma` in an empty directory), in this order: `template` (the files copied, named and keyed), `people` (you declared), `git` (the repository and its first commit), `install` (the package manager's install), then `database` (the company's own Postgres answering, from the `sanoma` the install brought, which then starts the worker and the app). A stage that fails has no `done`; an `error` follows. `database` comes on every run, not only the first, around the `database` event; none when a URL is named.
- `{"sanoma":1,"event":"database","how":"started","url":"postgresql://postgres:…@127.0.0.1:54012/sanoma","place":"this-computer"}`: the company's own [Postgres](/hosting/postgres/) answers, once, before the worker starts (in dev mode, from the parent, not each child): `how` is `created` (made first), `started`, or `answered` (another `sanoma` runs it), and `url` holds its password, so a parent never logs it. None when a URL is named.

With the variable, the end of stdin (the parent closing it, or exiting), or an error reading it, stops `sanoma` as SIGTERM does, so the parent keeps stdin open while it runs. `sanoma` never prompts and, without the variable, never reads stdin; it opens no browser. SIGTERM stops everything it started (the app, then the worker; in dev mode its child and the watch builds), then the company's own [Postgres](/hosting/postgres/) when it started it and no other client is connected, and it exits 0.
