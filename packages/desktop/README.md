# @sanoma-ai/desktop

The Sanoma desktop shell, for people who will not open a terminal: it opens a company folder, runs that company's own `sanoma` launcher (the one in its `node_modules`), and shows the app in a window. Private: it is never published to npm.

It adds nothing to the product. The window shows the same app `sanoma` serves at `http://127.0.0.1:<port>`, and the app does not know it is inside the shell. There is no second UI, no runtime concept and no agent here.

## Run it from the checkout

```sh
pnpm install
pnpm --filter @sanoma-ai/desktop start                 # the start window
pnpm --filter @sanoma-ai/desktop start ~/Companies/acme  # or open a company at once
```

`start` downloads Electron's binary the first time (a plain `pnpm install` skips it: `allowBuilds` in `pnpm-workspace.yaml`), builds the shell, fills `stage/` (`scripts/stage.ts`: the pinned Node, `scripts/download-node.ts`, and a copy of the pnpm running the script), and opens it. A company to try it on: `pnpm dlx sanoma` in an empty folder, with Postgres answering at the URL in its `.env`.

`pnpm --filter @sanoma-ai/desktop run test:e2e` is the smoke test: it builds and stages as `start` does, then starts the shell with Playwright (no browsers to install) on a copy of `test/fixtures/company`, whose `pnpm install` links a fake launcher. One window must show the start, then the app on the Node the shell ships (inside the template's `engines`), with no other window made; closing it must leave the launcher running, opening the folder again must show that window without a new start, Quit must stop the launcher, and the next launch must open the company again at the window's bounds. CI runs it on Linux under xvfb for changes to this package (`.github/workflows/desktop.yml`); the root `pnpm test` runs the unit tests only.

`pnpm --filter @sanoma-ai/desktop package` builds the app, unpacked, into `out/` (Electron Forge, `forge.config.mts`), and `make` builds the dmg and zip for arm64 and x64 into `out/make` that [`desktop-release.yml`](../../.github/workflows/desktop-release.yml) uploads to a draft GitHub Release (the root README, "Desktop (preview)").

## What it does

- **Opens a company**: a folder with a `sanoma.config.ts`, from the start window (Open folder…, Recent, which marks the companies running), File → Open Company… or Open Recent, the command line, a second launch (which hands the folder to the running shell) or a folder dropped on the Dock icon. A folder iCloud syncs gets a warning, as does the Intel build on Apple silicon. A folder that holds no company, and any other reason something asked of the shell did not happen (a folder New Company or Clone cannot use, Get Updates' answer), is said in one line in the start window, never in a dialog.
- **In one window, from the click to the app**: the company's window opens at once and shows the install, the start and the log's tail, then the app in that same window once it answers. Opening a company that runs already shows its window, on the app, without starting it again. A second company gets a second window.
- **Installs and starts it**: `pnpm install --prefer-offline` in the folder (when that fails but `node_modules/sanoma` is there, it goes on with a warning), then the launcher `node_modules/sanoma`'s `bin` names, in a process group of its own, with `SANOMA_EVENTS=1` and `SANOMA_APP_PORT` set (which win over the company's `.env`), and `PATH` starting at the shims in `<userData>/bin`: `node` and `pnpm` run the Node and the pnpm the shell ships, whatever the computer has, then the system's `PATH` and Homebrew's.
- **Knows when it is ready** from the launcher's `ready` event, or, for a launcher without events (sanoma 0.6.0 and before), its `<app> at <url>; ctrl-c to stop` line or the first answer from `/healthz`.
- **Shows the app**: one window per company, a `BaseWindow` holding the shell's own page and the app's view over it, swapped in place. The app's view has storage of its own (`persist:company-<hash of the folder>`: the app's `sanoma_actor` cookie ignores ports, so two companies must not share one), is sandboxed and has no preload. Each company keeps its port across starts (`<userData>/companies.json`; a new free one when it is taken), so the page remembers who you are. Links to the app, its public sites (`<name>.localhost:<port>`) and GitHub (the GitHub App's setup returns to the app) stay in the shell; any other web link opens in the default browser.
- **Keeps it running**: closing a company's window hides it, and the company goes on, its scheduled workflows with it; the Dock menu lists the companies running.
- **Stops it**: Company → Stop, Company → Restart and Quit close the launcher's stdin and send SIGTERM to its group, then SIGKILL after 10 seconds; Quit (Cmd-Q, or Quit in the Dock menu) waits for every company. A launcher that stops on its own is not restarted: its window comes back and shows why (exit code 2 is a problem with the config), its last 200 log lines and Start again.
- **Remembers**: each company window's bounds, and which companies are open, in `companies.json`. The companies open at Quit (running, or showing why they stopped) open again at the next launch, each in its window where it was. Company → Stop, or closing the window of a company that does not run, takes it off that list, as does the line a failed company's window shows ("Don't open it at launch").
- **Logs**: each start's output, timestamped, in `~/Library/Logs/Sanoma/<company>.log`, the previous start's kept as `.1.log` (Company → Show Log, Help → Show Logs Folder). A URL's password or token is hidden first (the launcher's `database` event carries the cluster's).
- **Starts a new company** (File → New Company…, or New company… in the start window): in an empty folder, chosen or made in the dialog (it starts where the last company is, else the home folder; a folder iCloud syncs gets a warning first), it runs the launcher's own init, `pnpm dlx sanoma`, with the shims and the environment of a run. Its output streams into the new company's window; it commits, installs, and then serves the company it started in that window. Until a launcher with embedded Postgres is on npm, that needs a Postgres at the URL in `.env` (or Docker); otherwise the start window shows the launcher's own error.
- **Clones a company** (File → Clone Company…, or Clone… in the start window): the start window asks for the repository's address, then a dialog for the folder to clone into; the system git clones it without ever prompting (`GIT_TERMINAL_PROMPT=0`, ssh in batch mode), so a public repository, or one the OS credential helper knows, works. The clone's output streams into the company's window, then the company installs and starts as an opened one does; a failed clone says why in one line there (a failed sign-in points at signing in with GitHub, which comes later, #286 D6), Start again clones again, and Recent does not list it.
- **Checks git first**: on macOS, `xcode-select -p`; without Apple's command line tools a dialog offers their installer and Check Again. Before New and Clone, a missing `user.name` or `user.email` is asked for once in the start window and set with `git config --global` (the launcher's init commits as them).
- **Gets updates** (Company → Get Updates): only when the company has an `origin`, is on `main` and has nothing of its own (no change in the tree, untracked files included, and no commit GitHub does not have); otherwise it refuses in one line and changes nothing. A `pnpm-lock.yaml` changed in the tree and nowhere else is the shell's own install's doing, not the person's: it counts as clean, and is put back before `main` moves. It fetches `origin`'s `main`, says when there is nothing new, else stops the company, fast-forwards `main` (`git merge --ff-only origin/main`, a `git pull --ff-only` without a second fetch) and starts it again, which installs its packages; the window stays.
- **Checks for a newer version**: in the built app, at start and at most once a day (the time in `<userData>/settings.json`), it asks GitHub Releases for the newest `desktop-v*` that is neither a draft nor a prerelease (`src/update-check.ts`). A newer one gets one notification and a Help menu item that opens its release page; Help → Check for a Newer Sanoma asks at once. It never downloads or installs anything: an unsigned app cannot update itself.

Not yet: updating itself, GitHub sign-in, Windows, signing.

## Why it ships a Node

Electron's own Node (24.22 in Electron 45) serves a company, but `sanoma check` crashes in it: oxlint's JS plugins pass the source through memory outside V8's heap, which Electron's V8 sandbox refuses. So the shell carries the official Node 26 (`scripts/download-node.ts`, sha256-pinned) in its resources, runs the launcher with it, and points the `node` shim at it, for whatever the company runs.
