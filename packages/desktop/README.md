# @sanoma-ai/desktop

The Sanoma desktop shell, for people who will not open a terminal: it opens a company folder, runs that company's own `sanoma` launcher (the one in its `node_modules`), and shows the app in a window. Private: it is never published to npm.

It adds nothing to the product. The window shows the same app `sanoma` serves at `http://127.0.0.1:<port>`. The one thing the app gets from the shell is the list of the window's companies, for its account menu (`window.sanomaDesktop`, below). There is no second UI, no runtime concept and no agent here.

## Run it from the checkout

```sh
pnpm install
pnpm --filter @sanoma-ai/desktop start                 # the start screen
pnpm --filter @sanoma-ai/desktop start ~/Companies/acme  # or open a company at once
```

`start` downloads Electron's binary the first time (a plain `pnpm install` skips it: `allowBuilds` in `pnpm-workspace.yaml`), builds the shell, fills `stage/` (`scripts/stage.ts`: the pinned Node, `scripts/download-node.ts`, and a copy of the pnpm running the script), and opens it. A company to try it on: `pnpm dlx sanoma` in an empty folder, with Postgres answering at the URL in its `.env`.

`pnpm --filter @sanoma-ai/desktop run test:e2e` is the smoke test: it builds the shell (`package`: Forge has no build-only command) and stages it as `start` does, then starts the shell with Playwright (no browsers to install) on a copy of `test/fixtures/company`, whose `pnpm install` links a fake launcher. The one window must show the start, then the app alone on the Node the shell ships (inside the template's `engines`), with no other window made; closing it must leave the launcher running, and opening the folder again must show it without a new start. A second company must join that window with the first still running and loaded; the Window menu's ⌘1 and the apps' `window.sanomaDesktop` must switch between them, an unknown id switching nothing, and the other app must hear of it; Company → Stop must stop the shown one and show the other, Quit must stop that, and the next launch must open it alone again at the window's bounds. CI runs it on Linux under xvfb for changes to this package (`.github/workflows/desktop.yml`); the root `pnpm test` runs the unit tests only.

`pnpm --filter @sanoma-ai/desktop package` builds the app, unpacked, into `out/` (Electron Forge, `forge.config.mts`), and `make` builds the dmg and zip for arm64 and x64 into `out/make` that [`desktop-release.yml`](../../.github/workflows/desktop-release.yml) uploads to a draft GitHub Release `v<version>` (the root README, "Desktop (preview)"); the zip, under Forge's name, is what the installed apps update from.

## Signing and notarization

On a Mac, the environment decides how `package` and `make` sign the app (`forge.config.mts`):

- **`APPLE_SIGNING_IDENTITY`** names a Developer ID in the keychain (the release's is in `desktop-release.yml`): the app is signed with it under the hardened runtime, and so is the dmg. Electron's own code keeps `@electron/osx-sign`'s entitlements (Chromium's); the Node the shell ships gets [`node.entitlements.plist`](node.entitlements.plist), whose comment says why each. The `EnableCookieEncryption` fuse is on. Its Keychain item holds across updates from the same team; a release from another team (as after incorporation) asks for Keychain access once. Only such a build updates itself (`SIGNED_BUILD`, defined in `vite.main.config.mts`), and Squirrel.Mac takes only an update signed by the running app's team: a release from another team is installed by hand once. A build without the fuse (`start`, an ad hoc `package`, which share an installed release's `~/Library/Application Support/Sanoma`) cannot read the cookies it wrote: its companies' apps start signed out, and the cookies it drops are the release's too, so give it a `--user-data-dir` of its own.
- **`APPLE_API_KEY`** as well, the path of an App Store Connect API key (`.p8`), with `APPLE_API_KEY_ID` and `APPLE_API_ISSUER`: each app is notarized and stapled before the makers pack it (so the zip's app is too), and each dmg after.
- **Neither**: signed ad hoc, without the hardened runtime, cookie encryption off. `start`, the smoke test and a `package` on your Mac work as before.

`desktop-release.yml` sets them from the repository secrets `MAC_CERT_P12` (the certificate and its key, a base64 `.p12`), `MAC_CERT_PASSWORD`, `APPLE_API_KEY` (the `.p8`'s text), `APPLE_API_KEY_ID` and `APPLE_API_ISSUER`. It imports the certificate into a keychain of its own and writes the key to a file, checks that each app and dmg is signed, notarized and stapled before the draft release, and deletes both at the end. To try a signed build on a Mac with the identity in its login keychain (signed, not notarized): `APPLE_SIGNING_IDENTITY="Developer ID Application: …" pnpm --filter @sanoma-ai/desktop package`.

On Windows, **`WINDOWS_SIGN_WITH_PARAMS`**, signtool's arguments, signs with them every executable in the app and the installer, the bundled `node.exe` and Squirrel's `Update.exe` among them, with one SHA-256 signature (`forge.config.mts`, Forge's `windowsSign`); `WINDOWS_SIGNTOOL_PATH` and `WINDOWS_TIMESTAMP_SERVER` are `@electron/windows-sign`'s own. Only such a build updates itself (`SIGNED_BUILD`), and its `EnableCookieEncryption` fuse is on (the key is the Windows user's, so nothing asks). Without the variable the build is unsigned, as in `desktop.yml`. `desktop-release.yml` signs with [Azure Artifact Signing](https://learn.microsoft.com/azure/artifact-signing/): Microsoft's dlib, pinned, with the account, profile and endpoint at the top of its `windows` job, and an OIDC login (`azure/login`, the repository variables `AZURE_CLIENT_ID` and `AZURE_TENANT_ID`, no secret); it fails unless `Get-AuthenticodeSignature` calls every executable `Valid` (`scripts/check-windows-install.ps1`).

What the release cannot sign is what runs later from npm, in `%LOCALAPPDATA%\sanoma-postgres` (PostgreSQL's 123 executables and DLLs) and a company's `node_modules` (oxlint, esbuild and the like): none is signed, so Windows 11's Smart App Control, where it enforces, may block them. See "Not yet".

## What it does

- **Opens a company**: a folder with a `sanoma.config.ts`, from the start screen (Open folder…, Your companies, which marks the ones running), File → Open Company… or Open Recent, the command line, a second launch (which hands the folder to the running shell) or a folder dropped on the Dock icon. A folder iCloud or OneDrive syncs gets a warning on the company's page, and its app waits for Got it, once per folder (`companies.json`). The Intel build on Apple silicon (or the x64 build on an Arm PC) says so on the start screen, with a link to download the other. A folder that holds no company, and any other reason something asked of the shell did not happen (a folder Copy from GitHub cannot use, Get Updates' answer), is said in one line on the start screen, never in a dialog.
- **One window, from the click to the app**: the shell has one window. With no company open it shows the start screen (New company…, Open folder…, Copy from GitHub…, under the companies once there are any), on the app's colours and fonts, light or dark as the system is. Choosing a company turns it into that company at once: its page shows the name and one word for 3 seconds, as most opens are done by then, then the steps, with Stop, then the app in its place once it answers. Show details opens the output in a read-only terminal, with Copy and Show log file, and is remembered for every start. A start that prints nothing for 2 minutes says so, and stops nothing. Opening a company that is open already switches to it, without starting it again. A second company joins the same window and shows; the first goes on running, its app loaded and where it was.
- **Switches companies**: the app's account menu (under your initials, at the bar's foot) lists the window's companies, the shown one checked, and Add company…, which shows the start screen in the window; so do File → Add Company…, the Window menu (⌘1…⌘9, Ctrl elsewhere), the Dock menu and, elsewhere than macOS, the tray icon's menu. The window has no chrome of its own: the app's page fills it. Switching swaps which company's views show, at once; nothing reloads, and every company keeps running. The account menu's Companies needs an app release that has it; on an older one, the menus switch.
- **Installs and starts it**: `pnpm install --prefer-offline` in the folder (when that fails but `node_modules/sanoma` is there, it goes on with a warning), then the launcher `node_modules/sanoma`'s `bin` names, in a process group of its own (on Windows, which has none, a process tree with no console window), with `SANOMA_EVENTS=1` and `SANOMA_APP_PORT` set (which win over the company's `.env`), and `PATH` starting at the shims in `<userData>/bin`: `node` and `pnpm` run the Node and the pnpm the shell ships, whatever the computer has, then the system's `PATH` and Homebrew's. On Windows the shims are `pnpm.cmd` and the Node's own folder (a program that runs `node` without a shell finds only an `.exe`), and `PATH` is the `Path` Windows has.
- **Knows when it is ready** from the launcher's `ready` event, or, for a launcher without events (sanoma 0.6.0 and before), its `<app> at <url>; ctrl-c to stop` line or the first answer from `/healthz`.
- **Shows the app**: the window is a `BaseWindow` holding the start screen and, per company, the shell's own page and the app's view, swapped in place. The app's view has storage of its own (`persist:company-<hash of the folder>`: the app's `sanoma_actor` cookie ignores ports, so two companies must not share one) and is sandboxed. Its only preload is `src/app-preload.ts`, `window.sanomaDesktop`: the window's companies (an id made up at each launch, the name, whether it is shown), switching to one, adding one (the start screen) and a subscription to changes; the shell answers it for the app's own page in its top frame only, never for GitHub's or a public site's page in that view, nor for a window the app opened. Each company keeps its port across starts (`<userData>/companies.json`; a new free one when it is taken), so the page remembers who you are. Links to the app, its public sites (`<name>.localhost:<port>`) and GitHub (the GitHub App's setup returns to the app) stay in the shell; any other web link opens in the default browser.
- **Keeps it running**: closing the window hides it, and every company goes on, its scheduled workflows with it; a click on the Dock icon shows it again. Elsewhere than macOS, a tray icon does (its menu shows the window, lists the companies and quits); there, closing the window with no company in it (and no form waiting on the start screen) quits, and where no tray icon shows (stock GNOME), launching Sanoma again shows the window.
- **Stops it**: Company → Stop, Company → Restart and Quit close the launcher's stdin and send SIGTERM to its group, then SIGKILL after 10 seconds; Quit (Cmd-Q, or Quit in the Dock menu; File → Quit elsewhere) waits for every company. Windows has neither signal: closing stdin is the stop there, and `taskkill /T /F` ends the launcher and everything under it at the deadline. Should the shell or the launcher die there, what they ran ends with them (Node's job object), but for the company's Postgres, which `pg_ctl` starts out of its reach: the company's next launch finds no client on it and stops it at its own end. Company → Stop also takes the shown company out of the window: the next one shows, or the start screen when none is left (a company that stopped on its own leaves the same way). A launcher that stops on its own is not restarted: its company's page shows why (exit code 2 is a problem with the config), its last 200 log lines and Start again, and comes to the front when the window is hidden or shows the start screen with no form open; it never takes the window from the company in use.
- **Remembers**: the window's bounds, in `settings.json`, and which companies are open, in `companies.json`. The companies open at Quit (running, or showing why they stopped) open again in the window at the next launch, in the same order, the one opened last showing. Company → Stop takes a company off that list, as does the line a failed company's page shows ("Don't open it at launch").
- **Logs**: each start's output, timestamped and without colour codes, in `~/Library/Logs/Sanoma/<company>.log` (Electron's `logs` folder: `%APPDATA%\Sanoma\logs` on Windows), the previous start's kept as `.1.log` (Show log file, Company → Show Log, Help → Show Logs Folder). A URL's password or token is hidden first (the launcher's `database` event carries the cluster's).
- **Starts a new company** (File → New Company…, or New company… on the start screen): the start screen asks what it is called and shows where it goes, a folder named after it where the last company is, else in `~/Companies` (Change… picks another place, and a place iCloud syncs warns there). The shell makes the folder and runs the launcher's own init, `pnpm dlx sanoma`, with the shims and the environment of a run. It commits, installs, and then serves the company it started in its place; the page shows two steps, setting up until the launcher's `database` event, then starting, says it takes about a minute and that the window can close. Until a launcher with embedded Postgres is on npm, that needs a Postgres at the URL in `.env` (or Docker); otherwise the company's page shows the launcher's own error.
- **Copies a company from GitHub** (File → Copy from GitHub…, or the same on the start screen): the start screen asks for the repository's address, then a dialog for the folder to clone into; the system git clones it without ever prompting (`GIT_TERMINAL_PROMPT=0`, ssh in batch mode), so a public repository, or one the OS credential helper knows, works. The clone is its page's first step, then the company installs and starts as an opened one does; a failed clone says why in one line there (a failed sign-in points at signing in with GitHub, which comes later, #286 D6), Start again clones again, and Recent does not list it.
- **Checks git first**: on macOS, `xcode-select -p`; without Apple's command line tools a dialog offers their installer and Check Again. Before New and Clone, a missing `user.name` or `user.email` is asked for once on the start screen and set with `git config --global` (the launcher's init commits as them).
- **Gets updates** (Company → Get Updates): only when the company has an `origin`, is on `main` and has nothing of its own (no change in the tree, untracked files included, and no commit GitHub does not have); otherwise it refuses in one line and changes nothing. A `pnpm-lock.yaml` changed in the tree and nowhere else is the shell's own install's doing, not the person's: it counts as clean, and is put back before `main` moves. It fetches `origin`'s `main`, says when there is nothing new, else stops the company, fast-forwards `main` (`git merge --ff-only origin/main`, a `git pull --ff-only` without a second fetch) and starts it again, which installs its packages, in its place in the window.
- **Updates itself** (`src/self-update.ts`): a release build on macOS (signed with the Developer ID) that runs from an Applications folder, or on Windows (signed) as Squirrel's installer put it, asks [update.electronjs.org](https://github.com/electron/update.electronjs.org) at start and every hour (Electron's [`update-electron-app`](https://github.com/electron/update-electron-app)) for a newer release's zip for its architecture (which releases: the root README, "Desktop (preview)"). Squirrel.Mac (Electron's `autoUpdater`) downloads it in the background, checks it is signed by the same team, and installs it when the app next quits, so the next launch is the new version; checks stop until then. Nothing restarts the app or asks anything: Help → Restart to Update, there once the update is downloaded, quits as Quit does (every company stopped, and reopened at the launch) and relaunches the new version. A failed check (offline, the service down) goes to the console only. From the dmg, or opened from elsewhere (App Translocation), the app is on a read-only volume and cannot replace itself, so it does not try. On Windows the offer is the release's `RELEASES` and nupkg; the first check waits 15 seconds on the launch right after an install, as Squirrel holds its lock about 10; and the new version is the next launch's, or Help → Restart to Update's.
- **Checks for a newer version** where it does not update itself (a built app outside Applications, an ad hoc or unsigned build): at start and at most once a day (the time in `<userData>/settings.json`), it asks GitHub Releases for the newest `v*` that is neither a draft nor a prerelease (`src/update-check.ts`). A newer one gets one notification and a Help menu item that opens its release page; Help → Check for a Newer Sanoma asks at once. It never downloads or installs anything.

Not yet: a second window, a company's unread or attention badge, GitHub sign-in, an icon of its own (the tray shows the executable's). On Windows (x64 only; `desktop.yml` builds the packaged app and runs it, New Company and the installer included): the provider bridge has no Windows binary, so resources and Go live fail; the agent's session expects a POSIX shell; PostgreSQL and a company's native modules run unsigned from npm (Signing, above); git is not bundled, and the shell asks for Git for Windows.

## Why it ships a Node

Electron's own Node (24.22 in Electron 45) serves a company, but `sanoma check` crashes in it: oxlint's JS plugins pass the source through memory outside V8's heap, which Electron's V8 sandbox refuses. So the shell carries the official Node 26 (`scripts/download-node.ts`, sha256-pinned; `node.exe` from the Windows `.zip`, which bsdtar reads: macOS's `tar`, Windows' `System32\tar.exe`) in its resources, runs the launcher with it, and points the `node` shim at it, for whatever the company runs.
