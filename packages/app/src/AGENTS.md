## The look

`ui.css` holds the look once, as Tailwind theme tokens: the colours in shadcn's names on `:root` (light) and `.dark` (the brand's palette, then the operation effects, the tones, the code colours and `--overlay`), the fonts (`font-sans` IBM Plex Sans, `font-mono` IBM Plex Mono, `font-display` Fraunces for display only, an empty state's headline, from Fontsource; shadcn's `font-heading` is the sans), `--radius`, the two sizes off Tailwind's scale (`text-reply`, a chat reply's 15 px, and `text-bar`, the bar's 11 px labels) and default gaps; the colours in the theme layer, so a site's own values win (README, "The kit on a site"). `style.css` imports it and adds the shell's: its widths (`--bar-width`, `--chat-width`) and a floating card's (`--float-width`), and on `#app` the gaps and the panes' heights (`h-(--pane)`, `--pane-tall`, `--pane-short`), lower on a phone and, the graph's and the Code card's, when Compact. Change the look there, not in a component.

- A colour is a token (`bg-card`, `text-muted-foreground`, `border-border`); a tint is a token with an alpha (`bg-primary/10`); `bg-white` or `text-red-500` generates nothing. A new colour is a new token, with its dark value, and at least 4.5:1 for text on the fill it sits on.
- A size that repeats is a token: corners from `--radius` (`rounded-lg` a control or a card inside a page, `rounded-xl` a page's card), spacing from `--spacing`, which Compact scales, a pane's height from a `--pane*` variable. In the app's own components an arbitrary value (`w-[100px]`) is for one-off geometry only, never a colour, a type size or a repeated size; the shadcn components keep their upstream ones.
- A control's height and label size are set in its `cva` variants in `components/ui/` (28 px, 12 px medium), the only place.

## The app on the Worker

`buildAppBundle` (`bundle-build.ts`) builds the whole app, every route and site, for workerd, over the same route tree as `buildApp`; `worker/app.ts` serves it with `appHandler`, as the Node adapter does. What the bundle reads of the company is its snapshot, baked in at build time; what writes the repository or runs an agent is a run in the worker (`steps/`), which the bundle leaves out: a chat turn there runs where the instance's worker has the app's steps, and fails at once where it has none. The Worker never prepares the database (`checkPreparedOnly`): the worker does at its start. Its client is the request's own, connected on its first call, so a prerendered or SEO answer opens no connection. The staff sign-in and each site's login run there as on Node: `staffLogin(betterAuthStaffLogin, social)` and `siteLogin` are composed with the handler, and a login half reaches the database through `LoginContext.database`, the request's own pool (`SanomaClient.pool`), so Better Auth (`@sanoma-ai/connector-better-auth`, the one connector the app imports itself, since the staff sign-in is the product's) keeps an instance per pool and nothing across requests; the worker prepares its schemas (`prepareBetterAuth`, `prepareBetterAuthStaff`), never the Worker. The bundle's prerender runs the handler under a throwaway `SANOMA_SIGNING_KEY`, since the logins are made with it and sign nothing a prerendered page holds. `PUBLIC_FNS` stays the visitor's allow-list on a site's host (`publicOnly`).
