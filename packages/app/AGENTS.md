# Working on @sanoma-ai/app

This package owns the local web UI over a Sanoma config. Its server functions are its only HTTP surface, besides a login provider's `/auth/<name>/` routes, `/healthz` (answered before the login) and the GitHub App's manifest flow at `/setup/github/` (server routes in `routes/setup/github/`, behaviour in `src/server/setup.ts`); scripts use `SanomaClient` from `@sanoma-ai/workflows`.

## Maintenance boundaries

- Use `@phosphor-icons/react` for interface icons, with the default regular weight and per-icon imports from `@phosphor-icons/react/dist/csr/<Name>`. Keep `components.json`'s `iconLibrary` set to `phosphor` so shadcn additions use the same library.
- Keep server-only config, credentials, and runtime code out of browser modules. Server functions (`src/functions.ts`) parse their argument and call `src/server/core.ts`, where their behavior lives and where the tests call it.
- Browser modules import values from `@sanoma-ai/workflows` only through `/shared`, and types from the rest; `@sanoma-ai/workflows/scenario` values (`loadScenarios`, `check`) only in `src/server/core.ts`.
- `callFn` is a site's one way in: it calls only what `callApi` (`src/server/core.ts`) dispatches, an operation through `SanomaClient.call` (which keeps the one rule, `isDirect`) or a workflow by `apiNameOf`, always as the person asking. A new kind of call is a new name form there, in `createApi` and in `readSites` (`@sanoma-ai/workflows`' `src/sites.ts`, which reads a site's calls for Used by), never another server function for sites.
- Preserve the loopback Host check, the loopback login's refusal of any other host, the dev server's refusal of any host but this machine (its hot updates' websocket bypasses the login), and actor requirements on mutations. The default typed actor name is not authentication; keep the README accurate when this boundary changes.
- Serve a file's text only for a file the config description names, a workflow's or a data file (`fileSource` in `src/server/core.ts`); never read a path a request makes up. A drift check is an ordinary run (`{ workflow: "drift", input: {} }`) that reads the data files itself; the page's declared list is the description's, read once at boot, joined with the last report's rows.
- `src/routeTree.gen.ts` is generated by TanStack Router; change route sources instead. The package ships `src/` without it: a company's build (`src/build.ts`, [Sites](README.md#sites)) writes its own tree, cache and output under the repo's `.sanoma/app/`, never into the app's install or `node_modules`. The router imports it as `#/routeTree.gen.ts`, which the company's build and its generated tsconfig (`paths`, ahead of this checkout's own tree) point at `.sanoma/app/routeTree.gen.ts`.
- `src/site.ts` is `@sanoma-ai/app/site` (re-exported as `sanoma/site`), exported as source: Vite compiles it in a company's build, never `tsconfig.build.json`. It is browser code, the app's own router's APIs, `defineSite` and `api` (`src/api-client.ts`'s `createApi` over `callFn`, typed by the company's `.sanoma/api.ts` through `Register`; the SDK's types re-exported from `@sanoma-ai/workflows/shared`), with nothing server-side; it does not re-export `createFileRoute`, which a route file imports from `@tanstack/react-router` for the generator. `src/ui.ts` is `@sanoma-ai/app/ui`, the kit, exported as source the same way: an explicit list that `test/sites-build.test.ts` snapshots, so an export is added on purpose, as public surface the app keeps stable; browser code only. The Sites panel finds `sites/*/site.ts` by a root-relative glob (`src/lib/sites.ts`), which matches nothing in the package's own build.
- `vite.config.ts` is `appViteConfig()` from `src/build.ts`: the shipped build and a company's with sites are one pipeline, so a change to the build goes there, and `pnpm build`'s `dist/client` and `dist/server` stay what the zero-site build makes (Tailwind scans the whole package, `test/` too, so a fixture site uses no class the app lacks). `appDevServer` (`startApp`'s `dev`) is that config plus dev-only plugins, so `sanoma check` beside a dev server generates the same route tree. On its server `sanoma` is `noExternal` (why beside it); only an install from tarballs, `packages/sanoma/test/packed.test.ts`, shows a mistake there. `src/build.ts` loads only Node's modules and `@sanoma-ai/workflows/shared` at import (the bin loads it to write the site files); a site's folder name is `SITE_NAME` there, which `readSites` reads by too; Vite and its plugins load when a config or build needs them.
- What the app's source imports at build time is a dependency, not a devDependency: a company's install builds it. Its compiler options live in `tsconfig.site.json` (shipped; `tsconfig.json` extends it), its ambient types in `src/env.d.ts`.

## Checks

Run `pnpm --filter @sanoma-ai/app run typecheck:ui`. Build with `pnpm --filter @sanoma-ai/app build` before `pnpm vitest run packages/app`: `startApp` serves the built app even when imported from source. Integration tests need Postgres; build workflows first in a fresh checkout.
