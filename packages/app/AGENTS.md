# Working on @sanoma-ai/app

This package owns the local web UI over a Sanoma config. Its HTTP surface is its server functions and two server routes, `POST /api/chat` (the operator agent's chat: `routes/api/chat.ts` with its own CSRF middleware, behaviour in `src/server/agent/`) and `POST /api/sign-in` (a code a person pastes back to their own agent's sign-in, `routes/api/sign-in.ts`, `src/server/agent/acp.ts`), besides a login provider's `/auth/<name>/` routes, `/healthz` (answered before the login), `startApp`'s `ingress` (machine routes: the wakeup's `/wake` and the webhooks later; each checks its own token) and the GitHub App's manifest flow at `/setup/github/` (server routes in `routes/setup/github/`, behaviour in `src/server/setup.ts`); on a public site's own host, only `callFn`, `getActor`, the site's login's `/auth/<connector>/` routes and its `/robots.txt` and `/sitemap.xml` (`src/seo.ts`). Scripts use `SanomaClient` from `@sanoma-ai/workflows`.

## Maintenance boundaries

- Use `@phosphor-icons/react` for interface icons, with the default regular weight and per-icon imports from `@phosphor-icons/react/dist/csr/<Name>`. Keep `components.json`'s `iconLibrary` set to `phosphor` so shadcn additions use the same library. The one exception is a site's own icon, a Lucide name in its `site.ts`, which only `SiteIcon` (`src/components/site-icon.tsx`) draws, with `lucide-react`, from the icons the build imports by file (`virtual:sanoma/icons` in `src/build.ts`): `lucide-react` stays pinned exactly, since those files are its layout, not an export.
- Keep server-only config, credentials, and runtime code out of browser modules. Server functions (`src/functions.ts`) parse their argument and call `src/server/core.ts`, where their behavior lives and where the tests call it.
- Browser modules import values from `@sanoma-ai/workflows` only through `/shared`, and types from the rest; `@sanoma-ai/workflows/scenario` values (`loadScenarios`, `check`) only in `src/server/core.ts`.
- `callFn` is a site's one way in: it calls only what `callApi` (`src/server/core.ts`) dispatches, an operation through `SanomaClient.call` (which keeps the one rule, `isDirect`) or a workflow by `apiNameOf`, always as the person asking. A new kind of call is a new name form there, in `createApi` and in `readSites` (`@sanoma-ai/workflows`' `src/sites.ts`, which reads a site's calls for Used by), never another server function for sites.
- A public site's host (`startApp`'s host table, then `login/public.ts`'s `publicFront`) is answered ahead of the staff login and never reaches it: there only `callFn` and `getActor` answer (`PUBLIC_FNS` and `publicOnly` in `src/middleware.ts`), as the visitor the site's login half verifies or `anonymous`, never as the staff login's cookie or header. The router learns the site from Start's request context on the server and `<html data-site>` in the browser, never from the URL's host; the app's chrome and root queries stay out of the root's static imports (`components/app-chrome.tsx`, loaded lazily), so the public host never loads them.
- Preserve the demo login's refusal of an app not started with `demo: true` (it admits anyone as any declared person, and a demo's every vendor is a fake), and what a demo refuses so that nothing outlasts its reseed: the agent's routes and Go live (`DEMO_CLOSED` in `src/index.ts`), and the server functions `DEMO_REFUSED` names (`notInDemo` in `src/middleware.ts`).
- Preserve the loopback Host check, the loopback login's refusal of any other host, the dev server's refusal of any host but this machine (its hot updates' websocket bypasses the login), and actor requirements on mutations. The default typed actor name is not authentication; keep the README accurate when this boundary changes.
- Serve a file's text only for a file the config description names, a workflow's or a data file (`fileSource` in `src/server/core.ts`); never read a path a request makes up. A drift check is an ordinary run (`{ workflow: "drift", input: {} }`) that reads the data files itself; the page's declared list is the description's, read once at boot, joined with the last report's rows.
- `src/routeTree.gen.ts` is generated by TanStack Router; change route sources instead. The package ships `src/` without it: a company's build (`src/build.ts`, [Sites](README.md#sites)) writes its own tree, cache and output under the repo's `.sanoma/app/`, never into the app's install or `node_modules`. The router imports it as `#/routeTree.gen.ts`, which the company's build and its generated tsconfig (`paths`, ahead of this checkout's own tree) point at `.sanoma/app/routeTree.gen.ts`.
- `src/site.ts` is `@sanoma-ai/app/site` (re-exported as `sanoma/site`), exported as source: Vite compiles it in a company's build, never `tsconfig.build.json`. It is what talks to the running app, as browser code with nothing server-side: the app's own router's APIs, `defineSite`, `api` (`src/api-client.ts`'s `createApi` over `callFn`, bound in `src/queries.ts`, which the app's own calls share; typed by the company's `.sanoma/api.ts` through `Register`; the SDK's types re-exported from `@sanoma-ai/workflows/shared`), `content`, a public site's languages (`defineMessages`, `useMessages`, `useLocale`, `useLocales`), `RunForm` and `useActor`; it does not re-export `createFileRoute`, which a route file imports from `@tanstack/react-router` for the generator. `src/ui.ts` is `@sanoma-ai/app/ui` (re-exported as `sanoma/ui`, the one path a site imports it by), the kit, exported as source the same way: how a page looks, presentational only, so it could become a package of its own with no change to a site. Nothing it exports may reach the running app; a piece that needs the app goes in `site.ts`, or stays internal. `test/ui.test.ts` holds its module graph to that and snapshots its explicit list, so an export is added on purpose, as public surface the app keeps stable. The kit's own pieces are `src/components/kit.tsx`, which `components/common.tsx` re-exports for the app's screens. The Sites page and the bar find `sites/*/site.ts` by a root-relative glob (`src/lib/sites.ts`), which matches nothing in the package's own build.
- `vite.config.ts` is `appViteConfig()` from `src/build.ts`: the shipped build and a company's with sites are one pipeline, so a change to the build goes there, and `pnpm build`'s `dist/client` and `dist/server` stay what the zero-site build makes (Tailwind scans the whole package, `test/` too, so a fixture site uses no class the app lacks). `appDevServer` (`startApp`'s `dev`) is that config plus dev-only plugins, so `sanoma check` beside a dev server generates the same route tree. On its server `sanoma` is `noExternal` (why beside it); only an install from tarballs, `packages/sanoma/test/packed.test.ts`, shows a mistake there. `src/build.ts` loads only Node's modules and `@sanoma-ai/workflows/shared` at import (the bin loads it to write the site files); a site's folder name is `SITE_NAME` there, which `readSites` reads by too; Vite and its plugins load when a config or build needs them.
- The chat's coding agents (`src/server/agent/harness.ts`) run through `HarnessAgent` in `LocalSession`, whose environment is explicit (never `process.env`); the model's key reaches an adapter only as its `auth` record, never in a log, a fixture or a session's environment. `@ai-sdk/harness*` stay pinned exactly and outside the server bundle and resolved from the app's install (`OWN` in `src/build.ts`): an adapter reads its bridge's files beside its own `dist/`. They sit on `@ai-sdk/harness` 1.0.158, whose exact `ai` the workspace's `overrides` raises to the one pin; move to the latest set, and drop the override, once their bridges ship lockfiles again (vercel/ai#23829). The override is this workspace's alone: a company's install keeps 7.0.147 under `@ai-sdk/harness`, and needs the template's `allowBuilds` (`packages/sanoma/template/pnpm-workspace.yaml`) for Pi's model providers under pnpm 11.
- A person's own coding agents (`src/server/agent/acp.ts`) run over our ACP client on `@agentclientprotocol/sdk`, pinned exactly (its default import speaks ACP v1). The agents are not dependencies: `OWN_AGENTS` pins each one's packages, installed on first use by `pnpm add --ignore-scripts --ignore-workspace` (no native module, nothing pnpm 11 would stop on) under the repo's `.sanoma/agent-home/acp/<agent>`, never npm (the desktop shell ships none; `install` says why); a version bump there is a new install. Each runs as a child with an explicit environment (`sessionEnv`, never `process.env`), its `HOME` the person's own (`.sanoma/agent-home/people/<id>`, by id, never an email) and shims refusing `gh`, `security`, `open` and `xdg-open` first on its `PATH`, so only the person can sign it in; the engine refuses a principal that is not a person, and nothing of ours reads that `HOME`. A sign-in is the vendor's flow, shown on the card: never open its link, enter its code or keep either in the transcript once it ends, and never add a pseudo-terminal library (a vendor whose sign-in needs a real terminal gets the "run it once on this computer" card). Its read and edit requests and `fs/*` go through `allowedPath`, `allow_always` is never chosen and only an offered option returned; what it runs through `terminal/*` is its own.
- The coding agents' state, kept across restarts under the repo's `.sanoma/agent-home`, is three directories (`agentHome` in `src/server/agent/checkout.ts`), so that no engine's files cover another's: `harness`, the `HarnessAgent` session's home (Claude Code's bootstrap and the bridges' run files, Pi's settings), which with the draft is all `LocalSession`'s path rule allows; `acp/<agent>`, a person's own agents' installs (and `acp/shims`; the install's `HOME` is `acp`, so pnpm's store stays there); `people/<id>`, each person's own agent's `HOME`, given only to that person's child and read by nothing of ours (an ACP agent's `fs/*` is the draft's only). Never give an engine a home that holds another's directory. Nothing below the machine user isolates people on a shared instance: what an agent runs itself, and Claude Code's own reads, can reach another person's directory.
- The Permissions grid is the runtime's `permissionsGrid` (`@sanoma-ai/workflows/describe`), which `sanoma check` reports too: `permissions` in `src/server/core.ts` adds only the policy and its files, so a change to the grid goes there, never here. A draft's check is the repository's (`Source.check`, the `sanoma` package's `localGitSource`); `src/server/drafts.ts` hands its result to the draft's card and the agent without the grid. Two grids are diffed by `src/lib/grid-diff.ts` and shown by `components/permissions-diff.tsx` through the page's own `PermissionsTable`, so the page and a change's review render one table. A change's pages (`routes/changes/`) read `SanomaClient.changes` and `.change` (`getChanges`, `getChange`), its Publish is its run's pending approval covering `sanoma.change.merge`, decided as any approval is, and the bar shows Changes only when the repository has a remote (`getRemote`, never the URL, which may carry a token).
- What the app's source imports at build time is a dependency, not a devDependency: a company's install builds it. Its compiler options live in `tsconfig.site.json` (shipped; `tsconfig.json` extends it), its ambient types in `src/env.d.ts`.

## Checks

Run `pnpm --filter @sanoma-ai/app run typecheck:ui`. Build with `pnpm --filter @sanoma-ai/app build` before `pnpm vitest run packages/app`: `startApp` serves the built app even when imported from source. Integration tests need Postgres; build workflows first in a fresh checkout.
