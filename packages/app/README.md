# @sanoma/app

A web UI for a [Sanoma](https://github.com/Sanoma-AI/sanoma) config: the runs, each run's ledger and approvals, a form to start a workflow, and what each workflow may call. It reads the same `sanoma.config.ts` your worker runs, so it shows exactly what the worker enforces: it renders from `describeConfig(config)`, the config's ledger store and Postgres. The only workflow code it reads is each workflow's `run`, once at start, to draw its outline. It runs no workflows itself. The page talks to the server through TanStack Start server functions, its only HTTP surface; scripts and agents reach the same runs through [`SanomaClient`](https://www.npmjs.com/package/@sanoma/workflows#building-your-own-ui), over the same Postgres.

It is a [TanStack Start](https://tanstack.com/start) app (React, TanStack Router, Query and Form), built into the package and served by `startApp` from Node.

## Usage

```sh
npm install @sanoma/app @sanoma/workflows
```

The [`sanoma`](https://www.npmjs.com/package/sanoma) bin runs the app beside the worker over a repo's `sanoma.config.ts`; `startApp` remains for a custom host. Run it beside the worker, from the same config:

```ts
import { startApp } from "@sanoma/app";
import config from "./sanoma.config.ts";

const app = await startApp(config, { port: 3000 });
console.log(app.url); // http://127.0.0.1:3000
```

`startApp` checks the config first and throws what the worker would refuse (missing credentials refuse nothing: the connector pages show and set them). The worker and the app share the config's Postgres (`databaseUrl`, else `SANOMA_DATABASE_URL`): the runs, the credentials and, by default, the ledger, which `postgresLedger` keeps in a table there, so the app reads what a worker in any process records. A config with a `jsonlLedger` shares its directory instead, and a `memoryLedger` is visible only in the process that wrote it. A run that has started but has no records in the app's ledger says so on its page, since the likeliest cause is an app on another ledger than the worker's (another database, or a `jsonlLedger` directory relative to another working directory). Without `port`, the app takes any free port and reports it in `app.url`. `app.close()` stops it.

## Screens

Four pages, in the sidebar: Inbox, Workflows, Resources and Connectors. The app opens on Workflows, its home, which shows each workflow and how its runs went. Old links still work: `/` redirects to `/workflows`, `/runs` to its All runs view, `/runs/<id>` to the run's page under its workflow, and `/start?workflow=<name>` to that workflow's page with its New run panel open, which says if the workflow is unknown (`/start` naming none, to `/workflows`).

- **Workflow** (`/workflows/<name>`): one workflow's page, which takes the window's full width (the other pages keep to a reading width). Its header names the workflow, with **New run** at its end (none for a retired workflow), which opens the New run panel on the pane that shows. Beside the pane, or above it on a narrow screen, a rail links to **Workflow**, the workflow's own pane, then lists its latest 50 runs, newest first: each with its status (and, while it waits, the first approval it waits on), a sandbox run's badge, who started it and when, linking to its pane. The rail's menu shows all of them, or only live, sandbox, waiting or failed runs, kept in the URL as `?runs=`, which the page's links keep: live and sandbox are picked from the latest 50 (so the rail says it found none, or lists those it found, among the latest 50), while waiting and failed are the latest 50 with that status, however old. The runs refresh every 2 seconds while one of them can still change, else every 30 seconds, and at once when you start a run or decide an approval. The rail ends with **All runs of this workflow →**, the Workflows page's All runs filtered to it. Its button folds it to a narrow column: the button to unfold it, **Workflow** as an icon, and each run as a dot in its status's colour, its status, starter and time in its tooltip. The rail stays as you left it on your next visit, kept in a cookie (`sanoma_rail`), so the server renders it folded or not from the first paint. A workflow the config no longer has keeps its page while it has runs: its header names it, its own pane says it is gone, and its runs draw a graph with only its name. With no runs either, its page is not found.

  Both panes are one view of the workflow, drawn by its design or by the run picked in the rail. Under a run's status and a notice for what it waits on (who, and for which approval, with **Show approval** to select it) or why it failed, the graph's card sits beside an inspector, or above it while the pane is narrow; under them, the **Code** tab (and on a run's pane **Ledger**, open at first). Clicking a node selects it: the graph rings it, Code marks its lines, and the inspector shows it, closing New run if it is open. Clicking a line in Code selects its node, and a ledger row's **Show in graph** button selects the node it is drawn as. The inspector shows, first match wins:
  - **New run**, while the URL has `?new` (its close button drops it), on either pane: two links, **Live vendors** and **Sandbox**, each its own URL (`?scenario=<name>` is Sandbox with that scenario, none is Live), then the form. `/workflows/<name>/new`, the old New run URL, redirects here, keeping `?scenario=` and `?runs=`.
    - **Live vendors**: says which vendors the run calls for real, then the form, built from the workflow's input schema: text, date and time (in your browser's time zone, shown as its ISO text until the page has loaded), numbers, yes/no, choices, lists with Add and Remove, and objects one level deep; anything else is entered as JSON. Optional fields left empty are left out, so the schema's defaults apply. The server checks the input with the workflow's schema and its complaints appear on the fields they name. **Start run** starts it and opens the run.
    - **Sandbox**: a menu of the workflow's [scenarios](https://www.npmjs.com/package/@sanoma/workflows#scenarios-and-sandbox-runs) (**Sandbox** opens the first; with none, it is disabled and says so), and the form showing the chosen scenario's input with its controls disabled and no Add or Remove, since a sandbox run takes its input from its scenario. **Start sandbox run** starts it and opens the run: nothing leaves Sanoma, the fakes answering its calls. The scenario's lines of its feature file are behind **Scenario**, and the workflow's graph badges each operation a `Given` seeds ("seeded") or makes fail once ("fails", for `fails once`, `is rate limited once` and `loses its reply once`), and one a `Then` expects to be called ("expected"), not called ("not called"), denied by the policy ("must deny") or held by it ("must hold"), matching an outline's computed segment (`*`) as the run graph does. A scenario the feature files do not have says so. The scenarios are read again every 5 seconds while the page is open and when its window regains focus, so an edited feature file shows up without a restart; a file that cannot be read says why at the top of the workflow's pane. The app decides nothing: the run's approvals wait for people, as a live run's do. Each sandbox run calls its own copies of the fakes, so several run at once, and one waiting on an approval holds up no other.
  - **The selected node**: its kind, its step's name (when its call gives one) and label; for an operation, its id, effect and vendor and what it does; and **Lines a–b** of the source, which opens Code. On a run's pane, also the node's ledger records (a held call's with the policy's request and decision, an approval's with its decision), and the approval it waits on with **Approve** and **Reject**, so it is decided in place.
  - With nothing selected, **About** on the workflow's pane: what it may call, its operations with their effects, its built-ins and its input; on a run's pane, the run's facts (who started it, when and its id) and its approvals, each with the operations it lets through (badged by effect), and **Approve** and **Reject** with an optional note while the run can still read a decision. When the run has not read a decision within 5 seconds (no worker is running, say), it stays queued and the run reads it when it next runs: the dialog closes and the page shows the decision as queued, with Approve and Reject disabled for that approval, until the run's status changes.

  The panes:
  - **Workflow** (`/workflows/<name>`): the workflow's outline (see [Outline](#outline)), and its source under Code.
  - **Run** (`/workflows/<name>/runs/<id>`): the run's status (a sandbox run badged `sandbox · <scenario>` beside it) and its graph (see [Run graph](#run-graph)). Its Ledger tab lists a sandbox run's **Checks**, drawn as the ledger's rows are: each `Then` of its scenario, which Cucumber runs against the ledger, each on its own, met, failed with why, or "not yet" while its answer can still change (until the run ends, unless it expects a call that has been made); when the run's scenario is no longer in the feature files, or they cannot be read, Checks says why instead. Then the ledger as a timeline: the start, each operation call with its effect, the policy's decision, duration, input and output, each approval asked, decided or ignored, and how it ended; a sandbox run's says how many calls it was seeded with. A run of another workflow opens under its own.

- **Inbox** (`/inbox`): a list of approvals beside the one that is open, which stacks above it on a narrow screen. Three links pick the list, each its own URL (`?show=`): **For you**, the pending approvals you may decide (the default once the page knows who you are), **All waiting**, every pending approval (the default until then), both newest first and with how many they list, and **Decided**, the approvals decided in the latest 50 runs, latest first. Each row has the approval's title, its workflow, who started the run and how long ago it was asked (a decided one: its decision, and how long ago it was made), and opens it (`?approval=<runId>/<approvalId>`). The open one, by default the first for you, else the first, is a sentence saying whose run of which workflow wants to do what (the operations it lets through, such as "publish a post in Ghost"), above its card, with the same controls as on its run's page. Once you decide, it leaves the list and the next one opens. Refreshes every 5 seconds.
- **Workflows** (`/workflows`): the home. Its top card names the app, the config's version and whether a policy is configured (and its version). Two links, **By workflow** and **All runs**, switch between its two views, each its own URL. **By workflow** shows a card per workflow in the config: its title (linking to its page), its name, built-in for the built-in `drift` (which starts like any other, with no input), the vendors its operations call, in order of title, and its last 12 runs as a strip of squares, oldest to newest, coloured by status (a sandbox run fainter), each linking to its run and naming its status, workflow, time and scenario; the strip is read in the browser and refreshed every 5 seconds while one of its runs can still change, else every 30 seconds, and says "No runs yet" before any. Beside it, how many approvals its runs wait on; then **Test** (when it has scenarios), which opens its page's New run in Sandbox mode with its first scenario chosen, **Run**, which opens its page's New run, and its outline (see [Outline](#outline)). What it may call, its built-ins and its input are on its page. **All runs** (`?view=runs`) lists the latest 50 runs of every workflow, newest first: each with its workflow (linking to the run's page under its workflow, the run's id as its tooltip), a sandbox run's badge, its status, who started it and when, how many approvals it waits on, and a failed run's error. Its **Status** menu shows only the runs with that status, the latest 50 however old, kept in the URL as `?status=`; `?workflow=<name>`, which a workflow's rail links to, shows only that workflow's, named beside the menu with a button that removes it. The table refreshes as a workflow's rail does.
- **Resources**: each resource the data files declare (its name, type and vendor, and the declaration it comes from, which opens in its file below the table, marked), with the latest drift check's verdict: clean, drifted (with each field that differs, as declared and as the vendor holds it, shown under its row), gone, error (and why), or not checked. **Run drift** starts the built-in `drift` workflow, which reads the data files as they are then; the page reads the drift runs as a workflow's rail does, every 2 seconds, links to the latest run, and shows the report of the latest that finished. Problems in the data files show above the table, each at its file, line and column, since their resources are left out: those the app found when it started, and any the last check found. The declared list is the one the app read when it started (`describeConfig`), so a data file changed since shows in the last check's rows and problems, but its declaration opens only once the app is restarted (to do: read the files again when they change).
- **Connectors**: each vendor the config's operations are from, by title, with its logo and id, how many operations it has and how many workflows use it, and, when its drivers declare environment variables, whether it is configured or how many variables it needs, each linking to its page.
- **Connector** (`/connectors/<vendor>`): links to its connector's npm package and source (from `defineConnector`'s `package` and `homepage`, when it gives them), its resource types, and each operation with its effect, whether it is safe to retry, its description, its contract (input and output as JSON Schema), its scenario `phrases`, the scenarios with a step about it (each marked as seeding it, making it fail, expecting it or saying it must not be called, and linking to its workflow's New run in Sandbox mode with it chosen), and the workflows that may call it; a feature file that cannot be read says why above the operations, as on a workflow's page. A vendor with workflow operations whose connector attaches no fake (its `VendorEntry`'s `fake`) says "Its connector attaches no fake" once, above its operations; one with only a resource type's `read` and `import` needs none, since those read real state and a sandbox run never calls them.

For a vendor whose drivers declare the environment variables they read (see [Credentials](https://www.npmjs.com/package/@sanoma/workflows#credentials)), the connector's page lists them under **Credentials**, above its operations: each variable's name, its description, whether it is optional, and its status: set, missing, or invalid with the reason. A variable the app's environment sets says "set in the environment" and has no controls, since the environment wins. Any other has **Set** (**Replace** once set), which opens a small form with the variable's description and a password field: **Save** stores the value in the runtime's database as you, and running workers load it without a restart; the schema's reason for refusing a value shows under the field. A stored value reads "set · by <who> · <when>" and has **Clear**, which deletes it. The page never shows a value, and the form forgets what you typed once it closes. The statuses are read when the page asks, from the app's environment and the stored values, so run the app on the worker's environment.

The screens share one shell: a sidebar with the pages (Inbox badged with how many approvals are pending), each workflow listed under Workflows (badged with how many approvals its runs wait on) and, above the page, a breadcrumb (the page; or Workflows, the workflow's title and, on a run's pane, the run's id; or Connectors and the connector's title). **Collapse sidebar**, at the foot of the sidebar, or Ctrl+B (⌘B on a Mac), folds the sidebar down to its icons (**Expand sidebar** opens it again), and the sidebar opens as you left it on your next visit (it keeps that in a cookie); on a phone the sidebar is a sheet over the page, opened from the toggle beside the breadcrumb, that closes as you follow a link. **Density**, in the sidebar's footer menu under the theme, switches the page to **Compact**, a tighter density for people who live in the app: the page beside the sidebar a quarter tighter in every padding, gap and control (its icons too; the text keeps its size), half the gap between a page's regions, a lower graph card and source and one-line runs in a workflow's rail (status and when). Switching it on folds the sidebar to its icons once (not on a phone); switching back to **Comfortable** leaves the sidebar as it is. The browser remembers the density as it does the sidebar, in a cookie (`sanoma_density`), so the server renders the page in it from the first paint. The sidebar's footer is a menu with who you are (and Change name, under the default resolver), the theme (light, dark or the system's, which the browser remembers) and the density. The screens are built with [shadcn/ui](https://ui.shadcn.com) components (`src/components/ui`, from `components.json`) on Tailwind CSS.

### Run graph

A run's pane draws the run as a graph, left to right: the start, each operation call (its effect, the policy's decision, its duration or error), each sleep, each approval the workflow asked for, and how the run ended, or a dashed end while it has not. An approval the policy asked for sits on the call it holds. The calls of one `ctx.all` branch out side by side and join again after it. Each node's colour says how it went: done, failed or denied, waiting on a person or a sleep, or running. The graph is read from the ledger alone, so it shows what happened, not what the workflow may still do, and it redraws as the page polls. Clicking a node shows it in the inspector, scrolls to its record while the Ledger tab is open, and marks the call in the workflow's source under **Code**: the one the worker placed the call at, which the record names (`node`), when the source still has that call there, so a loop's every pass marks its one call, and a call from a ledger written before calls were placed, or whose file has changed so that another call or none is where it was, marks nothing rather than a guess. Clicking a call in the source selects its node: of a loop's passes, the latest. A sleep is labelled with the time it ends, in UTC, as the ledger shows times, so the server and every browser draw the same text. It is drawn with [React Flow](https://reactflow.dev) in the browser only; the server renders a placeholder of the same size, the graph's code loads, once, only on the pages that draw a graph (a workflow's page and Workflows), starting as the page's data loads, and each graph is drawn when it first scrolls near the screen. A graph pans sideways with the scroll wheel or a drag; its zoom control (React Flow's zoom slider, in the bottom left corner) zooms out and in, shows the zoom (a click sets it back to 100%), and fits the whole graph in view.

A `ctx.all` draws as one lane per member, top to bottom in member order, between the step before it and the step after: in a run that posts to three vendors at once, sleeps, then reads two results at once, the graph shows three lanes, the sleep, then two lanes, each lane coloured as its call went (a call the policy holds waits in its own lane). While a `ctx.all` is the last thing the run has done and the run goes on, each member that has recorded nothing yet has a dashed "not started" lane. Members that never ran, after one failed, or once the run has moved past the group or ended, have no lane. An operation whose call has a [step name](../workflows/README.md#step-names) other than its id says the name, with the id on the line below; a sleep with a name says it the same way, above its clock and the time it ends. A long loop label is cut short in its box; hovering shows it whole.

### Outline

Each workflow card on the Workflows page, and a workflow's page, draw the workflow's shape before it runs, from the `outline` that `describeConfig` (`@sanoma/workflows/describe`) reads once per workflow when `startApp` starts; the source under a workflow page's Code tab is the workflow's file as it is when the page asks for it. It is the run graph's drawing without colours: the operations (with their effects), approvals and sleeps the body of `run` calls, a `ctx.all` as lanes, a loop or a `ctx.all` over a list as a box labelled from its code ("for each of subscribers", "repeat while more") (the line into the box goes on inside it to its first nodes, and its last nodes join the line out), an operation or sleep by the name its call gives, and an `if` or `switch` as a diamond that splits into one lane per case, plus a lane marked "otherwise" when the run can go by without any of them (an `if` without `else`, say). It is a reading of the source, labelled so: "Read from the body of run; the functions it calls are not shown, even those defined in it". When the source cannot be read the card says why instead.

## No authentication

This is a local tool. There is no login. The page asks "Who are you?" once, keeps the answer in the browser, and sends it, URI-encoded, in the `x-sanoma-actor` header with every server function call; a change that names nobody is refused. Anyone who can reach the app can start runs and decide approvals as any name they type; the approver check only compares names. The app listens on 127.0.0.1 unless you pass another `host`. While it listens on this machine only, it refuses every request (page, server function or static file) whose `Host` names anything but this machine, so another site cannot reach it through DNS rebinding. Do not expose it to a network you do not trust.

Reads are open. Anyone who can reach the app sees every run, its ledger (each operation's input and output included) and its approvals, through the page and the server functions it reads them with; nothing asks who they are. On this machine, the Host check above is the only protection. A failure the app does not expect shows only "Something went wrong": its message can name internal details, such as a database host, so the app logs it instead.

### Hosted

A hosted deployment puts its own authentication in front of the whole app (a reverse proxy or an identity-aware proxy), since the app checks no one on a read. It also replaces the header with its own login through `resolveActor`, which turns each request into the person acting (`{ id, groups? }`), or `undefined` to refuse a change:

```ts
await startApp(config, { resolveActor: async (request) => sessionUser(request) });
```

With its own `resolveActor`, the page never asks for a name: it shows who the deployment says you are. An approval addressed to a group (`{ group: "finance" }`) can be decided only by a principal whose `groups` lists it, and the default header carries a name only, so group approvals need a `resolveActor` that supplies `groups`. The app calls `resolveActor` only for a request that needs to know who is asking, once per request. One that throws fails the change with a 500, logged as "Could not tell who you are: " and the resolver's message; the sidebar's footer says "Could not tell who you are" and asks again every 10 seconds.

## Developing

In the repo, `pnpm --filter @sanoma/app build` builds the app (`vite build` into `dist/client` and `dist/server`, and the `startApp` entry). `startApp` serves that build even when run from source, so rebuild after changing anything under `src/` except `index.ts`.
