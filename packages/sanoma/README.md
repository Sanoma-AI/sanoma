# sanoma

One command over a company repo: `sanoma` runs its workflows and the app, `sanoma check` checks it, `sanoma env` writes its `.env.example`, `sanoma ledger export` exports a run. It also carries the surface a workflow imports (`defineWorkflow`, `defineConfig` and the types), so a repo depends on `sanoma` and its connectors, and writes no `worker.ts`, `app.ts`, compose file or vitest config.

## Start a company

```sh
mkdir acme && cd acme
npx sanoma
```

In an empty directory (dotfiles aside), `sanoma` starts a company there, then runs it: it copies the template this package ships (`template/`: `sanoma.config.ts`, a `publish-post` workflow with its scenarios, `policies/policy.cedar` and `policies/changes.cedar` (every change waits for `admin`), `resources/people.ts` with you as its first person (your GitHub login as `gh` is signed in, else this machine's user name, named as git's `user.name`), an empty `resources/` tree, `AGENTS.md`, `.env.example`), names the package after the directory, writes `.env` with a new `SANOMA_SECRETS_KEY` (keeping what a `.env` there already sets; no database URL, so the company runs on [its own Postgres](#postgres)), commits what it wrote (never a dotfile that was already there) as the first commit of a git repository on `main`, "Start a Sanoma company", as your git user, then installs with the package manager that ran it (`npm_config_user_agent`; pnpm when it names none), with `sanoma` at its own version and each other package the template names at `latest`, and adds the lockfile to that commit. The `sanoma` it installed then serves the company. Without git or a git user it stops before writing anything; a failed install leaves the commit, to install and run `sanoma` again in. A directory holding anything else and no `sanoma.config.ts` is refused, as for every command.

## Install

```sh
npm install sanoma @sanoma-ai/connector-ghost
```

`sanoma` brings `@sanoma-ai/workflows`, `@sanoma-ai/app`, `zod`, `typescript`, `@types/node` and `oxlint` with it: a repo installs nothing else but its connectors. Node's types reach the repo's `tsc` through `sanoma` itself (its declarations reference them, resolved from where it is installed), under pnpm, npm or a link alike, so a repo lists no `@types/node`. A repo that lists its own of another major gets two sets of Node's declarations, which conflict: keep one, by matching sanoma's or letting the installer dedupe them. A tsconfig project that imports nothing from `sanoma` (a scripts directory with a tsconfig of its own, say) gets none this way: it sets `"types": ["node"]` and lists `@types/node` itself. Node 26 or later. Nothing else: the [Postgres](#postgres) it starts comes with it, as `@sanoma-ai/postgres-<platform>`, an optional dependency.

A repo holds `sanoma.config.ts` at its root, with `workflows/`, optional `policies/` (Cedar files), `resources/` (data files, the people among them) and `scenarios/` (feature files) beside it, and a `tsconfig.json` that extends the one this package ships:

```json
{
  "extends": "sanoma/tsconfig.json",
  "include": ["sanoma.config.ts", "workflows", "resources"]
}
```

```ts
// sanoma.config.ts
import { ghost } from "@sanoma-ai/connector-ghost";
import { defineConfig } from "sanoma";
import publish from "./workflows/publish.ts";

export default defineConfig({
  workflows: [publish],
  connectors: [ghost],
});
```

Each connector carries its driver and its fake, so the config names neither. The rest is the repo's layout: the app's name is `package.json`'s `name`, the scenarios are `scenarios/`, the data files `resources/` and the policies `policies/**/*.cedar`, beside `sanoma.config.ts` (see [People and policies](#people-and-policies)). The ledger is Postgres's, on the config's database; `ledger: jsonlLedger(dir)` keeps it in files instead.

```ts
// workflows/publish.ts
import { ghost } from "@sanoma-ai/connector-ghost";
import { defineWorkflow, z } from "sanoma";

export default defineWorkflow({
  name: "publish",
  trigger: "manual",
  input: z.object({ id: z.string() }),
  uses: [ghost.post.publish],
  run: (ctx, { id }) => ctx.ghost.post.publish({ id }),
});
```

A workflow imports from `sanoma` what the lint lets it (`defineWorkflow`, `mayDecide`, `errorCode`, `z`, and types); `zod` itself and `@sanoma-ai/workflows` are accepted too. The config file imports `defineConfig` (and a ledger store, `jsonlLedger`, `memoryLedger` or `postgresLedger`, when it names one) from `sanoma`, and its connectors from their packages. A site, `sites/<name>/` (pages the app serves under `/sites/<name>/`; `defineSite({ public: true, login })` in its `site.ts` marks one for visitors, served at the root of its own host too, and `locales` its languages), imports `defineSite`, the app's route APIs (`Link`, `Outlet`, `useNavigate`, …) and `api`, which calls the company's operations and workflows as the person on the page ([calling operations and workflows](https://www.npmjs.com/package/@sanoma-ai/app#calling-operations-and-workflows)), from `sanoma/site` with the rest of what talks to the app (`RunForm`, a workflow's start form, and `useActor`, who is signed in), how its pages look (the app's components, presentational only) from `sanoma/ui`, and `createFileRoute` from `@tanstack/react-router`; the [app's README](https://www.npmjs.com/package/@sanoma-ai/app#a-sites-imports) has the whole list. A data file under `resources/` imports `secret` and `sanoma` (the people types) from `sanoma/resources`, and `resources/data.ts`, the company's [collections](../workflows/README.md#collections), imports `collection` from `sanoma/data` and nothing else:

```ts
// resources/data.ts
import { collection } from "sanoma/data";

export const outbound = collection({
  name: "outbound",
  key: "company",
  fields: { company: "text", stage: { enum: ["researched", "contacted", "won", "lost"] }, owner: "person" },
});
```

Every command that loads the config imports `resources/data.ts` too, when there is one, and adds its collections to the config's `collections` (each of its exports must be one), so `sanoma.config.ts` does not list them. A workflow that calls `ctx.data.outbound.get` imports `outbound` from `../resources/data.ts` to name it in `uses`: the one file outside `workflows/` the lint lets it import.

## People and policies

`resources/people.ts` declares who uses the company's app, the agents that act in it and the groups ([people](https://www.npmjs.com/package/@sanoma-ai/workflows#people)), and `policies/*.cedar` who may do what ([policies](https://www.npmjs.com/package/@sanoma-ai/workflows#policies)):

```ts
// resources/people.ts
import { sanoma } from "sanoma/resources";

export const ada = sanoma.person({ id: "ada", name: "Ada Ortiz", email: "ada@acme.test", github: "ada-ortiz" });
export const bo = sanoma.person({ id: "bo" });
export const editor = sanoma.group({ name: "editor", members: [ada] });
```

```cedar
// policies/policy.cedar
@hold("editor")
@title("Review before it goes out")
forbid (principal, action in [Sanoma::Action::"effect:publish", Sanoma::Action::"effect:send"], resource)
unless { principal in Sanoma::Group::"editor" };
```

Only a declared person signs in to the app (on this machine by picking their name; with GitHub sign-in by their verified email, then their `github` login), starts a run, calls an operation or decides an approval, and nobody decides an approval on a run they started while someone else in the group could (a founder alone in a group decides their own, and the ledger says so). Everything is allowed unless a `forbid` refuses it: one with `@hold` waits for that group's or person's approval, one without is denied with its `@reason`. A visitor of a public site, in the group `visitors` (or `anonymous`, when nobody is signed in), is the exception: it may start a run or call an operation directly only where a `permit` names it, the one `permit` a policy file may hold (`permit (principal in Sanoma::Group::"visitors", action == Sanoma::Action::"workflow:signup", resource);`), and inside a run it started its calls are allowed as anyone's, the forbids still holding. Write them against `.sanoma/schema.cedarschema`, which `sanoma check` and `sanoma` write from the config: each operation's id as an action in its effect's group, `workflow:<name>` for a run's start, the groups the people file declares, and each operation's input as `context.input`. `sanoma check` reports a policy problem at its place and runs no scenario until there are none; `sanoma` refuses to start on one. A scenario runs as the agent `scenarios` unless it says who is acting (`Given bo is acting`, `Given a visitor is acting`, `Given anonymous is acting`), and checks the policy with `Then ghost.post.publish was held for group "editor"` and `Then <op> was denied with "<reason>"`. The app's Permissions page shows what the policies answer for each group.

### For a parent process

A parent process, such as a desktop shell, runs `sanoma` with `SANOMA_EVENTS=1` and reads its stdout line by line: beside the lines a person reads, each event is one JSON object on a line of its own, `{"sanoma":1,"event":…}`; logs stay on stderr.

- `{"sanoma":1,"event":"ready","url":"http://127.0.0.1:3000","sites":{"www":"http://www.localhost:3000"}}`: the app listens, right after the `at <url>; ctrl-c to stop` line, each time it starts (in [dev mode](#dev-mode), after each restart); `url` is where the app listens, on the port `SANOMA_APP_PORT` names (the free one it took, for 0), and `sites` is `{}` without public sites. `sanoma worker` has no address and prints none.
- `{"sanoma":1,"event":"error","message":"…"}`: the launcher cannot start or stop, with the message it printed on stderr, then exits 2 for a mistake in the call or the config, 1 for a failure. In dev mode a child that fails prints it too, and the launcher waits for the next build to start it again.
- `{"sanoma":1,"event":"checked","ok":false,"problems":["…"],"warnings":[]}`: `sanoma check`'s result, the lines it printed as two lists, before it exits; a check that cannot read the config ends with `error` instead. Read it rather than the printed lines: DBOS logs on stdout too.
- `{"sanoma":1,"event":"database","how":"started","url":"postgresql://postgres:…@127.0.0.1:54012/sanoma","place":"this-computer"}`: the company's own [Postgres](#postgres) answers, once, before the worker starts (in dev mode, from the parent, not each child): `how` is `created` (made first), `started`, or `answered` (another `sanoma` runs it), and `url` holds its password, so a parent never logs it. None when a URL is named.

With the variable, the end of stdin (the parent closing it, or exiting), or an error reading it, stops `sanoma` as SIGTERM does, so the parent keeps stdin open while it runs. `sanoma` never prompts and, without the variable, never reads stdin; it opens no browser. SIGTERM stops everything it started (the app, then the worker; in dev mode its child and the watch builds), then the company's own [Postgres](#postgres) when it started it and no other client is connected, and it exits 0.

## Postgres

The worker and the app run on the config's `databaseUrl`, else `SANOMA_DATABASE_URL` (from the environment or `.env`; an empty value is none). A URL named is used as it is: `sanoma` (through `sanoma serve`), `sanoma check` and `sanoma ledger export` probe it first (`SELECT 1` on its server's `postgres` database, as its user), and stop with a message when nothing answers there or the server refuses the user. For `postgresql://postgres:dbos@localhost:5433/sanoma`, which earlier versions wrote into `.env` and started in Docker, the message says to start that container to keep its records, or to remove the line to move to the company's own.

With none named, a company runs on its own PostgreSQL 18, from the `@sanoma-ai/postgres-<platform>` package installed with `sanoma` (macOS and Linux on arm64 and x64; Windows untested), extracted once into the OS's cache (`~/Library/Caches/sanoma/postgres/<version>-<platform>-<sha>` on macOS, under `$XDG_CACHE_HOME` or `~/.cache` on Linux, `%LOCALAPPDATA%` on Windows), or from `SANOMA_POSTGRES_DIR`, a directory holding its `bin/`. Its cluster is `.sanoma/postgres` in the company's directory of the main checkout (beside git's common directory, so a worktree of the repo uses the same one): `data/`, `server.log`, `password` (random, readable by its owner alone) and a `.gitignore` of its own. It listens on 127.0.0.1 alone, at a port picked when it was made (another when that one is taken), at `postgresql://postgres:<password>@127.0.0.1:<port>/sanoma`, which `sanoma` sets as its own `SANOMA_DATABASE_URL` for the runtime and every child it starts, never in `.env`. `sanoma` creates it on the first run (`initdb`, saying once where the records live), starts it on the next, and uses it as it is while another `sanoma` on the repo runs it; `check` runs its scenarios on `sanoma_check` beside the company's `sanoma`. It runs in a process group of its own, so a terminal's ctrl-c reaches `sanoma` alone, which stops it after the app and the worker when it started it and no other client is connected (another `sanoma`'s worker), and leaves it up otherwise. `sanoma worker` and `sanoma app` never start it: they exit 2 when it does not run. Deleting `.sanoma/postgres` deletes the company's records. PostgreSQL refuses to run as root: there, set `SANOMA_DATABASE_URL`. A synced folder (iCloud Drive, Dropbox) may copy the files of a running database half-written: keep the repo out of one (`sanoma` warns in iCloud Drive).

## `.env.example`

`sanoma env` keeps `.env.example` the manual of the variables: `SANOMA_DATABASE_URL`, `SANOMA_APP_PORT`, `SANOMA_APP_HOST` and the GitHub sign-in variables first, with their defaults, then a block per vendor in the connectors' order, each variable its driver's `env` declares with its `.describe()` text. A required variable is `NAME=`; an optional one is commented out, `# NAME=`, with `Optional.` before its description. The same config gives the same text, which `--check` compares byte for byte. Copy it to `.env` (ignored by git) and fill it in; the vendor variables can also be set on the app's connector pages, where a value from the environment wins over a stored one.

## The lint

`sanoma check` lints `workflows/`, `resources/` and `sites/`, those that exist, with oxlint, run in the repo's root on the repo's own `.oxlintrc.json`, so an editor's oxlint reads the same file and the rules' `workflows/**` globs match against the root. `sanoma check` writes that file when there is none:

```json
{
  "extends": ["./node_modules/sanoma/oxlint.json"]
}
```

`sanoma/oxlint.json` is self-contained (it extends nothing): `@sanoma-ai/workflows`'s rules (the clock, randomness, the network, the environment, the imports a workflow may make, the data-file subset, with its plugin inside `sanoma`), a site's (client code only: no server function, `*.server.*` file or route `server` handlers, no import of the runtime, a connector, Postgres, DBOS, Node's modules or TanStack Start, the app only through `sanoma/site` and `sanoma/ui`, no relative import out of `sites/`, no `virtual:` module (content comes through `content`), no `process` or `require`; types may be imported from anywhere; `sites/__virtual.ts`, the build's listing, aside) and the rules this repo holds its own code to. Add your own rules beside the `extends`; `sanoma check` leaves an existing file alone.

## Sites

A folder under `sites/` with a `routes/` directory is a site: TanStack Router file routes the app serves under `/sites/<name>`, in its shell (see [`@sanoma-ai/app`'s Sites](../app/README.md#sites)). A route file imports `createFileRoute` from `@tanstack/react-router`; the repo installs nothing for it but `sanoma`.

- `sanoma app` (and `sanoma` when `SANOMA_APP_HOST` is another machine's) builds the app with the repo's sites before anything starts (`building the app with 1 site (hello)`), into `.sanoma/app/build/<key>`, and serve that build. The key covers the app's version and every file under `sites/` and `content/`, so a start with nothing changed reuses the build (`app build up to date`). With no site, they serve the build the app ships and write nothing under `.sanoma/` but `api.ts`. A build that fails stops the command before the worker starts.
- `.sanoma/api.ts` is the generated SDK: `sanoma check` (first, before tsc), and `sanoma`, `sanoma serve` and `sanoma app` at start, write it from the config when its text changed, with sites or without; while `sanoma` serves the sites from its dev server, it writes it again (`wrote .sanoma/api.ts`) when `sanoma.config.ts` or any TypeScript file in the repo outside `sites/`, `.sanoma/` and `node_modules/` changes. It types `api` from `sanoma/site`: `api.<workflow>` (the workflow's name in camelCase, `WorkflowFn` of its input), `api.<vendor>.<resource>.<op>` for each operation a person may call directly (a vendor's read, `OpFn` of its input) and `api.data.<collection>` (`CollectionApi` of the collection's record), each with its title and descriptions as JSDoc, so whoever writes a site sees what each call is and `tsc -p sites/tsconfig.json` refuses a call that does not fit. The sites' tsconfig is the only one that reads it: the repo's root `tsconfig.json` (Node, no DOM) must not include it. A workflow whose api name another workflow, a vendor or `data` has is left out of it, and `sanoma check` reports it. Never edit it.
- `sanoma check`, when there is a site, writes the sites' generated files, then, beside tsc, oxlint and the config, builds the app with the sites (reused when nothing changed) and runs `tsc -p sites/tsconfig.json`, which types every `Link` against every page of the app and the sites. Each of these is a problem: a type error at its `file:line:col`; two pages claiming one path (`More than one page claims /sites/hello/: …`); a site importing server code (`sites/hello/routes/index.tsx:4:28: Import denied in client environment: "@sanoma-ai/workflows"`); a folder whose name is not one URL segment (`sites/<name>: a site's folder name is a URL segment (lowercase letters, digits and dashes)`), which the app does not mount; and under `content/`, front matter that is not a YAML mapping, at its line (`content/posts/bad.md:2:1: front matter: Tabs are not allowed as indentation`), or a folder or file whose name is not a URL segment, which the sites do not see.
- On a public site, `sanoma check` reports each start (`api.signup(…)`, `.start(…)`, a `RunForm`) and each direct call (`api.data.<collection>.<op>`, `api.<vendor>.<resource>.<op>`) that no `permit` in `policies/` could let a visitor make, whatever its `when` and `unless` (one for `anonymous`; on a site with a `login`, for `anonymous` or `visitors`), at its `file:line:col` with the line to add: `sites/www/routes/index.tsx:8:9: a visitor's call to workflow "signup" is refused: no permit in policies/ names anonymous for workflow:signup. Add: permit (principal == Sanoma::Principal::"anonymous", action == Sanoma::Action::"workflow:signup", resource);`. Nothing is held to the policies while they have a problem. Whatever they say, a public site's call of a built-in workflow, or read of a workflow's runs but `.result`, is reported too: the app refuses it to every visitor.
- `content/` holds the Markdown a site reads through `content` from `sanoma/site` ([`@sanoma-ai/app`'s Content](../app/README.md#content)): `content/<kind>/<slug>.md`, front matter and a body, found by convention as `sites/` is. `.sanoma/content.ts` types it from the files' front matter, written with the sites' generated files and, on the dev server, again when a file under `content/` changes. A file with `draft: true` shows on the dev server and never in a build.

### Developing a site

`sanoma` serves the app and the sites from Vite's dev server instead of a build (`serving the app with 1 site (hello) from Vite's dev server: edits show as they are saved`), behind the same login, and writes no build:

- An edit to a site's file shows in the open page as it is saved, without a reload, the page's state kept (hot module replacement); the server's render of the page follows on the next request.
- A file saved under `content/` shows on the next render of a page that reads it, drafts included, with no restart, and `.sanoma/content.ts` is written again.
- A new page, or a new site folder, is live once its first route file is written: the route tree is regenerated and open pages reload, with no restart. A Tailwind class in a new file is styled too, by the app's stylesheet and by a site's own ([`@sanoma-ai/app`'s A site's own stylesheet](../app/README.md#a-sites-own-stylesheet)).
- A change to `sites/__virtual.ts` itself needs a restart: the route generator loads that file once. `sanoma` writes it; never edit it.
- `sanoma check` beside it builds the app with the same route options, so it leaves the dev server's route tree alone.
- The dev server listens on this machine only: with `SANOMA_APP_HOST` naming another, `sanoma` builds the sites and serves the build, as `sanoma app` does.
- A public site (`defineSite({ public: true })`) answers at the root of `<name>.localhost` on the app's port, with hot updates too, as its visitors see it ([public sites](../app/README.md#public-sites)); `sanoma`, `sanoma serve` and `sanoma app` print each one's address after they start (`www: http://www.localhost:3000`). Browsers send `*.localhost` to this machine with no setup.

## Dev mode

When the repo's `node_modules/sanoma` or any `node_modules/@sanoma-ai/*` is a link into a sanoma checkout (`pnpm link`), or `SANOMA_DEV_REPO` names one, `sanoma` runs `sanoma serve --dev` in a child process (serving the [sites](#developing-a-site) as `sanoma` does) and, in the directory of every package it reaches in the checkout, its `pnpm run watch` (each package's own watch build: `tsc --watch`, and `vite build --watch` too for the app). Those are the linked packages and each of `sanoma`, `@sanoma-ai/workflows`, `@sanoma-ai/app` and `@sanoma-ai/bridge` that Node resolves into the checkout through them, so a link of `sanoma` alone builds all four. A change under any of their `dist/` restarts the child, after three quarters of a second of quiet (with sites, except the app's own pages in `dist/client` and `dist/server`: the dev server serves the app's source from the checkout and hot-updates it), one restart at a time; a child that exits on its own is reported and started again on the next change. The child and each watch run in a process group of their own, so a terminal's ctrl-c reaches `sanoma` alone, which then ends each group (SIGTERM, SIGKILL after 5 seconds) and exits. It does the same, saying `dev mode: the repo no longer links <checkout>; stopping`, once none of the repo's links into the checkout is left (`sanoma-dev unlink`, an install; `node_modules` is looked at every second, and a link gone on two looks in a row is gone), so the checkout's server writes nothing more into the repo's `.sanoma/app` beside the installed sanoma.

Linking a core package while another still comes from a tarball (`@sanoma-ai/workflows` linked and `sanoma` not, or a declared `@sanoma-ai/app` left installed beside a linked `sanoma`) works, with two copies of a package in one process (the linked one, and the one an installed package depends on), and `sanoma` says which still come from their tarballs before it starts the child: `dev mode: sanoma, @sanoma-ai/app, @sanoma-ai/bridge still come from their tarballs, so edits to them in the checkout will not show`. [`@sanoma-ai/dev`](../dev/README.md)'s `sanoma-dev link` links `sanoma` and every declared `@sanoma-ai/*` package the checkout has.

## The wakeup service

An instance whose worker stops when nothing can run (a host that scales to zero) still has what is due at a time: a schedule's next run, a sleep until a date. The wakeup service keeps that time for it while it is stopped, and calls the instance's `GET {url}/wake` then; any answer but a 2xx is tried again (after 1 s, 2 s, 4 s and so on, at most 5 minutes apart) until one is, so a wake is late at worst, never lost. `sanoma wakeup` runs it on its own; a config with `wakeup: true` runs it inside `sanoma serve` instead, its routes in the app (as sanoma-ops does for its customers). It keeps its two tables, `sanoma_wakeup_accounts` and `sanoma_wakeup_instances`, in that database, and only the sha256 of each token.

Whoever runs it mints an account with `sanoma wakeup account <label>`, which prints `{"id","token"}` on stdout (or `mintAccount(label)` on [`startWakeupService`](../workflows/README.md#the-wakeup-service)); its token (`swa_…`) registers instances: `POST /wakeup/instances { url, token }` takes the instance's own token (`swi_` and 43 or more base64url characters), which the company minted (`/setup` does, as `SANOMA_WAKEUP_TOKEN`), and answers `201 { id }`; posted again by the same account, the token names the same instance, now at the URL given, and answers `200 { id }` (its registered wake kept only when the URL is unchanged), and another account's is a 409; `GET` and `DELETE /wakeup/instances/{id}` with the account's token show and remove one. Before it stops, the instance sends `PUT /wakeup/wake { at }` with its own token, which names it: a 204, which replaces what it registered. A wake is resume if stopped, so one that a retry or a replaced registration sends early or twice starts at most a worker with nothing to do. Every response is JSON and `no-store`; a missing or unknown token is a 401, another account's instance a 403, a bad body a 400.

A company uses one through the runtime's own wakeup, `sanoma.wakeup({ host })` (`import { sanoma } from "sanoma/resources"`), which every config with a host type has, no connector installed: `/setup` asks for the service's URL and an account's token (`SANOMA_WAKEUP_URL`, `SANOMA_WAKEUP_ACCOUNT_TOKEN`), and going live declares it when the host's own vendor has no wakeup of its own, the host given `SANOMA_WAKEUP_URL` and `SANOMA_WAKEUP_TOKEN`.

## Hosting it yourself

`sanoma worker` and `sanoma app` are the deployment's two processes. A host that composes its own process keeps `startWorker` from `@sanoma-ai/workflows` and `startApp` from `@sanoma-ai/app`, which the bin runs.

[`runtime/`](runtime/Dockerfile) is the image a container host runs: Node 26, git, pnpm and `provider-bridge`, and no company code. At start it clones `SANOMA_SOURCE` at `SANOMA_REVISION` (with `SANOMA_SOURCE_TOKEN` as an HTTP header when set), runs `pnpm install --frozen-lockfile` and `sanoma serve` on `0.0.0.0` and `PORT` (default 3000); the host passes `SANOMA_DATABASE_URL`, `SANOMA_SECRETS_KEY` and, as the app is not on loopback, the `SANOMA_GITHUB_*` sign-in variables too. Its health check is the app's `/healthz`. `sanoma serve` (not `sanoma app`, which runs no worker) also answers a [wakeup](../workflows/README.md#hosts)'s `GET /wake` before any login: 204, never cached, whatever the query. Its worker runs under a supervisor (`superviseWorker`): with a wakeup declared and the app beyond loopback (on this machine alone, the wakeup would wake the deployed instance) it stops itself when nothing can run soon, and a fresh one starts on a wake (resume if stopped), or on a write from the app (a run's start, apply, an approval's decision), never on a page read. `sanoma worker` never stops its worker: nothing in its process would start it again. A repo with [sites](#sites) is built at start, as `sanoma serve` does anywhere, into `.sanoma/app/` in the clone: the app listens once the build is done (the health check's start period allows 5 minutes for the clone, the install and the build); the image itself holds no build. `provider-bridge` is built from source at a pinned commit; `--build-arg BRIDGE_FROM=release --build-arg BRIDGE_VERSION=<x.y.z>` downloads a release instead. CI builds the image without pushing it; it runs no company in it, so it builds no site either. A release pushes it to Docker Hub as `sanomaai/runtime:<sanoma version>` ([Release](../../README.md#release) has the hand command).
