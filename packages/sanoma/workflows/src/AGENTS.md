# packages/sanoma/workflows/src

The source of `sanoma/workflows`: how connectors, workflows and policies are declared, how a worker runs them durably on DBOS, and the tools that read them (lint, outline, describe). Its entry points, from `exports` in `package.json`: `.` (`index.ts`), `./data`, `./describe`, `./description`, `./fake`, `./plugin`, `./resources` (`secret.ts`), `./scenario`, `./scenarios`, `./shared`, `./wakeup-service` and `./db` (the tables, `databaseOn` and `pgCode`, and the migrator with `underPreparationLock` for a connector's own generated folder, for the packages that share them, never a workflow).

Keep `runs with exactly` free of generated input: parse the supplied object through the workflow schema. Existing `runs with` and `runs` keep their documented input generation. See [scenario inputs](../README.md#scenarios-and-sandbox-runs).

`kms-secrets.ts` is the server-only `/kms-secrets` backend: GCP envelope encryption, fixed company scope, explicit KMS/database authority and versioned CAS. `managedKmsStore` composes broker auth with a lazy SDK client per bound adapter, closed by the runtime; `kmsPostgresStore` keeps supplied clients caller-owned. Preserve authenticated company/namespace/path/version/format and keep no plaintext/data-key cache. Validation probes persisted CRUD with a unique encrypted synthetic row; preserve exact-version cleanup and fail startup on unusable storage. [KMS-SECRETS.md](../KMS-SECRETS.md) owns deployment, readiness limits, rotation and recovery constraints.

`identity-provisioning.ts` owns the separate enrollment writer: pure config resolution, lazy runtime-owned pools with verified remote TLS and restricted writer checks, or caller-owned adapters; immutable mappings, serialized enrollment/retirement/revocation, generations without expiry until retired and sanitized failures, with run-local sandbox authority. Clients and workers close only the pools this configuration creates.

`storage-provisioning.ts` implements `sanoma.secretStore.prepare`: private KMS schema, restricted company/environment database login, immutable binding and stable retry credential stored by reference. Role creation passes the password as a bound parameter to a session-private `SECURITY INVOKER` function for server-side SCRAM hashing; never interpolate it into submitted SQL or claim only a verifier crosses the database boundary. It returns metadata only; sandbox preparation has no database effects. [Database preparation](../KMS-SECRETS.md#preparing-the-company-database) owns its privilege and readiness boundaries.
