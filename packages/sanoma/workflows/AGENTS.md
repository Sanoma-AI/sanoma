# Working on sanoma/workflows

This package owns workflow declarations, durable execution, policy and approval enforcement, and the ledger.

## Read when needed

- [README](README.md): public API, [resources](README.md#resources), and examples; [versions](README.md#versions) and [replay safety](README.md#keeping-workflows-replay-safe) for runtime changes.
- [Changes](README.md#changes): a draft sent for review, Publish, the deploy after it, and what the Permissions line means.
- [Usage](README.md#usage): the config (`connectors`, `workflows`) and its conventions (the root's `scenarios/`, `resources/` and `policies/`); each connector carries its driver and fake (`withSetup`). [People](README.md#people) and [Policies](README.md#policies): the people data file, admission, the Cedar policies, holds and denies, preview.
- [Scenarios and sandbox runs](README.md#scenarios-and-sandbox-runs): Cucumber's two runs (compile, check), the generic steps and those a connector ships, the connectors' fakes and the root's `scenarios/`, and what a sandbox run does differently.
- [Source map](src/AGENTS.md): locate execution, definitions, analysis, or browser-safe helpers.
- [Test map](test/AGENTS.md): select coverage and the shared DBOS harness.

## Maintenance boundaries

- Keep policy checks, approvals, driver calls, and ledger records coordinated in `src/call.ts`. Changes to the durable call sequence require updating `STEP_LAYOUT` in `src/version.ts` so old runs do not replay against a new layout. A held call ends as its approval does: a rejection or a withdrawal (`approval_withdrawn`, `src/approvals.ts`) is its failed `op.called`, naming the approval. A withdrawal makes the same DBOS calls as a decision (the list, the ledger, the decision event), so it needs no new layout; `withdrawApprovals` runs in the run's body, never a step, and depends only on the run's history.
- Every live wait of a run (`DBOS.sleep`, `DBOS.recv`) goes through the worker's `run.state.deadlines.waiting` (`src/deadlines.ts`), with its deadline when it has one: a PENDING run in no wrapped wait counts as executing, so `idle()` would keep the worker up for it forever, and a deadline left out would never be registered with the wakeup. The registry is the worker's (on `WorkerState`), never a module's.
- Keep `src/shared.ts` browser-safe: no DBOS, Node, or zod imports. UI-facing descriptions belong in the describe entry point, not the execution path. Its `apiNameOf` and SDK types (`WorkflowFn`, `OpFn`, `CollectionApi`) are what a site's `api` names and is typed with; the app re-exports the types from `sanoma/site`, since a company cannot resolve this package, and `describeConfig` reports a workflow whose api name is taken (`apiNameProblem` in `src/sdk.ts`, the one wording, which `generateApi` reads to leave it out). `src/sdk.ts` writes `.sanoma/api.ts` from a `ConfigDescription` alone, never the config: types and JSDoc, pure and deterministic, so check, serve and dev write the same text and an unchanged file is never rewritten.
- `sanoma/workflows/page` (`src/page-run.ts`) runs workflows in a browser page, so everything it reaches stays browser-safe: no DBOS, `pg`, Drizzle or Node module imported, Node's read only through `process.getBuiltinModule` where it is there (`src/company-file.ts`), and only types from the server's modules. A run's `ctx` is `ctxOf` (`src/ctx.ts`) on both paths, a world is `applyGivens` (`src/givens.ts`) as a sandbox run's seeds are: change a member or a seed there, never in one runner. `app/test/page-bundle.test.ts` builds it for a browser and fails on a forbidden module.
- `src/sites.ts` (`readSites`, `describeConfig`'s `sites`) reads what a site calls the way the outline reads a workflow: its pages are browser JSX, parsed with oxc, never run (the site's outline), only names written out; its `site.ts` is loaded (`src/load.ts`), as `app.ts` and the data files are; it resolves an `api` path as the app's `callApi` does, so a new name form there is a new case in `apiCall`.
- The outline (`src/outline.ts`) is a contract, not a reading, and the one definition of what a workflow may write: `outlineBody` returns the nodes and the `problems` (what the graph cannot draw), `startWorker` and `lintWorkflow` both refuse on the problems (`describeConfig` lists them on each workflow's entry, with the import rules, reading each file once through `readSource`), and the worker places every `ctx` call in the nodes at run time (`src/call.ts` `placeCall`, the backstop for what no static reading sees, such as `arguments`). A new rule goes in `outlineBody`, with a test in `outline.test.ts` or `lint.test.ts` and, when the worker's refusal is what matters, `callsite.test.ts`.
- Keep `sanoma/workflows/scenario`, `/scenarios` and `/wakeup-service` server-only: the shipped `oxlint.json` refuses them in workflow files, as it does `/fake`. The wakeup service's tables are its own, made by `startWakeupService` in the service's database: never add them to `db/company.ts`, whose migrations every company database gets: they are `db/wakeup.ts`, generated into `drizzle/wakeup/`, applied by the service under the preparation's lock (`underPreparationLock`). `lint.ts` is internal (no `/lint` entry): `describeConfig` is how a problem reaches a UI or `sanoma check`, and `src/lint.ts` is what the tests and the oxlint plugin import. `src/sandbox.ts` is internal; the worker imports it dynamically, only for a sandbox run, so a live worker never loads Cucumber or faker. The describe entry loads neither. Keep a sandbox run's seeding in its one checkpointed `sandbox:seed` step. Its checks are the worker's too (`recordChecks`, into the runtime's `sanoma_run_checks`, which `SanomaClient.runChecks` reads): run when it starts to wait on an approval and when it ends, after its outcome's record and before DBOS's, never in a step or a ledger record, so its replay neither reads nor differs by them. How far each app taken from a source is behind it is told the same way (`recordAppsBehind` in `src/worker.ts`, at the worker's start and after `WorkerState.followMain` moves the checkout, into `sanoma_app_behind`, read by `SanomaClient.appBehind`): in the background, one check at a time, no step.
- Cucumber runs the Gherkin files, and only `src/cucumber.ts` imports it: the library is built from data, by hand (`supportCodeLibraryBuilder.reset`, register, `finalize`), never with `loadSupport`, which finds no step definitions the second time in one process; runs are serial, in-process, given literal paths (Cucumber globs what it is given), and read back with Cucumber's own `Query` (`@cucumber/query`). `src/scenario.ts` says what the steps mean: compiling records only (pure; the app compiles), checking runs `Then` steps only, each judged on its own, and an operation's own test (`testFeature`) is the one run that calls a driver. `src/steps.ts` (`defineSteps`, on the main entry) stays free of Cucumber, Gherkin and faker, since connectors import it at their root; a connector never imports Cucumber. Keep `@cucumber/cucumber` pinned exactly, and its `@cucumber/*` dependencies one copy each across the workspace (`pnpm why`).
- Collections (`src/collection.ts`) are operations of the vendor `data` (`DATA_VENDOR`), which `resolveConfig` registers as it does `sanoma.source.resolve`: their connector, a driver on the `data` table (`src/collection-driver.ts`, over `src/db/company.ts`) through `dataStore` (a `lazyDb` the worker closes at stop) and a fake, under that vendor, and no connector may take it. A collection is read by its brand (`COLLECTION`, `Symbol.for`) and its schemas by property, never by `instanceof`. A save's `updated_by` is `CallContext.by`, which `callOp` sets inside the driver step it already has: no new DBOS step. Keep insert-only (`ifAbsent`) and full-record conditional (`ifRecord`) saves and deletes atomic in the driver, with same-actor receipt recovery and conflict refusal; neither is a lease across vendor calls. A batch (`saveMany`, `isBatch`) is the one operation that stands for others: the policy decides and the ledger records its entries as the collection's `save` or `delete` (`callsOf` in `src/ctx.ts`, the one place a batch is taken apart, which `callOp`, `SanomaClient.call`, `recordedCall` and a page's run share), the Cedar schema has no action for it, and its driver and fake make it all or none. Keep the fake's JSON equality and the browser-safe `CollectionApi` input aligned; public semantics are in [Collections](README.md#collections). A column change brings the records along through `sanoma.records.reshape` (`recordsOps` in `src/collection.ts`, `recordsDriver` on the connection store's pool, registered in every config like the change's operations, with no fake so a sandbox run refuses it): what each record becomes is `reshaped` in `src/shared.ts`, which the driver, the app's plan (its won't-convert counts) and the tests share, so the app's preview and the database agree by construction.
- A change's operations (`sanoma.change.*`, `changeOps` in `src/change.ts`) are registered by `resolveConfig` in every config, unconditionally, with their driver: the template's policy names `sanoma.change.merge`, and strict validation fails on an action the schema lacks, so a built-in operation a policy may name is never conditional on the config. Only the built-in `change` workflow calls them (`reservedFor`, the one rule `checkUses` and `callOp` share); after its merge it also calls `sanoma.records.reshape` for a plan that brings records along, which its Publish covers. `reservedFor` keeps that one to `change` and `patch`: it rewrites a collection's records outside their own operations and the policy on them. The merge acts on a `Sanoma::Change` (`schema.ts`), its attributes the change's facts (`ChangeFacts`), which `callOf` passes as the call's `entity` and `cedar.ts` builds into the request (with unknown attributes in a preview, so a rule on any change holds rather than depends). The runtime's own rule, `runtimeHold` (a change to the rules waits for `admin`), is asked in `decide()` before the company's policy, over the running instance's people (`readPeople(run.state.root)`): never a Cedar policy, since it must hold under `allowAll` and no company may delete it.
- The runtime's own operations a workflow uses (`sanoma.secret.*`, `sanoma.invite.mint`, `sanoma.token.*`, `sanoma.identity.*`, `src/runtime-ops.ts`) are registered by `resolveConfig` in every config with `runtimeDriver` (tokens on `connectionStore`), as the change's are, so a policy may name them; a sandbox run gets a fresh `sandboxRuntimeDriver` from `sandboxDrivers`. None answers a secret's value: a new one is written with `CallContext.secrets.ensure` and only its name, public half or id comes back. `ctx.startedBy` is `run.actor` as `SanomaClient.start` admitted it: a visitor's `email` as the app passes it on (kept by `admit` for a visitor alone), a token's `subject` read from its row by `start` (`withSubject`), never from the caller.
- Token provisioning saves the bearer before registering its hash (`runtime-ops.ts`, `tokens.ts`). Explicit IDs and persisted non-secret references are mutually exclusive; reference derivation stays deterministic and domain-separated. Preserve atomic registration checks for ID, bearer, subject and group membership, and refuse revoked registrations; conflict handling must not change or revoke an existing token. See [runtime operations](README.md#the-runtimes-own-operations) for recorded-ID recovery and its lifecycle limits.
- Direct calls (`SanomaClient.call`) run without DBOS: `isDirect` (`src/direct.ts`) is the one rule for what may be called so, which `describeConfig` (`OpEntry.direct`), the built-in `call` workflow (`src/call-workflow.ts`) and the app's callers read and never derive again. The policy decides through `decideCall` (`src/call.ts`), the function a run's policy step uses. A direct write and its ledger record share one Postgres transaction (`insertRecord`, and the collections' driver on that connection) when the ledger is the default; a policy hold becomes a run of `call` as the person, whose `CallContext.by` is the person's id. Adding a built-in workflow changes every app's version that registers it.
- A git host is reached only through a connector's remote half (`RemoteHalf`, `src/source.ts`), made once per resolution into `ResolvedConfig.remotes` and found by `remoteFor` from `origin`'s URL: neither the runtime nor the app imports a host's connector. A verified webhook starts the built-in `follow` (`src/follow-workflow.ts`, held to the lint; its steps `src/follow-steps.ts`), through `SanomaClient.follow` alone, as the runtime's agent `host-check`, one run per event (`follow:<sha256>`; `start` refuses another id or actor, as it holds `change` to `openChange`: `OWN_STARTS` in `src/client.ts`); the worker runs it over its `source`, and it only tells: a push to `main` applies the hosts once the checkout has followed it, a push to a draft's branch is fetched into the draft before its change is told `commits`, and a closed pull request is told `merged` or `closed`, which the change run checks on the host before it acts on it. Its writes to the checkout go one at a time with the app's steps' (`WorkerState.serially`; `main` through `followMain`, as a change's deploy follows it), and its tells and reads go through the worker's own client (`WorkerState.client`).
- A built-in run (any of `BUILT_IN_WORKFLOWS`: apply, change, drift, call, login-code, import, the app's actions, follow and chat) carries its workflow's code (`builtInCodeOf` in `src/version.ts`, `ResolvedConfig.builtInCodes`: that workflow's `computeVersion` terms with the runtime's, never the company's workflows) as its `builtInCode`, a DBOS attribute `SanomaClient.start` and `WorkerState.startRun` set, since attributes are fixed at enqueue. `carryBuiltInRuns` (`src/worker.ts`), on a worker that is the latest version, stamps each unfinished run of another version with its own code with its own version in one statement, only for the workflows that wait across a deploy (`CARRIED` in `stampVersion`, `src/db.ts`: `apply`, `change` and `migrate-store`, and a built-in's child run, such as a change's drift, which the change waits for; the runtime's one write to DBOS's tables, pinned to its schema), then queues the PENDING ones again on their own queue, the apply queue or the app's (`resumeWorkflows`); an apply queued and never started is carried whatever its code, and one started on other code is cancelled (it would hold the apply queue's one place for good); a stop between the two leaves a PENDING run of its version, which DBOS's recovery takes. It assumes one live worker per database. Not `rewindWorkflow`: it takes only a cancelled run and deletes the messages the run has not read. Never carry a company workflow's run: its replay is held to the company's code, which the version is.
- One live apply at a time per app and database: every apply but a sandbox one goes on `ResolvedConfig.applyQueueName` (`sanoma:<appName>:apply`, registered with `globalConcurrency: 1` right after `DBOS.launch()`), chosen by `queueFor` (`src/config.ts`), the one rule `SanomaClient.start` and `WorkerState.startRun` (a change's deploy, a push's, going live) share. Never start an apply outside it. DBOS counts the running one over every version of the app; across a deploy the carry takes the other versions' applies over or cancels them, so the limit assumes one live worker per database. `child()` in `src/change-steps.ts` reports a cancelled child as the deploy's error. `idle` (`src/deadlines.ts`) does not count an apply queued behind a PENDING one. `SanomaClient.applyAhead` names the apply a queued one waits for.
- The `Sandbox` contract (`src/sandbox-contract.ts`) stays vendor- and library-neutral: web streams, no AI SDK, no vendor's facts but the declaration's fields (`SandboxContext.declared`). A config resolves to one declared sandbox at most (`sandboxes()`, the second a problem of the data files as a second wakeup is) and its connector's backend maker (`sandboxBackends`); choosing among them and the local backend is the app's (`personBox`).
- The sandbox runner (`src/sandbox-runner.ts`) runs inside a remote box on the box's Node (22 or later), as one file esbuild bundles: keep what it imports to Node's built-ins, `ws` (a devDependency, bundled in) and `local-sandbox.ts`/`runner-protocol.ts`. Bump `RUNNER_PROTOCOL` with any change to the protocol: a backend replaces a runner whose health (`RUNNER_HEALTH`, `/runner/health`) answers another (a box that slept keeps its runner across releases).
- `RUNTIME_VERSION` is `sanoma`'s `version`, read from `../../package.json` by `src/version.ts` and `dist/version.js` alike (and rewritten for the Worker's bundle by `app/src/bundle-build.ts`): keep that file directly under `src/`. Public export changes also affect consumers and the root source aliases. `allowImportNames` of the `sanoma/workflows` entry in `oxlint.json` is the one list of names a workflow may import, from each package in `AUTHOR_PACKAGES` (`src/lint.ts`); the `sanoma` package derives its own entry from it at build and re-exports the list from `packages/sanoma/src/index.ts`, so a name added there is added to that index.
- Company files are read by loading them (`src/load.ts`), and written by parsing (`src/writer.ts`), which changes only a literal. `resources/data.ts` (`COLLECTIONS_FILE`, `src/paths.ts`) is the data file the launcher and workflows import: collections only, never matched to a connector or the lockfile; no other data file declares one. The workflow lint's one allowance outside `workflows/` is that file, by real path (`src/lint.ts`). The workflow rules are configured only in the shipped `oxlint.json`, loaded from `dist/plugin.js`; the `./plugin` entry exports them for `sanoma`'s `oxlint.json`, which loads it from its own `dist/`.
- `src/change-workflow.ts` is held to the workflow lint as drift and apply are, and registered in every config (so every app's version changed with it); its steps are `src/change-steps.ts`, reading the run from `currentRun`. Every wait of a change run goes through `deadlines.waiting`: its events on `CHANGE_TOPIC` as a `message`, its child runs (apply on the hosts, drift after it, started with `WorkerState.startRun` at `<run>:deploy` and `<run>:verify`, after the checkout follows `main`) as a `run`. A change event is always queued on the topic, and `SanomaClient.changeEvent` withdraws a pending merge approval so a run waiting on it reads the event; a `merged` or `closed` event is checked on the host (`settled`, as `next`/`queued` read it) before the run believes it, and the topic is read again after Publish, before the merge, and the merge's head guards (the host's and the draft's) are what keep a late event safe. Only `openChange` starts a change (`start` refuses another run id). Approvals are tied to no head: each round withdraws those approved for the merge (`withdrawApprovals`) before the policy is asked. The driver reads the worker's `source` from the run (`sourceOfRun`), and keeps each `SourceHost` it opens (per remote half, secrets and URL), so a token is minted once while it holds.
- A resource type's change operations (`isChangeOp`) are any workflow's to use; only apply changes a declared object. `callOp` refuses another workflow's call aimed at one (`refuseDeclared`): an `update` or `delete` of an id the lockfile binds, a `create` or `update` whose identity (the type's `find`) a data file declares or the lockfile binds, and any while the files have problems, read through `WorkerState.declaredObjects` (`ResolvedConfig.declaredObjects`, the data files and lockfile at each call) inside the call's policy step (`policy:<op>`, asked again after each approval), so a replay keeps the first answer and the step layout is unchanged.
- `src/drift.ts` and `src/apply.ts` are held to the workflow lint (a test lints them), so they import no DBOS and make no dynamic import: their data-file step is made in `src/config.ts` and passed in, and apply's other steps are in `src/apply-steps.ts`, which reads its run from `currentRun`. Every `ctx` call stays in a built-in's own `run` (the outline reads only that), so what drift and apply share of observing is pure (`observeBy`, `observed`, `compare`). The worker takes every definition, the built-in's too, from the running worker's config by name.
- The app's actions on the repository are built-ins too (`src/app-workflows.ts`, linted as any workflow: `adopt`, `patch`, `go-live`, `go-live-host`, `connect-existing`, `save-draft`), each a one-line `run` over an `AppRunner`; `src/app-steps.ts` is that runner (DBOS, reading `currentRun`): the step the worker was given (`WorkerOptions.app`, `AppSteps`, held on `WorkerState.appSteps`), given the worker's lazily connected client and its lock (`AppStepContext.serially`), which a step holds around its reads, writes and commits of the checkout only, and, for `stepThenApply`, an apply started as the run's child. `patch` with a column change's plan and no remote calls `sanoma.records.reshape` through `ctx`, then `AppRunner.reload` (`app:reload`, the worker's `reload`). A new action of the app's on the checkout is a method on `AppSteps`, its input and output types in `app-workflows.ts`, a name in `src/shared.ts`'s `BUILT_IN_WORKFLOWS`, and the app's step in `packages/sanoma/app/src/steps/`; never a server function that writes the checkout.
- A chat turn is the built-in `chat` (`src/chat-workflow.ts`, linted; its steps `src/chat-steps.ts`), started only by `SanomaClient.startTurn` as the chat's person (`client.start` refuses another id, `after`, or person), on ids alone (the chat, the message the app wrote to its transcript first, the turn before), since a run's input and output are in the ledger staff read: the turn is `AppSteps.chat` in one step, given what an app step is (`stepContext`), run beside the run's `recv` loop on `CHAT_TOPIC` (a stop aborts the step's signal, as the worker's `shutdown` does, a sealed code reaches its `onCode`, the step's own `ended` closes the loop, as does a `recv` that times out once the step has settled; DBOS numbers both as they are called, so a replay meets them in order). The recv loop holds no deadline: the turn's step is executing all the while, so the run is busy and the worker stays. The reply's chunks and transcript are the step's writes, in `chats.ts`; a turn a stop of the worker cut is resumed by the next one as begun (`Chats.begin` false), so it runs nothing again. A worker without `AppSteps` fails the turn at once (`NO_CHAT_STEPS`).
- Data files are found from the config's `root` (`defineConfig`'s call site, or set), never the working directory. The JSONL ledger's directory is still relative to the working directory: an inconsistency to fix, not a pattern to copy.
- The default ledger is `postgresLedger` on the config's database, with its table beside the credentials'; both go through `src/db.ts`. `resolveConfig` stays pure, and each entry point calls it once (the worker and the client at start, the app at `startApp`, the bin at load): `startWorker` and `SanomaClient` each make their own store (`ownedLedger` in `src/ledger.ts`) and are the only callers of `close`, which they call only on a store they made; a config's own `ledger` is never closed by the runtime.
- `resolveConfig` derives everything a config no longer says: each vendor's driver from its connector's setup, made once per resolution (`driversByVendor`, which `drivers` indexes and the credentials are read from), the makers of the fakes (`fakes`; `src/sandbox.ts` calls each once per sandbox run, and indexes that run's fakes itself), the app name from `<root>/package.json` alone (no walk up), `<root>/scenarios/` when it is a directory, and the policy from `<root>/policies/**/*.cedar` (`policyAt` in `src/cedar.ts`: `allowAll` without any, one refusing everything while `policyProblems` has lines). The policy is never a config field: Cedar is the one policy language, and a test that needs one writes `.cedar` files in its root (`rootWith` in `test/harness.ts`). `drivers`, `fakes`, `appName`, `scenarios` and `policy` are `@deprecated` `never` fields on `SanomaConfig`; `resolveConfig` keeps a guard for `drivers`, `fakes` and `policy` only (an untyped config would run live, or allowing everything), to delete once sanoma-ops has migrated. The setup is on the connector's `[VENDOR]` record, overlaid by `withSetup`; `setupOf` is internal (not exported), and `withSetup` stays off the workflow allow-list in `oxlint.json` and off `sanoma`'s author surface.
- The runtime's tables are declared in `src/db/` and queried through Drizzle's builder on a `Db` (`databaseOn`, `src/db.ts`): camelCase properties, snake_case columns (`casing`), a store taking a `Db` so a caller's transaction serves as a database. A table changes in its module, then `pnpm --filter sanoma generate` writes the migration into `drizzle/<folder>/` (committed, never edited by hand; a data migration is `drizzle-kit generate --custom --config drizzle/<folder>.config.ts`), which `prepareDatabase` applies under its lock; CI regenerates and compares, and refuses a migration older than `main`'s newest (the repository's `scripts/check-journal.ts`, over every tracked journal: this package's and a connector's), which the migrator would skip. The Worker never migrates (`checkPreparedOnly`). What the builder cannot say is the `sql` tag with the schema's columns (`${wakeupInstances.attempts}`), and an admin statement is `db.execute(sql…)`; only the modules that open connections import `pg`. A `jsonb` column takes the value itself, never `JSON.stringify`; a timestamp read through raw `sql` is a string, through the builder a `Date`; a parameter used twice is cast where it is used; a list is `inArray` or `sql.param`; a transaction left without an error is `tx.rollback()`, caught with `is(e, TransactionRollbackError)`. A failed statement throws the `pg` error itself (`pgCode`), never Drizzle's, whose message repeats the parameters.
- Every DBOS handle on the config's database takes `DBOS_DATABASE_OPTIONS` (`src/db.ts`): `DBOS.setConfig` in the worker, and each `DBOSClient` through `dbosClient`, never `DBOSClient.create` directly. `prepareDatabase` sets the idle-transaction timeout DBOS is told not to set per connection.
- Two copies of this package may load in one process (a connector's peer linked into a checkout, the app's from its tarball). What one copy makes and another reads is keyed by a registered symbol (`Symbol.for`, as `VENDOR`, `RESOURCE` and `DECLARED`) or read by property (`errorCode`, `retryable`), never by `instanceof` or an unregistered `Symbol`; a module-level registry (the worker's state, `prepared`, the logger's) is only read by the copy that fills it. `config.test.ts` reads connectors through a second instance of the module. A change to the `[VENDOR]` record's shape bumps `CONNECTOR_FORMAT` in `src/op.ts`.
- Secret resolution goes through `SecretAccess` (`src/secret-store.ts`), with the selected adapter and explicit bindings. Never reintroduce environment-first fallback, plaintext credential rows or global `process.env` synchronization. `src/credentials.ts` owns only the encrypted Postgres adapter; `src/deployment-key.ts` reads independent signing/encryption bootstrap outside the store. Follow [Credentials](README.md#credentials) for the public contract and the remaining driver migration boundary.
- Host delivery of additional environment bindings is explicit (`host: true`): `config.ts` passes names to `host-derive.ts`, which keeps secret markers in plans and refuses conflicting derived bindings. Preserve the exclusion of hosts that bind their own bootstrap and workflow-created company hosts; see [Secret store configuration](README.md#secret-store-configuration).
- `sanoma.secretStore.prepare` keeps privileged database work in `src/storage-provisioning.ts`, outside workflow history. Preserve immutable company/environment ownership and the saved retry credential; never give the runtime database/role administration or KMS-schema ownership. Its receipt proves initialization, not deployed KMS readiness. See [database preparation](KMS-SECRETS.md#preparing-the-company-database).
- Connection selection is account authority: keep its revision pinned through policy, approvals, driver execution and ledger records. Resource plans pin a selection when reading their declarations and carry it in the lockfile. `src/connection.ts` persists metadata only; authentication values stay in the trusted store boundary. A connector's existing `env` driver guard is not connection-scoped authentication and must not be used as a compatibility path for named accounts.
- Named authentication is resolved by `indexDrivers` inside the authorized invocation, shared by direct and durable calls. Keep verifier and SDK errors sanitized, and limit auxiliary secrets to input markers and declared `createsSecrets` destinations. Sandbox selection is synthetic and run-local; it must never read production connection records or credential stores.

- Keep `previewConnection` / `connectConnection` credential intake outside durable operations. Only metadata enters the prepare/configure/activate gates. Preserve pending/uncertain refusal, expected versions and stored-version receipts when changing retries; card reads are metadata-only and health is last-tested, never a live promise. See [Connecting and managing accounts](README.md#connecting-and-managing-accounts).

The server-only `/identity-service` entry performs no schema installation; administrator setup owns its enrollment and audit schemas, which must never enter `db/company.ts`: they are `db/identity.ts`, declared for the query builder and never generated. Keep runtime and provisioning issuance separate: `/token` supplies ten-minute company OAuth tokens; `/identity` supplies Google OIDC tokens for a fixed provisioning WIF subject/audience. They require separate enrollment readers, bootstraps and attached issuer accounts. `identity-broker.ts` shares request/audit checks only. Preserve evidence limits in [Cloud identity](CLOUD-IDENTITY.md).

Identity enrollment uses the config's explicit `identityProvisioning`. Database configuration creates a separate lazy pool per client/worker, closed on shutdown or startup failure; explicit adapters remain caller-owned. A `secret()` `databaseUrl` is read through the config's secret access inside the enrollment operation on each use (a changed value replaces the pool), never at resolution; `ResolvedConfig.identityProvisioning.secret` names it for the app's Hosting page. Keep resolution/descriptions free of I/O and credentials, enforce restricted writer permissions and verified remote TLS, and never fall back to a company or broker database pool or initialize schemas. See [Cloud identity](CLOUD-IDENTITY.md#provisioning-operations).
