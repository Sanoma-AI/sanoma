# Secret storage and named-account support

What `main` supports for secret stores, credential methods and named accounts, and where each stops. It describes `sanoma/workflows` **0.11.25**, `sanoma/app` **0.10.20**, `sanoma` **0.11.21**, `@sanoma-ai/connector-gcp` **0.2.0**, `@sanoma-ai/connector-supabase` **0.5.1** and `@sanoma-ai/connector-cloudflare` **0.6.6**. Until those are published, npm's latest releases lack OAuth consent and renewal, moving between stores and the driver-error redaction, so check the installed versions before relying on them. The bridge client pins [provider-bridge v0.2.0](https://github.com/Sanoma-AI/provider-bridge/releases/tag/v0.2.0); the Go binary release alone does not update installed npm packages.

Configuration and lifecycle contracts are in [Credentials](README.md#credentials). See also the [Supabase Vault setup and recovery instructions](../../../connectors/supabase/README.md#supabase-vault-as-the-secret-store), the [connection UI](../app/README.md#connection-management), the [KMS store](KMS-SECRETS.md), the [Cloud identity services](CLOUD-IDENTITY.md) and the [bridge session contract](../bridge/README.md).

## Stores

A store is selected in code (`secrets.store`) and the app names it by its ID; other stores a move may use are named in `secrets.stores`. Every supported store offers atomic conditional writes, destroys on delete and detects changes by reading; each is writable, except a Supabase Vault adapter configured read-only.

| Store                            | Supported                                                                                                                                                                                                                                                                                                                                                     | Needs and limits                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Built-in, `postgres`             | The default when `secrets.store` is omitted. AES-256-GCM rows in the company database, authenticated to namespace and path, with opaque versions; plaintext rows and moved ciphertext are refused. Values up to 64 KiB.                                                                                                                                       | `SANOMA_SECRETS_KEY` (or `_FILE`) outside the database; `SANOMA_SIGNING_KEY` is separate. A backup needs the rows and the key. A sealed value is bound to key, namespace and name, not to its database ([trust limits](#trust-limits), [#705](https://github.com/Sanoma-AI/sanoma/issues/705)).                                                                                   |
| Supabase Vault, `supabase-vault` | Server-only `@sanoma-ai/connector-supabase/vault`: a private SQL gateway, a deployment-scoped database login, Sanoma-managed values and read-only mappings to existing Vault secrets. Values up to 64 KiB.                                                                                                                                                    | The gateway installed and its grants given, and a bootstrap database login. No `SANOMA_SECRETS_KEY`. Project-wide locks serialize Vault writes; project administrators remain trusted. A move's destination check writes in `sanoma-move-check` and `sanoma-move-check-other`, so the login needs grants there.                                                                   |
| Sanoma Cloud, `kms-postgres`     | `sanoma/secrets` (`kmsPostgresStore` and `managedKmsStore`): `sanoma_kms.secrets` rows in the company database, each value under a fresh data key that a company-specific GCP CryptoKey wraps. Values up to 64 KiB.                                                                                                                                           | A KMS client authorized for that company's key only, through the [runtime identity broker](CLOUD-IDENTITY.md); `sanoma.secretStore.prepare` installs the schema and a restricted login. No `SANOMA_SECRETS_KEY`. Retained ciphertext needs every key version it was written under.                                                                                                |
| Cloudflare host bootstrap        | Delivery, not a store: the host's derived secrets and `{ env, host: true }` bindings are resolved on the machine that applies, uploaded as Worker `secret_text` bindings and given to the container as its environment at start. In the runtime there, environment and bootstrap bindings refuse writes and deletes, and an undelivered one reads as missing. | A changed value reaches the container at its next start (advance `configurationRevision`). `_FILE` inputs are read on the applying machine, never delivered. Values are plain in the Worker's and container's environment. See [Cloudflare secrets](../../../connectors/cloudflare/README.md#secrets).                                                                            |
| Cloudflare account Secrets Store | Not supported: no adapter.                                                                                                                                                                                                                                                                                                                                    | Readable only through a Worker binding, with no version or conditional write; management writes need an API token with Secrets Store Write; 100 secrets per account in open beta (facts dated 2026-11-06 in [the Cloudflare README](../../../connectors/cloudflare/README.md#the-account-secrets-store)). Use the built-in store or Supabase Vault for credentials Sanoma writes. |
| AWS Secrets Manager              | Deferred ([#462](https://github.com/Sanoma-AI/sanoma/issues/462)).                                                                                                                                                                                                                                                                                            | No adapter; not a release requirement.                                                                                                                                                                                                                                                                                                                                            |
| HashiCorp Vault KV v2            | Deferred ([#464](https://github.com/Sanoma-AI/sanoma/issues/464)).                                                                                                                                                                                                                                                                                            | No adapter; not a release requirement.                                                                                                                                                                                                                                                                                                                                            |

A `{ path, management: "external" }` binding is read-only to Sanoma in any store, and an `{ env }` or `{ bootstrap }` binding is read-only everywhere.

## Credential methods

A connector declares each authentication method with `defineAuthentication`. Every method keeps one versioned bundle in the store, and declares what that bundle needs from it. A method whose needs its binding or store cannot meet is a setup problem on its connector card and in `sanoma check`, and is refused before preview or consent; nothing is copied to another store instead.

| Kind      | What the bundle holds                                                         | What it needs from the store                                                                                                                                                                                         | Shipped users                                                                                         |
| --------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `api-key` | A key or token a person enters, checked against the method's schema.          | Readable; no writes by Sanoma after intake, so an external or read-only binding works. A Sanoma-managed binding is written once at Save with a conditional write.                                                    | Neon `apiKey`; Supabase `accessToken`; GCP `workloadIdentity` (the provisioning bearer, `{ bearer }`) |
| `fields`  | Several named values a person enters.                                         | As `api-key`.                                                                                                                                                                                                        | The runtime's OAuth application bundle (`client`, `{ clientId, clientSecret }`)                       |
| `signed`  | A signing key a person enters.                                                | As `api-key`.                                                                                                                                                                                                        | None yet                                                                                              |
| `oauth2`  | The grant (`oauthGrant`), written by the runtime's exchange and each renewal. | Writable by Sanoma, with conditional writes, so a Sanoma-managed binding in the built-in store, Vault or `kms-postgres`. Refused before consent otherwise. The application (`client`) is a separate `fields` bundle. | Supabase `oauth`                                                                                      |

## Accounts, connections and lifecycle

| Surface                       | Supported                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Boundary                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Named accounts                | Static declarations, code-defined dynamic creation rules, explicit defaults, account and revision selection through policy and execution, and isolated sandbox accounts.                                                                                                                                                                                                                                                                                                      | The connector must declare and verify its method, and its driver must opt into it. Declaring an account alone does not add driver support.                                                                                                                                                                                                                                                                                                                                                                    |
| Connection management         | Verify, review and Save intake; metadata-only prepare, configure and activate gates; ownership-aware controls, Test, storage review and workflow dependency labels.                                                                                                                                                                                                                                                                                                           | Health is last-tested. Pending and uncertain connections cannot run operations.                                                                                                                                                                                                                                                                                                                                                                                                                               |
| OAuth consent                 | `oauth2` methods: consent with single-use state and PKCE, the callback at `/connect/<vendor>/callback`, the code exchanged once by the built-in `connect` workflow, the grant and the application stored apart.                                                                                                                                                                                                                                                               | An exchange held for an approval must be approved within ten minutes. A grant the provider issued but the store did not keep leaves the account `uncertain` (Reconnect).                                                                                                                                                                                                                                                                                                                                      |
| OAuth renewal                 | On use: near expiry, or once on a rejection status the connector declares (`tokenRejected`); one process at a time under a lease in `sanoma_connection_renewals`. A scheduled renewal, and so a wake of a stopped instance, only for a flow that declares `refreshTokenLifetime`.                                                                                                                                                                                             | A renewal that may have spent a refresh token without storing the new grant leaves the account `uncertain`. Renewal on use is part of the call that needs it, not a policy decision of its own; a scheduled renewal is (`sanoma.connection.refresh`).                                                                                                                                                                                                                                                         |
| Reconnect, Disconnect, Revoke | Reconnect is a new consent. Disconnect makes the binding unusable and, for `oauth2`, deletes the stored grant; Revoke (`sanoma.connection.revoke`) asks the provider first, for a method with `revoke`.                                                                                                                                                                                                                                                                       | Disconnect deletes no other kind of stored credential and revokes nothing at the vendor. A call already at the provider completes.                                                                                                                                                                                                                                                                                                                                                                            |
| Moving between stores         | The built-in `migrate-store` workflow: plan, prepare (checks the destination), transfer under a write fence with expected versions, verify by reading every copy back, cut over once the deployed code selects the destination (rebinding connections), and retire the old copies after the rollback window. Each step is a policy-decided operation in the ledger; receipts hold names, versions and sizes, never values. The app's Secret storage panel runs it (**Move**). | One move at a time. A host's derived secrets are not found by themselves; pass them as `names` ([#707](https://github.com/Sanoma-AI/sanoma/issues/707)). An OAuth application already at the destination is kept and its grants need Reconnect. While the source is fenced, an OAuth renewal there fails closed and the current token stays in use; connect, disconnect and revoke wait. A rollback is a move back. Vendor tokens are not revoked, and a binding or namespace change alone transfers nothing. |
| Provider bridge               | A UUID session and a fresh provider process per operation, protocol-1 negotiation, process-bound plan tokens, shared release and schema caches, and session cleanup.                                                                                                                                                                                                                                                                                                          | At most 64 active or configuring sessions. No implicit mutation replay. Calls through the bridge carry no HTTP status, so an OAuth grant there renews only near expiry.                                                                                                                                                                                                                                                                                                                                       |

## Connector coverage

| Connector                           | Named methods                                                                          | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Neon                                | `apiKey`                                                                               | The verifier requires exactly one organization. It does not attest granular permissions or expiry; Neon enforces them on each request. A new SDK client per invocation.                                                                                                                                                                                                                                                                          |
| Supabase                            | `oauth` (the company's own OAuth application), `accessToken` (a personal access token) | Every call needs a named connection or a declared default; `SUPABASE_ACCESS_TOKEN` is not read. The account is the organizations the credential reaches, so a personal access token's account changes when its user joins another organization ([#706](https://github.com/Sanoma-AI/sanoma/issues/706)). Supabase publishes no refresh-token lifetime, so it gets no scheduled renewal. Supabase Vault is a store, separate from these accounts. |
| GCP                                 | `workloadIdentity` (an `api-key` bundle holding the provisioning bearer)               | The identity's project, number, service account, audience and issuer are declared in code (`gcpWithIdentity`); `verify` federates once through the provisioning identity service. Google IAM enforces permissions.                                                                                                                                                                                                                               |
| GitHub, Stripe, Docker and the rest | None                                                                                   | Their drivers keep their existing authentication. GitHub, Stripe and Docker resources use the session-capable bridge but do not opt into named authentication.                                                                                                                                                                                                                                                                                   |

The control plane's enrollment writer (`identityProvisioning.databaseUrl`) is a `secret()` entered on the app's Hosting page and read when an enrollment operation uses it; unset, the page lists it as missing and enrollment is refused. Login, model and remote secrets are separate from named operation accounts. For a new named account, the connector's method, live verifier, driver opt-in and per-call credential use must all be present; bridge session isolation supplies the provider-process boundary, not those pieces.

## Trust limits

What still sees a credential in the clear, and what the runtime does not promise. [`secret-leakage.test.ts`](test/secret-leakage.test.ts), [`secret-isolation.test.ts`](test/secret-isolation.test.ts) and [`oauth-lifecycle.test.ts`](test/oauth-lifecycle.test.ts) check the rest with sentinels in every column of the database (`findSentinels` in `sanoma/testing`).

- **The worker and any process making a direct call.** A bundle is read and opened per call, inside the call, and lives in that process's memory while the driver runs. Code authorized for a credential (a connector's driver, a verifier, an agent's operation) can use it as it likes: encryption is not a sandbox for that code. Errors are cleared of what the driver read; a result is recorded as the driver returns it, and so is what a driver logs.
- **The provider bridge.** The bridge sidecar and its provider process are given a resource's resolved write-only fields and the provider's credentials over the socket, in the clear, and their diagnostics may repeat them. The runtime takes out of an error the values the driver read, as written: a value shorter than eight characters, one the provider encoded, hashed or cut, or one the driver derived (a token it minted from a key it read) is not recognized.
- **The host's environment at start.** A Cloudflare host's Worker and container are given their secrets, `SANOMA_SECRETS_KEY` and `SANOMA_SIGNING_KEY` among them, as plain environment values, uploaded through the host vendor's API from the machine that applies (which resolves `_FILE` inputs). Anything running in the container can read them, and the secrets key opens every value the built-in store keeps.
- **The built-in store's key.** A sealed value is bound to its key, namespace and name, not to its database or company: a row copied to another database opens there under the same key and namespace. Each company's key (and each preview's) must be its own.
- **Revocation windows.** Disconnect deletes the stored grant, and the next call in any process is refused (a named connection's bundle is read per call; only the change driver keeps a GitHub installation token it minted, while that token holds), but a call already at the provider completes and an access token stays valid at the vendor until it expires unless Revoke ends it there. A refresh token sent without an answer may be spent, so the account waits for Reconnect.
- **Not checked.** Process output (a connector's own logging), agent prompts beyond what operations return, and the database's administrators, who hold the ciphertext and may hold the key.
