## Boundaries

- Depend on `better-auth` pinned exactly (the tables are declared by hand, so a release that adds a field is taken on purpose, with `tables.test.ts` saying what it needs), `drizzle-orm` pinned exactly as `sanoma/workflows` pins it (one copy, so the tables are the runtime's `databaseOn`'s), and `pg`, which is the pool's type here but also `drizzle-orm`'s peer, so a consumer resolves one `drizzle-orm` for both packages. Nothing under a company's `sites/` imports `better-auth`: pages post JSON to `/auth/better-auth/*`.
- The tables are declared in `src/db/` as the runtime declares its own (camelCase properties, snake_case columns, [workflows](../workflows/AGENTS.md)), one set per schema from `loginTables`, and a change there is a new migration in both folders: `pnpm --filter sanoma generate`, committed under `drizzle/` and never edited by hand; CI regenerates and compares, and the repository's `scripts/check-journal.ts` refuses a migration older than `main`'s newest. Better Auth's own migrations (`better-auth/db/migration`, Kysely's) are never run or read: the shape the adapter expects is what `TABLE_OPTIONS` (the `github` column, `rateLimit.storage: "database"`) adds to Better Auth's models, and `db/tables.ts` declares that shape, so a model Better Auth adds a field to is a change here first.
- The migrations are the worker's, each login's schema its own (run by `startWorker` after the runtime's own tables: `prepareBetterAuth`, the connector's `prepare`, for the visitor login, and `prepareBetterAuthStaff`, the launcher's `prepare` option, for the staff login), never the app's: `openBetterAuth` checks once per process and schema, at the first request, that the schema's journal in `drizzle` holds every entry the package ships (`migrationsApplied`, as `prepareDatabase` checks the runtime's own), waits up to a minute for a worker starting beside the app (`PREPARED_WAIT_MS`), and refuses otherwise, since on the Cloudflare host the app runs in the Worker script, which must not migrate (an advisory lock is one connection's, and Hyperdrive pools them). They run through the runtime's migrator under its preparation lock (`underPreparationLock`: polled on a session of its own, since a blocked lock statement can deadlock with a migration Postgres cannot see), once per database and schema per process: two workers preparing at once fail without the lock, which `login.test.ts` holds it to. The journal is what is trusted, on both sides: a schema dropped without its journal table reads as prepared (the tests drop both in `beforeAll`), and a schema with no journal is one Better Auth's own Kysely migrations made before this release, refused with the drop that resets it (`SCHEMA_EXISTS`), never migrated in place.
- The staff half answers on any host (`allowedHosts: ["*"]`), which leaves Better Auth's own Origin check nothing to compare: `handle` refuses a POST whose `Origin` is not the request's host itself (but at the token endpoint, `NO_ORIGIN`), and serves only the routes it lists (`ROUTES`, and `OAUTH_ROUTES` with the app's OAuth context).
- Better Auth sets no `input: false` field from a provider's profile (`parseAdditionalUserInputFromProviderProfile`), so `mapProfileToUser` cannot set `github`: the staff login admits in `user.validateUserInfo`, which Better Auth runs before any row on `create-user`, `link-account` and an OAuth `sign-in` with the raw profile (`source.oauth.profile.login`), answering `error=not_declared`; it keeps the login per request (a WeakMap on the endpoint context) and its account hooks write it (`keepLogin`), store no tokens (`dropTokens`, a `create`/`update` before-hook) and clear it when the account goes (`forgetLogin`); a new GitHub account under a login a row carries is refused (GitHub frees a renamed login), and a sign-in or link on an existing row is admitted by the row's verified email too; the visitor login's account hooks read the login from GitHub's `/user` with the account's own token on GitHub's redirect back (`noteLogin`, `/callback/:id` only), then drop the account's tokens (no GitHub grant is kept), refuse a second GitHub account (`oneGitHub`), and clear the login when the account goes (`forgetLogin`). Keep GitHub an untrusted provider for visitors (`trustedProviders` unset): a GitHub sign-in joins the account of its email only when GitHub verified that email (and, `requireLocalEmailVerified`, the account's own is verified), and a link needs GitHub's verified email too. A trusted GitHub would let an unverified GitHub email sign into someone's account, which `login.test.ts` holds it to. `allowDifferentEmails` is for the explicit link only (`/link-social`).
- The staff half's OAuth (`oauth.ts`, with `staff.oauth`) is the agent surface's authorization server, the app its resource server. `@better-auth/oauth-provider` and `@better-auth/cimd` are pinned exactly at `better-auth`'s version. Its plugins are made once per login, never per request (`openBetterAuth` makes an instance per pool on a Worker, sharing them): the CIMD discovery is the provider's own extension (`extensions`), not the `cimd()` plugin, whose start registers it again on each instance with an object of its own, which the shared options refuse. That discovery keeps a client's resolution under way and hands it to the next request that asks, unbounded, and a request a Worker cancels never settles its own: `oauthPlugins` waits for one no longer than `RESOLVE_WAIT_MS`, then drops the discovery that holds it (its document cache too) and resolves with a new one, for that request and those after. The signing keys are rows of `jwks`, so every instance signs with the same ones. A consent is kept by the agent its client stands for (`postLogin.consentReferenceId`, `agent:<id>` from the request the provider holds, `getOAuthProviderState`; its `shouldRedirect` never redirects), so a client mapped to another agent is asked again. A remembered consent is used only for a redirect that is the client's alone (`ownAddress`: HTTPS, not this computer): for any other, `handle` adds `prompt=consent` to authorize before the provider reads it (`withConsentAsked`), so the page is shown at every sign-in to a loopback redirect, which matches on any port (RFC 8252 §8.6). A token is that agent's alone: the provider asks the extension's `claims.accessToken` (`holding`) before it issues any access token, a code's or a refresh's (before the refresh token is rotated), with the reference the code or the refresh token carries, and it answers the agent as the token's `sanoma_agent` claim (`AGENT_CLAIM`), or refuses (`invalid_grant`) when the client stands for another agent now; `bearer` refuses a token whose claim is not the client's agent now, or that has none (a client with no agent any more is left to the app's admission, which names it). A client is only the declared agent's (`agentOf`, awaited: the app reads the files as they say then), at one gate: the provider finds every client through its discovery's `resolve` (`getClient`, which awaits it and takes null as no client; `matches` is not awaited, so cannot ask), which `oauthPlugins` wraps to answer none for a client no declared agent stands for, before its document is fetched, so the token endpoint and revocation answer `invalid_client` for one undeclared since. Two routes answer ahead of the provider, for what they say: authorize refuses on a page a person reads (the id as text, never a declaration to paste; the provider would redirect to an error page), and consent refuses one undeclared since its page was shown with a 403 (`consenting`; the provider answers 200 with its error page's address). The issuer and the resource are the instance's one configured agent address (`staff.oauth.address`, which each launcher makes from `SANOMA_HOSTNAME`, else `SANOMA_HOST_URL`, `agentAddressFrom` in `sanoma/workflows`; the login refuses at its making, `checkAgentAddress`, one not written as it is compared, since tokens are compared as strings, one whose issuer's path is not `STAFF_AUTH_PATH`, the login's base path, or whose resource is an origin's root; the other shape is a router's, `address.router`, from `SANOMA_AGENT_URL`, `SANOMA_COMPANY` and `SANOMA_ROUTER_SECRET`, read first: an issuer with no path and its `/mcp`, and no third shape), never read from a request: nothing in `staff.ts` or `oauth.ts` derives either from a `Host`, and nothing may. The issuer is the JWT plugin's `jwt.issuer`, the one setting the provider reads for a token's `iss` and the `iss` of authorize's redirect back. The resource's row is the login's to make (`ensureResource`, an insert that does nothing on a conflict, through `openBetterAuth`'s `seed`: once per process, database and resource, before the first instance there), never the provider's `resources` option, whose seed reads the table at each instance's start, which on a Worker is every request; no request makes a row, so a made-up `Host` leaves nothing (`enforcePerClientResources: false`, since a client is not linked to it). The provider issues a token only for a resource it has a row for and compares none with the request's host; authorize refuses any other `resource` itself, on a page. A row a former address left stays (nothing deletes one), and a token for it is refused by `bearer`. Behind a router the login still signs and checks everything, and the router nothing: its tokens name the company (`COMPANY_CLAIM`, which `bearer` checks is its own), its refresh tokens carry the company's prefix by the provider's own `prefix.refreshToken` (taken back only with it), and its authorization codes carry it by a wrap around `auth.handler` in `handle`, since the provider has no prefix for a code: `withoutCodeTag` strips it from the token endpoint's form (a code without it goes on as one the provider cannot find, so nothing is spent) and `withCodeTag` adds it wherever an answer sends a client a code, a `Location` or a JSON body's `url` that is an absolute URL with `code`, this issuer's `iss` and no `error`. It is applied to the routes that can send one alone (`SENDS_CODE` in `staff.ts`: authorize, the consent, and each route that makes a session, after which the provider goes on with the authorize), so no other answer is read; a route that sends a code is added there, a shape of it to `withCodeTag`, and `routed.test.ts` holds each of the four that do. A code it does not tag is one the router routes nowhere and the token endpoint refuses, and is said once on stderr. A refresh token without the company's tag is answered `invalid_grant` by `withoutCodeTag`, ahead of the provider, which would say `invalid_token`. It serves no RFC 8414 document for the router's issuer. The caller's address is the app's host's (`CLIENT_IP_HEADER`) unless the request is to the token endpoint or revocation, the routes a router forwards (`FORWARDED`), and carries this company's own secret at the router (`AgentAddress.router.secret`, what `routerSecretFor` makes of the router's master and the company's id, so one that leaks names callers at this company alone): never on a sign-in, an email code or the consent, whose limits a holder of the secret could otherwise step around (`withRoutedCaller`, the one place that header is believed; it rebuilds the request from its parts, since the app's request on Node is not one `new Request(request)` takes). Without an address there is no OAuth context: `handle` serves none of the provider's routes, every `/.well-known/` path is a 404, nothing is seeded and the half has no `bearer`. A token is a JWT only for a resource asked, and `bearer` checks the configured issuer and audience, on whatever host the request came in, against the keys' public halves, which `verifyJwsAccessToken` keeps under the login's one `keysCache` (five minutes, read again for an unknown key id at most every thirty seconds, one read shared by those waiting, through whichever request's instance began it; never an instance or a pool): a read that fails is thrown (`KeysUnread`), never a bad token. DPoP is off: the provider has no switch for it, so `handle` drops authorize's `dpop_jkt` and the token endpoint's `DPoP` header (`withoutDpop`), the wrapped `resolve` answers every client as not bound (a document's `dpop_bound_access_tokens` would make the provider demand the proof dropped), and every token is a Bearer, which is all `bearer` takes. The token endpoint and revocation are the routes a POST with no `Origin` reaches (`NO_ORIGIN`); name any other there explicitly. The RFC 8414 metadata is the login's own, never the provider's (which writes its endpoints on the request's host and says what is not served): `serverMetadataOf(address)`, a pure function of the address, its endpoint fields those `OAUTH_ROUTES` gives each route, on the issuer, its scopes and grants `AGENT_SCOPES` and `AGENT_GRANT_TYPES`, `none` alone for client authentication; `oauth.test.ts` pins every field. A route is added to `OAUTH_ROUTES` with its field, a method to `serverMetadataOf`. What a route answers itself ahead of the provider is in `GUARDS`, each guard for its own methods. The provider sends an authorize it cannot answer at the client's redirect to `<basePath>/error` (`getErrorURL`), which is no route of `ROUTES`: with the app's OAuth context `handle` answers it itself (`sentBack`, the refusal page with the link's `error` and `error_description` escaped), never Better Auth's own error page. The JWT plugin's `/token` is unlisted, so a 404 like any other route (`staff.test.ts`), with no `disabledPaths`. On the Worker, a document is fetched with `fetch` and redirects refused (`declaredMetadataFetch`: the Worker cannot pin an address it resolved), on Node with `@better-auth/cimd/node`'s transport, which `sanoma serve` passes.
- `verify` lets Better Auth's errors for a Host or configuration throw; only a missing or bad cookie is null. `handle` refuses a foreign Host itself (421) before `auth.handler`, which would throw it as a 500.
- Better Auth turns its Origin check off under `NODE_ENV=test` and its rate limit off outside production: the options set both explicitly, so tests run what production runs. The rate limit's counts are rows (`storage: "database"`) and the session is its row, read on every request (no `cookieCache`: it would hold a `github` a sign-in just wrote, and a revoked session, for its lifetime): nothing lives in the process but the token keys' public halves (`keysCache`), so an instance per request's pool (the Worker's shape) is the same login as one per process (Node's). The staff login mints one invite per email at a time across processes under a transaction-scoped advisory lock (`pg_advisory_xact_lock(hashtext('sanoma.login.invite.<email>'))`) on a connection of its own while Better Auth writes on another: safe through Hyperdrive's transaction pooling, and so the pool needs two connections.

After a change to `src/db/`, run `pnpm --filter sanoma generate` and commit `drizzle/`.
