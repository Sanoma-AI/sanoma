## Boundaries

- Depend on `better-auth` pinned exactly (the tables are declared by hand, so a release that adds a field is taken on purpose, with `tables.test.ts` saying what it needs), `drizzle-orm` pinned exactly as `sanoma/workflows` pins it (one copy, so the tables are the runtime's `databaseOn`'s), and `pg`, which is the pool's type here but also `drizzle-orm`'s peer, so a consumer resolves one `drizzle-orm` for both packages. Nothing under a company's `sites/` imports `better-auth`: pages post JSON to `/auth/better-auth/*`.
- The tables are declared in `src/db/` as the runtime declares its own (camelCase properties, snake_case columns, [workflows](../workflows/AGENTS.md)), one set per schema from `loginTables`, and a change there is a new migration in both folders: `pnpm --filter sanoma generate`, committed under `drizzle/` and never edited by hand; CI regenerates and compares, and the repository's `scripts/check-journal.ts` refuses a migration older than `main`'s newest. Better Auth's own migrations (`better-auth/db/migration`, Kysely's) are never run or read: the shape the adapter expects is what `TABLE_OPTIONS` (the `github` column, `rateLimit.storage: "database"`) adds to Better Auth's models, and `db/tables.ts` declares that shape, so a model Better Auth adds a field to is a change here first.
- The migrations are the worker's, each login's schema its own (run by `startWorker` after the runtime's own tables: `prepareBetterAuth`, the connector's `prepare`, for the visitor login, and `prepareBetterAuthStaff`, the launcher's `prepare` option, for the staff login), never the app's: `openBetterAuth` checks once per process and schema, at the first request, that the schema's journal in `drizzle` holds every entry the package ships (`migrationsApplied`, as `prepareDatabase` checks the runtime's own), waits up to a minute for a worker starting beside the app (`PREPARED_WAIT_MS`), and refuses otherwise, since on the Cloudflare host the app runs in the Worker script, which must not migrate (an advisory lock is one connection's, and Hyperdrive pools them). They run through the runtime's migrator under its preparation lock (`underPreparationLock`: polled on a session of its own, since a blocked lock statement can deadlock with a migration Postgres cannot see), once per database and schema per process: two workers preparing at once fail without the lock, which `login.test.ts` holds it to. The journal is what is trusted, on both sides: a schema dropped without its journal table reads as prepared (the tests drop both in `beforeAll`), and a schema with no journal is one Better Auth's own Kysely migrations made before this release, refused with the drop that resets it (`SCHEMA_EXISTS`), never migrated in place.
- The staff half answers on any host (`allowedHosts: ["*"]`), which leaves Better Auth's own Origin check nothing to compare: `handle` refuses a POST whose `Origin` is not the request's host itself, and serves only the routes it lists (`ROUTES`).
- Better Auth sets no `input: false` field from a provider's profile (`parseAdditionalUserInputFromProviderProfile`), so `mapProfileToUser` cannot set `github`: the staff login admits in `user.validateUserInfo`, which Better Auth runs before any row on `create-user`, `link-account` and an OAuth `sign-in` with the raw profile (`source.oauth.profile.login`), answering `error=not_declared`; it keeps the login per request (a WeakMap on the endpoint context) and its account hooks write it (`keepLogin`), store no tokens (`dropTokens`, a `create`/`update` before-hook) and clear it when the account goes (`forgetLogin`); a new GitHub account under a login a row carries is refused (GitHub frees a renamed login), and a sign-in or link on an existing row is admitted by the row's verified email too; the visitor login's account hooks read the login from GitHub's `/user` with the account's own token on GitHub's redirect back (`noteLogin`, `/callback/:id` only), then drop the account's tokens (no GitHub grant is kept), refuse a second GitHub account (`oneGitHub`), and clear the login when the account goes (`forgetLogin`). Keep GitHub an untrusted provider for visitors (`trustedProviders` unset): a GitHub sign-in joins the account of its email only when GitHub verified that email (and, `requireLocalEmailVerified`, the account's own is verified), and a link needs GitHub's verified email too. A trusted GitHub would let an unverified GitHub email sign into someone's account, which `login.test.ts` holds it to. `allowDifferentEmails` is for the explicit link only (`/link-social`).
- `verify` lets Better Auth's errors for a Host or configuration throw; only a missing or bad cookie is null. `handle` refuses a foreign Host itself (421) before `auth.handler`, which would throw it as a 500.
- Better Auth turns its Origin check off under `NODE_ENV=test` and its rate limit off outside production: the options set both explicitly, so tests run what production runs. The rate limit's counts are rows (`storage: "database"`) and the session is its row, read on every request (no `cookieCache`: it would hold a `github` a sign-in just wrote, and a revoked session, for its lifetime): nothing lives in the process, so an instance per request's pool (the Worker's shape) is the same login as one per process (Node's). The staff login mints one invite per email at a time across processes under a transaction-scoped advisory lock (`pg_advisory_xact_lock(hashtext('sanoma.login.invite.<email>'))`) on a connection of its own while Better Auth writes on another: safe through Hyperdrive's transaction pooling, and so the pool needs two connections.

Run `pnpm vitest run packages/sanoma/better-auth` with Postgres up (`pnpm db:up`) and the packages built (`site.test.ts` builds the fixture's app against them) and `SANOMA_TEST_DATABASE_URL` naming a database of your own. After a change to `src/db/`, run `pnpm --filter sanoma generate` and commit `drizzle/`.
