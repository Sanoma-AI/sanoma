# Working on sanoma/app

This package owns the local web UI over a Sanoma config. Its HTTP surface is its server functions and two server routes, `POST /api/chat` (the operator agent's chat: `routes/api/chat.ts` with its own CSRF middleware, behaviour in `src/server/chat.ts`; a turn of our loop is a 409 while `chatModel` says its model is not ready, as the composer says through `getChatModel`) and `POST /api/sign-in` (a code a person pastes back to their own agent's sign-in, `routes/api/sign-in.ts`, sent to the turn's run), and `/mcp` (the agent surface, an MCP server over Streamable HTTP: `routes/mcp.ts`, whose CSRF middleware lets through a request that says no origin, as an MCP client's, behaviour in `src/server/mcp.ts`; six tools as the person the login names, refused on a public site's host, to a visitor and to another site's `Origin`; no `subscriptions/listen`, so no request is held open), besides a login provider's `/auth/<name>/` routes, `/healthz` (answered before the login), `POST /api/token/redeem` (a handed-off api token for its one-time code and PKCE verifier, `src/server/token-redeem.ts`, registered by `appHandler` beside the webhooks, before the login), `appHandler`'s `ingress` (machine routes: the wakeup's `/wake`; each checks its own token), a git host's webhooks at `POST /webhooks/<vendor>` (`src/server/webhooks.ts`, registered by `appHandler` for each remote half with `webhook`, verified by the half's signature) and the GitHub App's manifest flow at `/setup/github/` (server routes in `routes/setup/github/`, behaviour in `src/server/setup.ts`), and an OAuth connection's callback, `GET /connect/<vendor>/callback` (`routes/connect/$vendor/callback.ts`, behaviour in `src/server/connect.ts`), and signing in to Sanoma's, `GET /hosting/sanoma/callback` (`routes/hosting/sanoma/callback.ts`, behaviour in `src/server/sanoma-sign-in.ts`: the Cloud token redeemed for its one-time code and stored, the state and verifier kept in the company's secrets, never a URL or a cookie); on a public site's own host, only `callFn`, `getActor`, the site's login's `/auth/<connector>/` routes and its `/robots.txt` and `/sitemap.xml` (`src/seo.ts`), and the files of its `public/` folder at their paths (`publicPath`); a GET or HEAD there under `/sites/<name>` that no file answers (Vite's dev server serves a site's modules there) is a 308 to its path at the root (`rootedAt` in `src/handler.ts`, by `sitePath` from `src/site-path.ts`). Scripts use `SanomaClient` from `sanoma/workflows`.

## Maintenance boundaries

- Use `@phosphor-icons/react` for interface icons, with the default regular weight and per-icon imports from `@phosphor-icons/react/dist/csr/<Name>`. Keep `components.json`'s `iconLibrary` set to `phosphor` so shadcn additions use the same library. The one exception is a site's own icon, a Lucide name in its `site.ts`, which only `SiteIcon` (`src/components/site-icon.tsx`) draws, with `lucide-react`, from the icons the build imports by file (`virtual:sanoma/icons` in `src/build.ts`): `lucide-react` stays pinned exactly, since those files are its layout, not an export.
- Login/setup signing uses `SANOMA_SIGNING_KEY`, independent of credential encryption. Login, model and remote secret lookups go through `src/server/secrets.ts` and the client's explicit bindings; never restore an environment-first fallback.
- Connection forms (`components/connections.tsx`, `form/secure-fields.ts`) keep entered values in the mounted form only and call secure intake server functions, never workflow operations or query/mutation caches. Actor-scope account queries, preserve approval request IDs, strip schema defaults/examples, and label provider health as last-tested. Agent tools return metadata and secure-input links only.
- Keep server-only config, credentials, and runtime code out of browser modules. Server functions (`src/functions.ts`) parse their argument and call `src/server/core.ts`, where their behavior lives and where the tests call it.
- Browser modules import values from `sanoma/workflows` only through `/shared`, and types from the rest; `sanoma/workflows/scenario` values (`loadScenarios`, `check`) only in `src/snapshot-build.ts`: a sandbox run's checks are the worker's, which the app reads (`SanomaClient.runChecks`).
- The app is one fetch handler, `appHandler` (`src/handler.ts`), the same on Node and on Cloudflare's workerd: it keeps nothing across requests but what it was built with, reaches Postgres through its client alone and reads no file. What the company's files say reaches it as `AppSnapshot` (`src/snapshot.ts`): made from the files by `src/snapshot-build.ts` (Node only), again once a file it read changed in the Node adapter (`startApp`, `liveSnapshot`), and once, at build time, in the Worker's bundle (`buildAppBundle`, `sanoma/app/bundle`). A server function reads `context.app.snapshot`, never `readFile`, `describeConfig` or git. What writes the repository (Adopt and Save, going live, connecting a repository) is a built-in workflow (`adopt`, `patch`, `go-live`, `go-live-host`, `go-live-cloud`, `connect-existing`) whose steps are `src/steps/` (`sanoma/app/steps`, given to the worker as `WorkerOptions.app`): a page starts the run and polls its `.result`, so the app itself never writes the checkout. What the worker tells the app it reads from the runtime's tables through its client: how far a taken app is behind its source (`SanomaClient.appBehind`) and a sandbox run's checks (`runChecks`). A git host's webhook is verified in the handler and followed by the worker, in a run of `follow`. A chat turn is a run too, of the built-in `chat` (`SanomaClient.startTurn`, its id `chat:<chat>:<message>`): the worker runs the engine (`src/steps/agent/`, `AppSteps.chat`) and writes the reply's chunks and the transcript to the database, `POST /api/chat` streams the chunks back from there (`replyStream` in `src/server/chat.ts`), and a stop (a new message) or a pasted sign-in code is a message to the run (`SanomaClient.turnCode`, sealed). A worker without the app's steps fails the turn at once (`NO_CHAT_STEPS`: chat from the Mac app). Never import a module of `steps/` from anywhere else but a type (the launcher imports `sanoma/app/steps`); the bundle's test (`test/app-bundle.test.ts`) holds them out of the bundle, and its build refuses a site's file or the app's own that imports what workerd lacks (`NodeOnlyImport`).
- `callFn` is a site's one way in: it calls only what `callApi` (`src/server/core.ts`) dispatches, an operation through `SanomaClient.call` (which keeps the one rule, `isDirect`), a workflow by `apiNameOf`, or `sanoma.describe` (`DESCRIBE_CALL`, the runtime's vendor, so none of the company's names: `agentDescription`, the description narrowed for an agent, the company's own workflows only, never the policy, a path, a desired value or a binding), always as the person asking. `/mcp`'s tools call nothing else. A new kind of call is a new name form there, in `createApi` and in `readSites` (`sanoma/workflows`' `src/sites.ts`, which reads a site's calls for Used by), never another server function for sites.
- A public site's host (`appHandler`'s host table, then `login/public.ts`'s `publicFront`) is answered ahead of the staff login and never reaches it: there only `callFn` and `getActor` answer (`PUBLIC_FNS` and `publicOnly` in `src/middleware.ts`), as the visitor the site's login half verifies or `anonymous`, never as the staff login's cookie or header. The router learns the site from Start's request context on the server and `<html data-site>` in the browser, never from the URL's host; the app's chrome and root queries stay out of the root's static imports (`components/app-chrome.tsx`, loaded lazily), so the public host never loads them.
- A webhook (`remoteWebhook`) is verified by its vendor's remote half, which reads the raw body once: nothing reads the request before it, and nothing it says happened is done until it verified. Each verified event is started as a run of the built-in `follow` (`SanomaClient.follow`, as the runtime's agent `host-check`, one run per event), which the worker does with its checkout; the route adds no rule of its own and is on every host, the Worker's bundle too.
- Preserve the loopback Host check, the loopback login's refusal of any other host, the dev server's refusal of any host but this machine (its hot updates' websocket bypasses the login), and actor requirements on mutations. The default typed actor name is not authentication; keep the README accurate when this boundary changes.
- Serve a file's text only for a file the config description names, a workflow's or a data file (`fileSource` in `src/server/core.ts`); never read a path a request makes up. A drift check is an ordinary run (`{ workflow: "drift", input: {} }`) that reads the data files itself; the page's declared list is the description's (made again once a file it loaded changes, `liveDescription`), joined with the last report's rows.
- `src/routeTree.gen.ts` is generated by TanStack Router; change route sources instead. The package ships `src/` without it: a company's build (`src/build.ts`, [Sites](README.md#sites)) writes its own tree, cache and output under the repo's `.sanoma/app/`, never into the app's install or `node_modules`. The router imports it as `#/routeTree.gen.ts`, which the company's build and its generated tsconfig (`paths`, ahead of this checkout's own tree) point at `.sanoma/app/routeTree.gen.ts`.
- `src/site.ts` is `sanoma/site` (re-exported as `sanoma/site`), exported as source: Vite compiles it in a company's build, never `tsconfig.build.json`. It is what talks to the running app, as browser code with nothing server-side: the app's own router's APIs, `defineSite`, `api` (`src/api-client.ts`'s `createApi` over `callFn`, bound in `src/queries.ts`, which the app's own calls share; typed by the company's `.sanoma/api.ts` through `Register`; the SDK's types re-exported from `sanoma/workflows/shared`), `content`, a public site's languages (`defineMessages`, `useMessages`, `useLocale`, `useLocales`), `RunForm` and `useActor`; it does not re-export `createFileRoute`, which a route file imports from `@tanstack/react-router` for the generator. `src/ui.ts` is `sanoma/ui` (re-exported as `sanoma/ui`, the one path a site imports it by), the kit, exported as source the same way: how a page looks, presentational only, so it could become a package of its own with no change to a site. Nothing it exports may reach the running app; a piece that needs the app goes in `site.ts`, or stays internal. `test/ui.test.ts` holds its module graph to that and snapshots its explicit list, so an export is added on purpose, as public surface the app keeps stable. The kit's own pieces are `src/components/kit.tsx`, which `components/common.tsx` re-exports for the app's screens. The Sites page and the bar find `sites/*/site.ts` by a root-relative glob (`src/lib/sites.ts`), which matches nothing in the package's own build.
- `vite.config.ts` is `appViteConfig()` from `src/build.ts`: the shipped build and a company's with sites are one pipeline, so a change to the build goes there, and `pnpm build`'s `dist/client` and `dist/server` stay what the zero-site build makes (Tailwind scans the whole package, `test/` too, so a fixture site uses no class the app lacks). `appDevServer` (`startApp`'s `dev`) is that config plus dev-only plugins, so `sanoma check` beside a dev server generates the same route tree. On its server `sanoma` is `noExternal` (why beside it); only an install from tarballs, `packages/sanoma/test/packed.test.ts`, shows a mistake there. `src/build.ts` loads only Node's modules and `sanoma/workflows/shared` at import (the bin loads it to write the site files); a site's folder name is `SITE_NAME` there, which `readSites` reads by too; Vite and its plugins load when a config or build needs them.
- The chat's coding agents (`src/steps/agent/harness.ts`) run in the worker through `HarnessAgent` in a session over the person's box (`boxSession` in `src/steps/agent/box-session.ts`, over a `Box` of the `Sandbox` contract), one turn at a time, on the box's clone of the draft (`src/steps/agent/carrier.ts`: the draft's branch in and the box's commits out as git bundles through `Source.bundle`/`unbundle`, never a remote URL or a token in the box), whose environment is explicit (never `process.env`); the model's key reaches an adapter only as its `auth` record, never in a log, a fixture or a session's environment. The agents are the installed connectors' (`ResolvedConfig.agents`, each a `CodingAgent` with its `KeyAgent` on the company's key): the engines are named `<id>` and `acp-<id>` and built from them at each turn (`engineOf` in `turn.ts`), an agent no installed connector gives failing its turn with a reply that says so; the app names no agent and imports no adapter. An adapter (`@ai-sdk/harness-claude-code`, `-pi`) is its connector's dependency, loaded by the connector when a turn needs it (never bundled: an adapter reads its bridge's files beside its own `dist/`), its key the model connector's (`KeyAgent.model`: the variables its driver declares, read through the client) passed as its `auth`. `@ai-sdk/harness` stays pinned exactly, at the version the connectors' adapters depend on. `@ai-sdk/provider-utils` is a dependency only so that the steps' declarations can name the types of `ai`'s `tool`; keep it at the version `ai` depends on. They sit on `@ai-sdk/harness` 1.0.158, whose exact `ai` the workspace's `overrides` raises to the one pin; move to the latest set, and drop the override, once their bridges ship lockfiles again (vercel/ai#23829). The override is this workspace's alone: a company's install keeps 7.0.147 under `@ai-sdk/harness`, and needs the template's `allowBuilds` (`packages/sanoma/template/pnpm-workspace.yaml`) for Pi's model providers under pnpm 11.
- Both engines' box is `personBox` (`src/steps/agent/box-session.ts`), chosen before the draft opens, in one of three places: the sandbox the data files declare (`ResolvedConfig.sandboxes()`, one at most), opened by its connector's backend (`sandboxBackends`, given the declaration's fields and the image and size its `sandbox.inputs` name, Agent37's in production); else, on this computer (`placeOf`, the bar's place), the local backend under `.sanoma/agent-home/boxes`; else, on a live instance, nowhere: the turn is refused with `NO_BOX` (what to declare, and Agent37's connector page), never run inside the live instance. Whatever the box, the checkout rule checks an agent's paths where its files are: `allowedPaths`/`mustAllow` take a `RealPaths`, `here` for our loop's draft on the instance and `realIn(box)` (the same function run by the box's Node) for an engine's clone, and the clone's install runs with the box's own pnpm (`OWN_PNPM`), never the version a `packageManager` names.
- A person's own coding agents (`src/steps/agent/acp.ts`) run over our ACP client on `@agentclientprotocol/sdk`, pinned exactly (its default import speaks ACP v1). The agents are not dependencies: each one's connector pins its packages (`OwnAgent`, read through `ownAgent`), installed on first use by `pnpm add --ignore-scripts --ignore-workspace` (no native module, nothing pnpm 11 would stop on) in the person's box under their `HOME` (`.acp/<agent>`), never npm (the desktop shell ships none; `install` says why); a version bump there is a new install. A box whose image carries the agent at those packages (`IMAGE_AGENTS/<agent>/installed.json`, Sanoma's box image, `packages/sanoma/box`) runs it from there and installs nothing; its `HOME` is `.acp` either way. Each runs in the person's box (`personBox`, the harness engine's too, stopped when the turn ends) through `Box.run`, never as a child of the worker (`acp.ts` imports no `node:child_process`), with the box's environment (the local backend's `sessionEnv`, never `process.env`), its `HOME` `.acp` under the box's home (`OWN_AGENTS_DIR`; the box by the person's id, never an email) and shims first on its `PATH` (`SHIMS`, under `.acp/shims`): `gh`, `open` and `xdg-open` refuse, and `security` is a Keychain that is there, empty, and takes nothing (a lookup or a removal answers macOS's "not found", 44), so only the person can sign it in and Claude Code keeps its sign-in in its own file in that `HOME` (a refused lookup, or no `security`, is to it a Keychain it cannot read, and it saves nothing); the engine refuses a principal that is not a person, and nothing of ours reads that `HOME`. A sign-in is the vendor's flow, shown on the card: never open its link, enter its code or keep either in the transcript once it ends, and never add a pseudo-terminal library (a vendor whose sign-in needs a real terminal gets the "run it once on this computer" card). Its read and edit requests and `fs/*` (then `Box.read`/`Box.write`) go through `allowedPaths`, `allow_always` is never chosen and only an offered option returned; what it runs through `terminal/*` is its own, in the box. The old `.sanoma/agent-home/acp` and `people` are no longer read: delete them by hand.
- The coding agents' state, kept across restarts under the repo's `.sanoma/agent-home`, is the local backend's boxes (`agentHome` in `src/steps/agent/checkout.ts`): `boxes/<name>`, a person's box for the company (`boxName`, `sanoma-<company>-<person>`), whose home holds both engines' state: their `HarnessAgent` sessions' (Claude Code's bootstrap and the bridges' run files, Pi's settings) and `repo`, the draft's clone (`carryIn`), which is all `boxSession`'s path rule allows, and under `.acp` (`OWN_AGENTS_DIR`) their own agents' `HOME` (`.acp/<agent>` installs, `.acp/shims`, pnpm's store and config, and their sign-ins), which a company-key session's own file calls may not reach and nothing of ours reads (an ACP agent's `fs/*` is the clone's only). Never give an engine a home that holds another's directory except as such a fenced one. What a bridge or an ACP agent runs itself reaches the whole box, the run files of a session under way too. Nothing below the machine user isolates people on a shared instance: what an agent runs itself, and Claude Code's own reads, can reach another person's box.

- The Permissions grid is the runtime's `permissionsGrid` (`sanoma/workflows/describe`), which `sanoma check` reports too: `permissions` in `src/server/core.ts` adds only the policy and its files, so a change to the grid goes there, never here. A draft's check is the repository's (`Source.check`, the `sanoma` package's `localGitSource`); `checks` in `src/steps/agent/checkout.ts` hands its result to the draft's card and the agent without the grid. Two grids are diffed by `src/lib/grid-diff.ts` and shown by `components/permissions-diff.tsx` through the page's own `PermissionsTable`, so the page and a change's review render one table. A change's pages (`routes/changes/`) read `SanomaClient.changes` and `.change` (`getChanges`, `getChange`), its Publish is its run's pending approval covering `sanoma.change.merge`, decided as any approval is (the run itself merges, deploys and closes the pull request on a rejection: the app never calls the host for a change), and the bar shows Changes only when the repository has a remote a connector reviews changes on (`getRemote`, `remoteOf`'s answer, the one the steps' `reviewsChanges` gives; never the URL, which may carry a token). A change opens from the chat's draft card (Review, `openChange`: `SanomaClient.openChange` titled as the chat, never `sanoma.change.open`, which only the change workflow calls; or Save, `saveDraft`, the `save-draft` built-in, which without such a remote merges the draft into the checkout, pushes `main` to an `origin` and reloads the worker), and every agent commit on a draft tells its change (`tellCommits`). The Permissions page's line under the grid is the host's own answer (`hostEnforcement`, `SourceHost.enforcement("main")`), its reason as the host words it. `test/changes-e2e.test.ts` walks the whole lifecycle through these surfaces over a real git repository and the fake host: a change to any of them keeps it passing.
- The app imports no connector a company chooses (a site's login comes from `resolved.logins`, by the name its `site.ts` gives), with one exception: `sanoma/better-auth`, whose `betterAuthStaffLogin` is the staff sign-in on a host, the product's own, which `worker/app.ts` composes as the `sanoma` bin does on Node. The connector's tests therefore import the app by the workspace's paths alone, never as a devDependency (a build cycle).
- What the app's source imports at build time is a dependency, not a devDependency: a company's install builds it. Its compiler options live in `tsconfig.site.json` (shipped; `tsconfig.json` extends it), its ambient types in `src/env.d.ts`.

## Checks

Run `pnpm --filter sanoma run typecheck:ui`. Build with `pnpm --filter sanoma build` before `pnpm vitest run packages/sanoma/app`: `startApp` serves the built app even when imported from source. Integration tests need Postgres; build workflows first in a fresh checkout.
