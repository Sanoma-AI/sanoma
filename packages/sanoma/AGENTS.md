# Working on sanoma

This package owns the `sanoma` bin a company repo runs, checks and exports itself with, and everything that repo imports besides its connectors (the author surface, `z`, `defineConfig`, the ledger stores, types): the one install. It is the one package: the runtime (`workflows/`), the app (`app/`), the OpenTofu bridge (`bridge/`), the test helpers (`testing/`), `sanoma dev` (`dev/`) and the Better Auth connector (`better-auth/`) are parts of it, each a directory with its own `src`, tests, guide and build (`build:<part>`), published as subpath exports (`sanoma/workflows`, `sanoma/app`, `sanoma/internal/bridge`, …). A part reaches another through the package's self-reference (`sanoma/workflows`), never a relative path across parts. There is one version, which every published connector carries too (`scripts/release-check.ts`).

## Maintenance boundaries

- `src/index.ts` re-exports exactly the names `allowImportNames` in `sanoma/workflows`'s `oxlint.json` lists (`z` from `zod`, the rest from `sanoma/workflows`), plus what `sanoma.config.ts` needs (`defineConfig`, the ledger stores) and types. A name added there is added here. The other entries are for one kind of file each, never a workflow (the lint refuses `sanoma/*` there), and each points straight at the part's module in `exports`: `sanoma/resources` (the runtime's `constructors`: `secret`) for data files, `sanoma/data` (its `data`: `collection` and its types) for `resources/data.ts`, the one data file that declares collections, `sanoma/secrets` (its `kms-secrets`) for a secret store's provider, and `sanoma/claims` (its `claims`: Sanoma's claims about connectors, apps and solutions) for a site's pages, which the site lint lets import beside `sanoma/site` and `sanoma/ui`.
- What a company repo's code imports at run time or for `tsc` is a dependency here, not a peer or a devDependency (`zod`, `@types/node`, `typescript`, `oxlint`): the repo installs `sanoma` and its connectors alone. The fixture holds that promise, with only those two installed and `sanoma` laid out as pnpm installs a tarball. Node's types reach the repo through the `/// <reference types="node" preserve="true" />` in `src/index.ts` (kept in `dist/index.d.ts` by `preserve`), never through the base's `types` or `typeRoots`, which cannot name pnpm's real path.
- `template/` is the company a new directory starts from (`init.ts`), shipped by `files`; the `Sanoma-AI/company-template` repository mirrors it. A company starts at the versions released with its launcher (`pinDependencies`): `sanoma` and each template connector at the launcher's own version, which every connector is released at. A connector added to the template is added to the root `package.json`'s `devDependencies` (`workspace:*`), so the tests run it from the checkout; `sanoma` itself never depends on a connector, which depends on it. npm drops a package's `.gitignore`, so it is `template/gitignore`, renamed when copied. A test starts a company from it (`startCompany`, its creator declared in `resources/people.ts`) and runs `check`, its Cedar policy and scenarios with it, and `env --check`: regenerate its `.env.example` with `sanoma env` when that fails. The scenarios' approver (`reviewer`) and the `editor` group are fixed in the template, since `sanoma init` changes only the founder's line; a creator's id that is the reviewer's or a runtime agent's becomes `founder`.
- The bin never imports `sanoma/testing` at run time; the fixture and the tests do.
- Dev mode runs each linked package's `watch` script and knows nothing of how it builds: a package that builds keeps a `watch` script beside `build`. Every child it starts is `detached` (a process group of its own) and ended through `end`, by its group; Windows has no groups, so there it is not `detached`, and `end` is `taskkill /T /F`.
- `identity` deliberately bypasses company config, `.env` loading and local database startup. Its service runs under a separate attached identity; never place it inside company-authored code.
- `cli.ts` imports only Node's modules, `./config.ts` and `./events.ts` (types aside); each command imports its module when it runs, and `init.ts` imports only Node's, so `--help`, `env`, `ledger export` and the dev-mode parent load neither the worker nor the app themselves. `sanoma` is `serve` in this process with the sites on the app's dev server, or in dev mode a supervised child `sanoma serve --dev` and nothing else; `sanoma serve` (hidden) always builds the sites; `worker` and `app` never start Postgres (`start: false`).
- Sites are built by `sanoma/app/build`, which `serve.ts` and `check.ts` import (through `sites.ts`) only when the repo has a `sites/` directory: a repo without one never loads it, and one without a site (a folder with `routes/`) has nothing written under `sites/` or `.sanoma/` but `.sanoma/api.ts`, the generated SDK, which `check` writes first and `serve` at start (`writeApi`), sites or not; the root `tsconfig.json` of a company never includes it. `sanoma` serves them from `startApp`'s dev server instead, on a loopback host only; the dev-mode parent imports the module for `sitesOf` alone, and ignores the app's `dist/client` and `dist/server` when there are sites. The build runs before the worker starts, and its server bundle imports the runtime as it resolves from this package's own `package.json` (`runtimeFrom`), so the worker and the app share one copy.
- `loadConfig` never calls `defineConfig` on what it loads: the config module's own call recorded its `file`, and a second call from here would record this package's. It then imports every file of `workflows/` and of each app's `apps/<app>/workflows/` (`kindDirs`) by its real path, adding each default export, a workflow, to `config.workflows`, and `<root>/resources/data.ts` and each app's the same way, the modules the workflows import, adding their exports, each a collection (`isCollection`, imported when needed), to `config.collections`, once each: the one data file the runtime runs, so `check`, the worker and the app see the same workflows and collections. A module imported by another path is another module, with its own definitions: hence the real path.
- `oxlint.json` is generated by `scripts/oxlint.ts` at build (gitignored, shipped by `files`): `sanoma/workflows`'s `oxlint.json` with a `sanoma` entry derived from its own, an override of its own for `sites/**` and `apps/*/sites/**` (not derived from the workflows' entry), the plugin from `dist/oxlint-plugin.js`, and the root `.oxlintrc.json`'s rules without vitest's. It must never `extends` a path into `node_modules`. `check` runs oxlint in the repo's root on the repo's `.oxlintrc.json`, which it writes when missing, never with `-c`.
- `sanoma/site`, `sanoma/ui` and `sanoma/ui.css` (the kit's look for a site's own stylesheet) point at the app's source, `app/src/site.ts`, `app/src/ui.ts` and `app/src/ui.css`, shipped by `files`: the app's site surface and kit are TypeScript source with JSX and DOM types, which only Vite and the sites' generated tsconfig read, so this package's Node-side `tsc` never follows them. `sanoma/ui` is how a page looks and `sanoma/site` what talks to the app (the rule and its test are in [the app's guide](app/AGENTS.md)).
- The company's own Postgres (`postgres.ts`) is the one place the bin starts a database: with no URL named, a PostgreSQL 18 cluster in `<main checkout>/.sanoma/postgres` from the `@sanoma-ai/postgres-<platform>` optional dependencies (`postgres-bin.ts`, as `sanoma/internal/bridge`'s `bridgeBin` resolves its own), its URL put in this process's `SANOMA_DATABASE_URL` before the config resolves and inherited by every child (dev mode's, a draft's check), never written to `.env`. A URL named is used as it is; nothing is started in Docker. `pg_ctl` runs `detached` (on Windows not, sharing the launcher's console, hidden under the desktop shell), and the launcher stops the cluster last, when no other client is connected and it started it or, as `sanoma` and `sanoma serve` do (`adopt`), found it left by another launcher: on Windows a crash leaves Postgres behind. In dev mode the parent owns it, so a restart of the child keeps it.
- `localGitSource` (`src/source.ts`) is the repository every change goes through ([Changes](workflows/README.md#changes)): a draft is a worktree at `.sanoma/drafts/<id>` on `draft/<id>` (the repo's `.gitignore` must cover `.sanoma/`), which the change workflow pushes to `origin` with the host's token as an `http.extraHeader` in git's environment (never the URL, the arguments or `.git/config`, and never in an error), checks, and removes with its branch once merged (`closeDraft`, after the draft's running check). `bundle` and `unbundle` carry a draft's branch to an agent box's clone and its commits back as git bundles (commits and the branch alone; an unbundle only fast-forwards the draft, its objects fsck'd by a git that checks a bundle's). `remoteUrl` is `origin`'s URL, which may carry a token: the app asks it only whether there is one.
- `localGitSource`'s `follow` fast-forwards a branch where it is checked out: the root's, or a draft's in its worktree (`draft/<id>`), which is how a push webhook's commits on a draft's branch reach the draft (the built-in `follow`, which the worker runs over this source). The webhooks reach `sanoma serve` (and `sanoma app`) through the app's handler, which registers `POST /webhooks/<vendor>` itself beside the `ingress` `serve.ts` passes (`/wake`); nothing in this package adds them, and an instance on a laptop hears none. `behind` is what the worker tells the Apps page, at its start and after each follow of `main`.
- A draft's `sanoma check` is `localGitSource`'s `check` (`src/source.ts`), which the app and the worker both call: one at a time in the process (a module-level queue, every check's scenarios on the one `<database>_check`), the company's installed bin as a child with only `CHECK_ENV` (`PATH`, `HOME`, and on Windows what its programs need to start) and the database URL, its result read from the last `checked` event, every field kept. `check` puts the repo's Permissions grid (`permissionsGrid` from `sanoma/workflows/describe`, the one the app's Permissions page computes) on that event, so a change is reviewed as the branch's grid against `main`'s from one code path.
- `tsconfig.base.json` (shipped as `sanoma/tsconfig.json`) is the compiler configuration a company repo extends, and the root `tsconfig.json` extends it too, adding the checkout's `types`, `paths`, `typeRoots`, `include` and `exclude`: there is one copy of the compiler options.

- Keep signing bootstrap independent of row encryption. `key.ts` respects direct and mounted-file inputs; local generation creates no encryption key when `config.secrets.store` supplies an external provider. Public behavior and recovery belong in [Secret storage and bootstrap](README.md#secret-storage-and-bootstrap).

Keep `runtime/Dockerfile`’s bridge release, source commit and archive checksums aligned with `packages/sanoma/bridge/scripts/download-bridge.ts`. Keep its `PNPM_VERSION` the root `package.json`'s `packageManager`, and its store's template what `scripts/runtime-packages.ts` prints: the release builds it after publishing, from npm. Keep the template project at `/pnpm/template`: `entrypoint.sh`'s `identity` runs its `sanoma`. `sanoma worker`'s port (`worker-port.ts`) is the image's; `sanoma serve` is the image's command `serve`, which `docker.container` passes. The image’s `SANOMA_BRIDGE_BIN` overrides npm’s platform binary. Preserve its build-time isolated-session protocol check; runtime changes require a new `sanoma` version.

## Checks

`pnpm vitest run packages/sanoma` needs Postgres (`pnpm db:up`) and builds what the fixture loads when it is stale (each part, `build:<part>`, then `connectors/ghost`, `anthropic` and `docker`); `packed.test.ts` installs `sanoma` and a connector as tarballs with pnpm, which needs the registry or a warm store for their third-party dependencies. `embedded.test.ts` runs this platform's PostgreSQL 18, which `pnpm postgres:download` fills in; without it the test skips, except in CI, where it fails. Run the gate with `SANOMA_TEST_DATABASE_URL` naming a database of your own.
