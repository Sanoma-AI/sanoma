# Working on sanoma

This package owns the `sanoma` bin a company repo runs, checks and exports itself with, and everything that repo imports besides its connectors (the author surface, `z`, `defineConfig`, the ledger stores, types): the one install. It is the umbrella: it depends on `@sanoma-ai/workflows`, `@sanoma-ai/app` and `@sanoma-ai/bridge` as dependencies, not peers.

## Maintenance boundaries

- `src/index.ts` re-exports exactly the names `allowImportNames` in `@sanoma-ai/workflows`'s `oxlint.json` lists (`z` from `zod`, the rest from `@sanoma-ai/workflows`), plus what `sanoma.config.ts` needs (`defineConfig`, the ledger stores) and types. A name added there is added here. The other entries are for one kind of file each, never a workflow (the lint refuses `sanoma/*` there): `sanoma/resources` (`secret`) for data files, and `sanoma/data` (`export *` of `@sanoma-ai/workflows/data`: `collection` and its types) for `resources/data.ts`, the one file the data-file lint lets import it.
- What a company repo's code imports at run time or for `tsc` is a dependency here, not a peer or a devDependency (`zod`, `@types/node`, `typescript`, `oxlint`): the repo installs `sanoma` and its connectors alone. The fixture holds that promise, with only those two installed and `sanoma` laid out as pnpm installs a tarball. Node's types reach the repo through the `/// <reference types="node" preserve="true" />` in `src/index.ts` (kept in `dist/index.d.ts` by `preserve`), never through the base's `types` or `typeRoots`, which cannot name pnpm's real path.
- `template/` is the company a new directory starts from (`init.ts`), shipped by `files`; the `Sanoma-AI/company-template` repository mirrors it. npm drops a package's `.gitignore`, so it is `template/gitignore`, renamed when copied. A test starts a company from it (`startCompany`, its creator declared in `resources/people.ts`) and runs `check`, its Cedar policy and scenarios with it, and `env --check`: regenerate its `.env.example` with `sanoma env` when that fails. The scenarios' approver (`reviewer`) and the `editor` group are fixed in the template, since `sanoma init` changes only the founder's line; a creator's id that is the reviewer's or a runtime agent's becomes `founder`.
- The bin never depends on `@sanoma-ai/testing` at run time; it is a devDependency for the fixture and the tests.
- Dev mode runs each linked package's `watch` script and knows nothing of how it builds: a package that builds keeps a `watch` script beside `build`. Every child it starts is `detached` (a process group of its own) and ended through `end`, by its group.
- `cli.ts` imports only Node's modules, `./config.ts` and `./events.ts` (types aside); each command imports its module when it runs, and `init.ts` imports only Node's, so `--help`, `env`, `ledger export` and the dev-mode parent load neither the worker nor the app themselves. `sanoma` is `serve` in this process with the sites on the app's dev server, or in dev mode a supervised child `sanoma serve --dev` and nothing else; `sanoma serve` (hidden) always builds the sites; `worker` and `app` never start Postgres (`start: false`).
- Sites are built by `@sanoma-ai/app/build`, which `serve.ts` and `check.ts` import (through `sites.ts`) only when the repo has a `sites/` directory: a repo without one never loads it, and one without a site (a folder with `routes/`) has nothing written under `sites/` or `.sanoma/` but `.sanoma/api.ts`, the generated SDK, which `check` writes first and `serve` at start (`writeApi`), sites or not; the root `tsconfig.json` of a company never includes it. `sanoma` serves them from `startApp`'s dev server instead, on a loopback host only; the dev-mode parent imports the module for `sitesOf` alone, and ignores the app's `dist/client` and `dist/server` when there are sites. The build runs before the worker starts, and its server bundle imports the runtime as it resolves from this package's own `package.json` (`runtimeFrom`), so the worker and the app share one copy.
- `loadConfig` never calls `defineConfig` on what it loads: the config module's own call recorded its `file`, and a second call from here would record this package's. It then imports `<root>/resources/data.ts` by its real path, the module the workflows import, and adds its exports, each a collection (`isCollection`, imported when needed), to `config.collections`, once each: the one data file the runtime runs, so `check`, the worker and the Resources page see the same collections.
- `oxlint.json` is generated by `scripts/oxlint.ts` at build (gitignored, shipped by `files`): `@sanoma-ai/workflows`'s `oxlint.json` with a `sanoma` entry derived from its own, an override of its own for `sites/**` (not derived from the workflows' entry), the plugin from `dist/oxlint-plugin.js`, and the root `.oxlintrc.json`'s rules without vitest's. It must never `extends` a path into `node_modules`. `check` runs oxlint in the repo's root on the repo's `.oxlintrc.json`, which it writes when missing, never with `-c`.
- `sanoma/site` and `sanoma/ui` are two one-line files each at the package's root, `site.js` and `site.d.ts` (`export * from "@sanoma-ai/app/site"`), `ui.js` and `ui.d.ts` (`export * from "@sanoma-ai/app/ui"`), shipped by `files`: the app's site surface and kit are TypeScript source with JSX and DOM types, which only Vite and the sites' generated tsconfig read, so it stays outside `src/`, where this package's Node-side `tsc` would follow it. `sanoma/ui` is how a page looks and `sanoma/site` what talks to the app (the rule and its test are in [the app's guide](../app/AGENTS.md)).
- The company's own Postgres (`postgres.ts`) is the one place the bin starts a database: with no URL named, a PostgreSQL 18 cluster in `<main checkout>/.sanoma/postgres` from the `@sanoma-ai/postgres-<platform>` optional dependencies (`postgres-bin.ts`, as `@sanoma-ai/bridge`'s `bridgeBin` resolves its own), its URL put in this process's `SANOMA_DATABASE_URL` before the config resolves and inherited by every child (dev mode's, a draft's check), never written to `.env`. A URL named is used as it is; nothing is started in Docker. `pg_ctl` runs `detached`, and the launcher stops the cluster last, only when it started it and no other client is connected. In dev mode the parent owns it, so a restart of the child keeps it.
- `tsconfig.base.json` (shipped as `sanoma/tsconfig.json`) is the compiler configuration a company repo extends, and the root `tsconfig.json` extends it too, adding the checkout's `types`, `paths`, `typeRoots`, `include` and `exclude`: there is one copy of the compiler options.

## Checks

`pnpm vitest run packages/sanoma` needs Postgres (`pnpm db:up`) and builds the packages the fixture loads when they are stale (`packages/workflows`, `packages/bridge`, `connectors/ghost`, `packages/app`, this one); `packed.test.ts` installs them as tarballs with pnpm, which needs the registry or a warm store for their third-party dependencies. `embedded.test.ts` runs this platform's PostgreSQL 18, which `pnpm postgres:download` fills in; without it the test skips, except in CI, where it fails. Run the gate with `SANOMA_TEST_DATABASE_URL` naming a database of your own.
