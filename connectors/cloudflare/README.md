# @sanoma-ai/connector-cloudflare

[Cloudflare Containers](https://developers.cloudflare.com/containers/) as a host that stops when quiet, and its [Durable Object](https://developers.cloudflare.com/durable-objects/)'s [alarm](https://developers.cloudflare.com/durable-objects/api/alarms/) as the wakeup that starts it again, for [`@sanoma-ai/workflows`](https://www.npmjs.com/package/@sanoma-ai/workflows). Both are one Worker per company, `sanoma-<name>`, on the account's workers.dev subdomain. And a set of [DNS records](#dns-records) in one of the account's zones, such as the ones a sending domain asks for.

## Usage

```sh
npm install @sanoma-ai/connector-cloudflare
```

The four types are writable: `read` and `import` (effect `read`), and the change operations only the apply workflow may call, `plan` (effect `read`), `create`, `update` and `delete` (effect `write`). The host is a host ([Hosts](https://github.com/Sanoma-AI/sanoma/blob/main/packages/workflows/README.md#hosts)) and the alarm a wakeup, with one more operation, `register`, which the worker calls. `container` is the host's earlier form, deprecated, the same Worker with every field declared:

| Type        | Operations                                                                                | Import id       |
| ----------- | ----------------------------------------------------------------------------------------- | --------------- |
| `host`      | `cloudflare.host.read`, `.import`, `.plan`, `.create`, `.update`, `.delete`               | its name        |
| `container` | `cloudflare.container.read`, `.import`, `.plan`, `.create`, `.update`, `.delete`          | its name        |
| `alarm`     | `cloudflare.alarm.read`, `.import`, `.plan`, `.create`, `.update`, `.delete`, `.register` | its host's URL  |
| `records`   | `cloudflare.records.read`, `.import`, `.plan`, `.create`, `.update`, `.delete`            | `<zone>/<name>` |

A data file declares them with the constructors in `@sanoma-ai/connector-cloudflare/resources`. The host says only the decisions: its name, its hostname and the database it runs on. Declaring the alarm is the whole switch for scaling to zero: without it, nothing starts a stopped container at a deadline, and a sleeping run waits for the next request.

```ts
// resources/sanoma/infra.ts
import { cloudflare } from "@sanoma-ai/connector-cloudflare/resources";
import { neon } from "@sanoma-ai/connector-neon/resources";

export const store = neon.project({ name: "acme", region: "aws-us-east-1" });
export const host = cloudflare.host({
  name: "acme", // the Worker sanoma-acme, at https://sanoma-acme.<subdomain>.workers.dev
  hostname: "app.acme.example", // optional: the app at its own domain, instead of workers.dev
  database: store, // the declared database it runs on: apply gives the host its URL
});
export const wakeup = cloudflare.alarm({ host });
```

Apply gives the host the rest before it plans (`deriveHosts` in `@sanoma-ai/workflows`), and a data file never writes it:

A `cloudflare.container` in the lockfile binds a `cloudflare.host` declaration of the same export: renaming the constructor recreates nothing, and the next change apply writes records the new type.

### Moving from `cloudflare.container`

As sanoma-ops moves, in one commit, then one apply from Resources:

1. **The host.** Replace `cloudflare.container({ … })` with `cloudflare.host({ name, hostname, database: store })` (`name` may go too: it defaults to the repository's), and drop `image`, `source`, `ref`, `port`, `secrets` and `domains`.
2. **The domains.** Put each one of `domains` on its site, `defineSite({ public: true, domain: "www.sanoma.work" })` in `sites/www/site.ts`. While the Worker has domains attached and no site declares one, the plan says so and changes nothing on the host, so a partial move never detaches them.
3. **The deploy key.** Remove the `deployKey` export (and from the default list). Keep `SANOMA_SOURCE_KEY` where it is (sanoma-ops binds it `{ env }`): the derived `#host.sourceKey` has the same public half, so apply finds the key GitHub holds by its text and takes over the `#deployKey` binding (a `bind` step `from` it, one lockfile commit), and makes no second key.
4. **The credentials.** Each credential the host is given must reach it from a binding or the store: one only in `.env` stops the plan, naming it, until it is bound `{ env }` in `sanoma.config.ts` (sanoma-ops binds `GITHUB_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `RESEND_API_KEY`, `SANOMA_SOURCE_KEY` and the GitHub App's keys already). `SANOMA_SIGNING_KEY` keeps its `{ bootstrap }` binding, so the host keeps its key and sessions; with none, the host gets its own, generated at its create.

The plan then binds `#host.sourceKey` from `#deployKey` and updates the host in place: the same Worker, its type recorded as `cloudflare.host`.

| Field                                | What it is                                                                                                                                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                               | The company's name, its identity: lowercase letters, digits and dashes, up to 56; the Worker and its application are `sanoma-<name>`                                                                       |
| `hostname`                           | Optional: the hostname the app is served at (`internal.acme.example`), attached like a site's domain; the host's `url` is then `https://<hostname>`                                                        |
| `database`                           | The declared database it runs on (a `neon.project` or `supabase.project`): apply gives the host its URL                                                                                                    |
| `image`, `source`, `ref`             | Optional overrides of what apply derives (above). `image` is pinned to a tag or digest, never `latest`: any registry's, which apply copies into the account's and pins by digest ([The image](#the-image)) |
| `configurationRevision`              | Optional non-secret configuration version: 1–63 ASCII letters, digits, `.`, `_` or `-`; advance it to restart with rotated bootstrap or environment values at the same source revision and image           |
| `id`, `url`, `worker_url`, `healthy` | Cloudflare's: the application's id, where the app answers (`https://<hostname>` once attached, else the Worker's workers.dev URL), the workers.dev URL, and whether it answers                             |

`cloudflare.container`, deprecated, declares every field itself: `image`, `source`, `ref`, `port`, `secrets` (each a `secret(...)`) and `domains` (by site name). Workflows that make a host for each of several companies (Sanoma Cloud's) call its operations with those fields filled.

The host's outputs are `{ url, wakeUrl, revision, healthy }` (`wakeUrl` its `worker_url`). Its capabilities: stops when quiet, a public URL, it runs an image rather than building one, no fixed egress. `healthy` is the application existing and the Worker answering `/__sanoma/health`, which does not start a stopped container: a stopped host is healthy, and a read or a drift check leaves it stopped.

An explicit `host.update` or `container.update` waits for startup readiness even when the desired fields are unchanged. It starts a stopped container and checks the source and configuration revisions before returning success, so retrying an upload whose startup failed cannot succeed from bindings alone. This unchanged update uploads no Worker or secret values. Reads and plans remain non-starting; a plan with no changes does not perform this readiness check.

`configurationRevision` participates in plans and reads. Change it when delivering new secret values without changing the source or image; for example, a managed lifecycle can derive it from its deployment and credential generation (`d1-g2`). The connector sends it as the reserved plain-text binding `SANOMA_CONFIG_REVISION`, and startup waits for that configuration revision as well as the source revision. It must contain no secret value. Secret values remain write-only: changing a stored value alone with the same configuration revision is not detected by a plan.

The alarm's field is `host`, the container it wakes (its URL); its state is `{ host, at, rang, healthy }`, the wake it holds, when its alarm last rang the host's `/wake` for it, and whether the host's Worker took the company's token. Its optional `token`, a `secret("NAME")`, names the secret that holds the host's wakeup token, by default `SANOMA_WAKEUP_TOKEN`: a workflow that makes a host and its alarm for each of several companies, outside any data file, gives each its own (`token: secret("CLOUD_ACME_WAKEUP_TOKEN")`, the secret the host's `secrets` give as `SANOMA_WAKEUP_TOKEN`). `create` mints the token there when none is stored, and its state then carries the name as `token`, so a `read`, `update` or `delete` given that state sends the same token; one given only an id uses the default. A data file leaves `token` out: apply reads and deletes an alarm by its id alone, so `plan` refuses another name. `register` takes `{ at }`, an ISO 8601 time, which replaces the wake the Worker held: a wake is "resume if stopped", so one that rings late, twice or for a replaced registration starts a worker that finds nothing to do and stops again. It names no host: on the host, the worker reads the host's URL from `SANOMA_HOST_URL`, which the Worker gives the container; off it, from the credential `alarm.create` stored. A runtime whose data files declare no wakeup, but whose environment has both `SANOMA_HOST_URL` and `SANOMA_WAKEUP_TOKEN` (a host Sanoma Cloud made), registers at the same route itself, with no connector call (`envWakeup` in `@sanoma-ai/workflows`).

The logo is Cloudflare's cloud from [Simple Icons](https://simpleicons.org/?q=cloudflare) (CC0), there only to identify the service an operation calls.

## The Worker

The Worker script is the company's app. The package ships what it uploads, `worker/`: `index.js`, the entry, and `instance.js`, its logic with no imports (typed by `instance.d.ts`), which the fake runs in Node so both kits check the code Cloudflare runs. Beside them goes the app bundle under `app/` ([The deploy](#the-deploy)), or, on a Worker that never served an app (a create's uploads before its first bundle), `no-app.js` in its place, which answers 503 "being set up": nobody was served there yet. The entry's fetch:

- sends `/__sanoma/health`, `/__sanoma/wake` and `/__sanoma/app-bundle` to the Worker's one Durable Object, `SanomaInstance` (`DurableObject` from `cloudflare:workers`);
- answers `GET /wake`, the Host contract's wake, by having the object start the container now (204);
- hands every other request to the app bundle's `fetch(request, env, ctx, host)`, imported on the first request, with `x-sanoma-client-ip` set from `cf-connecting-ip` over any copy the client sent, and `host.startNow()` the object's, over RPC (the app's call when it queues a run). A page, an API call, a webhook and a sign-in are all the app's, on the Worker, so a visitor never waits for a cold container (forty seconds to minutes), and the app reaches the company's database through [Hyperdrive](#the-database).

The object runs the company's worker in its container and never sees a visitor's request. It marks each of its answers with `x-sanoma-deployment`, the id of the Worker version that answered (its `CF_VERSION_METADATA` binding's, the `deployment_id` an upload answers with), so a deploy tells the version it uploaded from an earlier one still answering, and the object's answers from anyone else's. It:

- starts the container at the Worker's source revision, configuration revision and uploaded image (`ctx.container.images.runtime`: the copy, pinned by digest), as a `standard-1` instance (½ vCPU, 4 GiB: the policy refuses `basic`), with the Worker's text bindings (plain and secret) as its environment, and waits for its `/healthz` (up to ten minutes, the clone and install included). Container labels hold the two non-secret revisions, an image hash and a hash of `SANOMA_DOMAINS`; secret values never enter them. A container running with other labels is drained: sent SIGTERM, so its worker stops dequeuing and exits, given thirty seconds, then destroyed if it still runs, and started again at the Worker's labels;
- answers `GET /__sanoma/health` with the source revision, configuration revision when set, and whether the container runs and answered, without starting it. With `?start=1` and `Authorization: Bearer <SANOMA_WAKEUP_TOKEN>`, it starts the container at the Worker's revisions, answering 202 until it answers, then 200;
- passes `GET /__sanoma/app-bundle?revision=` with the token on to the container's port, starting the container first (202 meanwhile): the worker there builds the bundle at that revision ([The deploy](#the-deploy));
- holds the company's one wake at `/__sanoma/wake`, with the token: `GET` shows `{ at, rang? }`, `PUT { at }` replaces it and sets the object's alarm, `DELETE` clears it. Each route that needs the token answers 401 to another one, and 404 on a host without one;
- at the alarm, starts the container and calls its `/wake`, then notes when (`rang`); a failure throws, so Cloudflare rings the alarm again;
- over RPC, `startNow()`: sets the alarm now, unless one is due sooner, and the alarm starts the container without the caller waiting and sends it `/wake`; a wake held for later is set again once the start is made, and one that rang never rings twice.

A container that ended reports how once (`exit`, a 503), so a deploy waiting on it stops rather than starting it again. Cloudflare stops the container after ten minutes without a request to the object; the object, its storage and its alarm stay. Visitors' requests go to the app, not the object, so a run the worker keeps busy longer than that relies on the worker's own registration (a sleep's end, a queued run's `startNow`) to start it again.

The application is of the `durable_object` scheduling policy (public beta, the one Cloudflare documents for new applications; it refused `default` on the account the connector was first run on): the object starts its container, with the image and the instance type it names, so the application is only a name and the object's namespace, and has no image, versions or rollouts. The policy is fixed once an application is made: one of the `default` policy under that name is deleted by hand before the apply. A Worker of that name that is not Sanoma's (no `SANOMA_INSTANCE` binding) reads as gone, and a create or a delete refuses to touch it.

## The deploy

A create, in Wrangler's order, copies and pins the image and waits until Cloudflare prepared it ([The image](#the-image)), makes or updates the [database's config](#the-database), and, the first time, uploads the Worker without an app (`no-app.js`) with the object's migration (`new_sqlite_classes`) and its class as a container's with that image (`containers: [{ name, class_name, images: { runtime } }]`), turns its workers.dev URL on, makes the application for the object's namespace (`{ name, scheduling_policy: "durable_object", durable_objects: { namespace_id } }`), and uploads that Worker once more: the object learns which application backs its namespace only from a deployment made after the application exists (without it every start answers "There is no container application assigned to this Durable Object namespace", found on the first real deploy, 2026-10-29). Then every create and update deploys in three steps:

1. **The bundle.** `GET /__sanoma/app-bundle?revision=R` on the workers.dev URL with the instance token, asked every poll: the object starts the container if it is stopped (202, unmarked), and the worker there checks out `R` and builds the app bundle for `workerd` (`@sanoma-ai/app`'s `AppBundle`: its modules, its assets, its compatibility date and flags), answering 202 until it is built, then 200 with it, each answer marked `x-sanoma-app-bundle`. It is asked of the Worker deployed, whose container still runs R-1, when that runs the declared image; a deployment that cannot build it is stale: a 401 (the deployed Worker or its container holds another token), an `exit` (its worker ends at startup) or an unmarked 404 (a Worker without the route). A new image, a stale deployment and a create have R's own container build it instead: the Worker at R is uploaded first (R's bindings and image, this package's `index.js` and `instance.js`), serving visitors what they are served now: the app deployed, its modules read back (`GET …/scripts/{name}/content/v2`), its compatibility date and flags and its assets kept (`keep_assets`), untagged; a Worker that never served an app gets `no-app.js`. Its object starts the container at R, and once that version is [live](#live-before-asked) the bundle is asked of it: an answer without its version's id is an earlier version's, asked again whatever its status, and its own `exit` (R's worker ends at startup) is a refusal. A marked answer other than 200 or 202 (a failed build, a revision the route refuses) is a refusal. Anything else (no answer, an error of Cloudflare's, a body cut off, a workers.dev URL not routed yet) is asked again; one ask may take the whole budget, as a bundle is large. The bundle has its own budget, `startTimeoutMs` (ten minutes): still none after it fails the apply retryably, "still building the app bundle at R after 600 s", saying what the last ask saw. Its assets (the client build and the prerendered pages) then go in through an [assets upload session](https://developers.cloudflare.com/workers/static-assets/direct-upload/) (`POST …/scripts/{name}/assets-upload-session { manifest }`, then each bucket it asks for, one after another, to `POST …/workers/assets/upload?base64=true` with the session's jwt).
2. **One upload.** The Worker is uploaded once with everything: `index.js`, `instance.js` and the bundle's modules under `app/`, its compatibility date and flags, the bindings (the declared ones, the namespace, `CF_VERSION_METADATA`, `DATABASE` as Hyperdrive, `ASSETS`), `assets: { jwt, config }` (`run_worker_first: ["/*", "!/assets/*"]`, the client build straight from the assets; `html_handling` and `not_found_handling` `none`) and its version tagged with `R` (`annotations: { "workers/tag": R }`). From here visitors get the new app. Then the missing domains are attached, and the upload is waited for until it is [live](#live-before-asked).
3. **The restart.** `GET /__sanoma/health?start=1` with the token, asked every poll until the object answers 200 at `R` and the configuration revision: the object drains a container at another revision or image (SIGTERM, thirty seconds, then destroyed) and starts one at `R`; one R's build started already is kept. Its own budget, the same `startTimeoutMs`: still not after it fails the apply retryably, "still starting at R after 600 s". The step is idempotent: the next apply plans none, and an explicit update whose plan is none runs it alone, uploading nothing.

### Live before asked

An upload takes a while to reach every Cloudflare location, and until then the version before answers (on a new Worker, workers.dev's 404). After its last upload before a step asks the object, a deploy asks `GET /__sanoma/health`, without `start` so an earlier version starts nothing, every poll until the object answers with the uploaded version's id in `x-sanoma-deployment`, within the step's `startTimeoutMs`: any other answer, a 401, a 404 or a 503 among them, is "not yet", never "stale". The step's own asks then count only that version's answers.

No step answers a visitor 503 or an error: the app deployed answers until the upload of the new one, while R's container builds it too, and the new one after it, and neither needs the container; only a Worker that never served an app answers `no-app.js`. A domain declared before and no longer is detached before the first upload of R's bindings, while they still record it, and a missing one attached once the upload with the app records it: whatever fails in between, none is left attached and unrecorded. A plan compares the version's tag with the revision, so a deploy that ended between its two uploads (the app deployed still served under R's bindings, untagged) plans an update, and one whose version was not tagged (a deploy before tags) plans one once. A built-in workflow's runs on R-1 carry to R when its code is unchanged (`builtInCode` in `@sanoma-ai/workflows`), so the restart strands none of them. A plan compares secret binding names, never values: the Worker's settings never show them. Advance `configurationRevision` to upload rotated values and restart a running container with them; a value change alone does not trigger an update. A delete detaches the custom domains the Worker was declared to serve (its `hostname` too), deletes the application, the Worker with its object's storage, then the database's config.

## The database

Every host needs `SANOMA_DATABASE_URL` among its secrets: a create or an update without it, or with a URL that is not `postgres://` or `postgresql://`, is refused before anything changes, and the error never shows the URL. The container keeps the direct URL in its environment. The app on the Worker reaches the database through a [Hyperdrive](https://developers.cloudflare.com/hyperdrive/) config of the Worker's name, one per host, made or updated at every deploy from the URL (`{ scheme, host, port, database, user, password }`, port 5432 unless the URL names one, user and password decoded) with query caching off, `caching: { disabled: true }`: the app's reads must see its own writes. The upload binds it as `DATABASE`, whose `connectionString` the app connects with. Hyperdrive must reach the database from Cloudflare's network: a host on `localhost` or a private address is refused by Cloudflare at the config's write. The token needs Hyperdrive Edit.

## The image

A container of the `durable_object` policy runs an image of its own account's registry pinned by digest, `registry.cloudflare.com/<account id>/<repository>@sha256:<digest>`, never a tag, which Cloudflare stores and pulls without a limit (Docker Hub's pulls are not cached and are limited per address). So a create or an update first copies the declared image there and pins the copy by its manifest's digest, and the object starts that: `ghcr.io/sanoma-ai/runtime:0.8.1` becomes `registry.cloudflare.com/<account id>/sanoma-ai-runtime@sha256:…` (the path with `-` for `/`, copied as `:0.8.1`). An image in the account's registry by a tag is not copied: its manifest's digest is asked for (`docker-content-digest`); one there pinned by digest runs as it is, with no registry request. The copy is registry to registry in Node, no Docker: the source pulled anonymously (a public image; the token its registry's challenge names), the target pushed to with temporary credentials from `containers.registries.credentials.generate` (push and pull, an hour, never stored or logged). Each blob the account lacks is streamed across in one request of its known length, then the manifest, unchanged; when the account's manifest for that tag already has the source's digest, nothing is copied, and a digest-pinned source must answer that digest. Docker Hub is not copied from: declare `ghcr.io/sanoma-ai/runtime`. The source must be one image manifest (OCI or Docker v2), not an index: the release pushes one (`provenance: false`). Then the account prepares the pinned image to run (`POST …/containers/image-preparations { image }`, `containers.images.prepare`), asked again every two seconds until it is `ready`, as Wrangler does: an `error` fails the apply with Cloudflare's `reason`, not retryable, and fifteen minutes without `ready` fails it as retryable. Both come before the upload, so a copy or a preparation that fails leaves the Worker as it was.

The Worker's `SANOMA_IMAGE` binding holds the declared image and its upload the pinned copy, so a read reports the declared image, a plan and drift compare the declaration with it, and a declaration that names `ghcr.io` plans no change once applied. An image pushed by hand (`npx wrangler containers push`) is declared as the `registry.cloudflare.com/<account id>/...` reference Wrangler prints, and runs as it is, pinned; another account's is copied like any other registry's image.

## Scale to zero

1. **The connector.** Add `cloudflare` to the connectors in `sanoma.config.ts`: the worker on the host calls `cloudflare.alarm.register` through it.
2. **Credentials.** On the connector's page, `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (below).
3. **Go live.** `infra.ts` declares the host and, after it, `export const wakeup = cloudflare.alarm({ host })`: apply mints `SANOMA_WAKEUP_TOKEN` when none is stored and gives it to the host. One apply makes the Worker, waits for it, then the alarm, which checks the Worker holds the token.
4. **A sleeping run.** Start a workflow that sleeps past ten quiet minutes. Before the container stops the worker registers the sleep's end; at `at` the object's alarm starts the container and calls `/wake`, and the run continues.

To stop scaling to zero, delete the `wakeup` line (from a `cloudflare.container`, its `SANOMA_WAKEUP_TOKEN` too), and apply: the alarm is deleted, and the next request still starts the container. The token stays among the Worker's secrets (apply mints one when none is declared: the bundle and restart routes need it), so the runtime registers with the Worker's wake route itself (`envWakeup`), as a Sanoma Cloud company's does.

## Custom domains

Each hostname in `domains` is attached to the Worker as a [Workers custom domain](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) by a create or an update: Cloudflare then makes its DNS record and certificate and routes it to the Worker. The zone is the hostname's last two labels (`www.acme.example` is in `acme.example`), looked up in the account once per apex when a domain is to be attached (`GET /zones?name=&account.id=`); a hostname whose zone the account does not hold, or the token cannot read, is refused, naming the hostname and the zone, before anything changes. An update lists the Worker's attached domains first (`GET …/workers/domains?service=`), and only a missing one's zone is looked up; before the upload, the ones declared before and no longer are detached (`DELETE …/workers/domains/{id}`), while the Worker's bindings still record them, and after it each missing one is attached (`PUT …/workers/domains { zone_id, hostname, service }`), once they record it. Whatever fails in between, no domain is left attached that the bindings do not record, and the next apply attaches what is still missing; a site's domain never reaches a Worker that would serve the app there, and a renamed one is down from the detach to the attach. A domain attached by hand and never declared is left alone. A read lists the Worker's attached domains too and shows only the declared ones attached, so a domain whose attach failed, or one detached by hand, is drift that the next apply attaches again. A delete detaches every declared one before the Worker goes. A container without `domains` makes none of these requests, unless it served some before, which are then detached. A zone such as `acme.co.uk`, whose apex is three labels, is not found yet.

`hostname`, the app's own domain, is attached, detached and read the same way, in the same zone lookup, and the Worker's `SANOMA_HOSTNAME` binding records it (as `SANOMA_DOMAINS` records the sites'), so one no longer declared is detached and one detached by hand is drift. With it attached, the host's `url` is `https://<hostname>` (a read of one not attached gives the workers.dev URL, so a failed attach or one detached by hand never points at a name that does not route). The wake path stays on workers.dev, which stays on: the Worker's `SANOMA_HOST_URL` binding, the host's `wakeUrl` (its `worker_url`, which apply gives the alarm as its `host`) and the health checks, so a wake never waits on the hostname's DNS or certificate, and declaring or dropping a hostname leaves the alarm as it is. A `hostname` that is also one of `domains`' values is refused, `invalid`, at a plan and a create, before any request: the app answers at every hostname that is not a site's. A renamed `hostname` is detached before the upload and the new one attached after it, as a site's domain is: in between, a short window, no hostname is attached and the app answers on workers.dev alone (the host's `url` reads as it), and a failure there leaves the bindings naming the old one, detached, or the new one, not yet attached, which the next apply attaches.

## DNS records

`cloudflare.records({ zone, name, records })` is a set of DNS records in one of the account's zones, compared as a set, in no order. A sending domain's records are the case it is made for: `records` names a declared `resend.domain`, whose `dns_records` it then takes ([a field taken from another resource's state](https://github.com/Sanoma-AI/sanoma/blob/main/packages/workflows/README.md#resources)), or is a list written out.

```ts
// resources/infra.ts
import { cloudflare } from "@sanoma-ai/connector-cloudflare/resources";
import { resend } from "@sanoma-ai/connector-resend/resources";

export const mail = resend.domain({ name: "sanoma.work" });
export const mailDns = cloudflare.records({ zone: "sanoma.work", name: "resend", records: mail });
```

| Field                   | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `zone`                  | The zone's name, as the account holds it (`sanoma.work`); changing it replaces the set                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `name`                  | The set's label (`resend`): lower case letters, digits, `-` and `_`. Its identity is `<zone>/<name>`; changing it replaces the set                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `records`               | The records, at least one: `{ type, name, content, priority?, ttl? }` each (`dnsRecord` from `@sanoma-ai/workflows`): TXT, MX, CNAME or CAA, the full name in lower case (the zone's name or one ending in it), a TXT record's text unquoted, a priority for MX, a ttl in seconds (1, automatic, when left out). One type, name and content declared twice with another ttl or priority, a name outside the zone, or a CNAME declared beside another record of its name, or two SPF policies (`v=spf1` TXT records) declared at one name, is refused, `invalid` |
| `zone_id`, `record_ids` | Cloudflare's: the zone's id, and each record's, in the order of `records` as a read gives them                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

**Ownership.** Every record the set writes carries the comment `sanoma:<zone>/<name>` (`sanoma:sanoma.work/resend`), in that case exactly, which is how a read finds its records (`GET /zones/{id}/dns_records?comment.exact=`): the set is the records that carry it, and none is gone. A record's comment holds 100 characters on a Free zone, so a set whose mark is longer is refused, `invalid`. A record without that comment is never changed or deleted, whoever added it, with one exception: a record identical to a declared one in type, name and content, and an MX record's priority (one added by hand before the set was declared), is adopted, patched to carry the comment and the declared ttl; so is one a changed record would be patched to, whose marked one is then deleted. An adopted record is the set's from then on: it carries the mark, so it changes with the set and is **deleted with it**, and the comment it had is replaced by the mark (the set finds its records by the exact comment, so it keeps no other). A record in the way of a declared one is refused, `conflict`, naming it, before anything is written, whether the declared one is to be posted or a marked one patched to it: a CNAME at the name (or a declared CNAME beside any record), another SPF policy (a `v=spf1` TXT) at the name, an MX record to the same server at another priority, a record identical to a declared one that another set's comment marks, or one identical to it that is proxied (a set's records are DNS only, and adopting it would turn its proxy off). Every page of a lookup is read, so a busy name hides nothing.

**Writes.** A create or an update is one batch (`POST /zones/{id}/dns_records/batch`), which Cloudflare runs as one transaction, all or nothing: a post for each declared record no record holds, a patch for each marked record of a declared one's type and name whose content, priority or ttl changed, or whose proxy was turned on by hand (one of the same content first, so a ttl's change patches that record), and each one adopted, and a delete for each marked record no longer declared. Each record is written unproxied (`proxied: false`), with a ttl of 1 (automatic) unless declared; a CAA record's content, `0 issue "letsencrypt.org"` (its value quoted or not), is sent as its fields and compared with its value quoted, as Cloudflare shows it. A set already as declared writes nothing, an update retried after its batch was written too. A delete is one batch deleting the marked records, and only those. A read gives each marked record as `records` holds it: its name in lower case with no trailing dot, a TXT record's text with the quotes Cloudflare may show around it taken off (and a long one's quoted parts joined), the priority of an MX record, the ttl (1 when automatic); a plan and drift compare a declared ttl left out as 1.

**Records not known yet.** Where `records` is taken from a domain apply creates in the same run, `plan` is given `records: null`: a set not bound yet plans a create, one the zone holds an update, with `records` among `unknown`, and apply plans it again at its step with the domain's records. An `update` whose `desired` leaves `records` out (the domain is absent or unreadable, so drift and apply leave the field out) keeps what the zone holds and writes nothing. `records: null` at a create or an update is refused, `not_known`: apply fails such a step before it gets there.

**The token.** The API token needs **Zone → DNS → Edit** on the zone, beside Zone Read (the zone's lookup) and the Workers permissions the container needs. A token without it is refused, not retryable, `no_dns_permission` (status 403), naming the permission and the zone, whether Cloudflare refuses the read of the records or the batch. A zone the account does not hold, or the token cannot read, is refused at a create, an update or a delete, `no_zone` (Cloudflare lists neither, so a delete is not taken as done with the records perhaps left behind); a read there finds the set gone.

## Driver

`@sanoma-ai/connector-cloudflare/driver` calls Cloudflare through its official SDK, [`cloudflare`](https://www.npmjs.com/package/cloudflare) (Stainless), with its own retries off (the runtime retries what is retryable), and calls the company's Worker with `fetch`. The `cloudflare` connector the package root exports carries it and its fake (`withSetup` from `@sanoma-ai/workflows`), so a config names the connector alone and workflows never import the driver (the lint refuses that).

`./driver` (`cloudflareDriver`; `cloudflareDriver({ timeoutMs, startTimeoutMs, pollMs })`: 30 s a request, ten minutes for each of the deploy's waits (an upload live, the bundle, the restart), two seconds between tries; each request of the image's copy may take ten minutes) and `./fake` (`fakeCloudflare`) are internal entries, for tests.

A read is the Worker's settings (its bindings: what it runs is its plain-text bindings, never a secret's value), the application of its name (whether it exists, its id) and the account's subdomain (its URL); a plan compares the declared image, source, ref, revision, port, domains and hostname (each left out too) and secret names with them, and plans an update for a Worker whose version is not tagged with its revision (`workers/tag`: a create cut off before its upload with the app, a deploy cut off between its two uploads, or a Worker deployed before tags, once). The requests are made one after another, in the order the fixtures hold.

### Environment

It reads these on every call, never when the config loads:

| Variable                | What it is                                                                                                                                                                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`  | An API token with Workers Scripts Edit and Workers Containers Edit (Write, in the API's terms), Zone Read for `domains` (custom domains are attached and detached with Workers Scripts Edit) and DNS records, and Zone → DNS → Edit on the zones of [DNS records](#dns-records) |
| `CLOUDFLARE_ACCOUNT_ID` | The account's id, 32 hexadecimal digits, on its dashboard's overview                                                                                                                                                                                                            |

When either is unset, a call fails, not retryable, naming it. The driver declares both in its `env` ([Credentials](https://www.npmjs.com/package/@sanoma-ai/workflows#credentials)): the worker starts without them, and the app's connector page shows their status and lets you set them. The alarm's operations need neither: they call the Worker with `SANOMA_WAKEUP_TOKEN` (`alarm.create` mints it when none is stored), and `alarm.create` stores `SANOMA_HOST_URL` once the host answered, for a register made off the host; it keeps the first one stored, which the Worker's own binding overrides on the host. A read without the token reads the alarm as unhealthy, so a plan to delete it still goes on.

### Errors and retries

A 429, a 5xx, a timeout or no reply is retryable, the image's copy's requests too; any other 4xx is not. `status` and `vendorCode` (Cloudflare's first error `code`) are kept. The driver's own refusals are not retryable: `exists` (a Worker of that name that is not Sanoma's, which is neither overwritten nor deleted), `plan_changed` (an update whose plan changed since it was approved, or is not an update: a new name is a delete and a create), `no_token` and `token` (a host without the company's `SANOMA_WAKEUP_TOKEN`, or with another one), `no_zone` (a domain or a record set whose zone the account does not hold), `conflict` (a record in the way of a declared one), `no_dns_permission` (a token without Zone → DNS → Edit), `not_known` (records given as `null`), `invalid` (a container's `hostname` that is one of its `domains`, a record the shared shape refuses, an MX one without a priority, one outside the zone, a CNAME or a second SPF policy beside another declared record, or a set's mark longer than 100 characters), and a Worker that did not answer at its revision in time, which says what it answered.

### Plan

Containers need the Workers Paid plan. An instance is billed while it runs, by its `standard-1` size, and not while it is stopped; the Worker and its object are billed per request.

### Testing the driver

`test/driver.test.ts`, `test/records.test.ts` and the features replay Cloudflare's replies (`test/fixtures`) with [`@sanoma-ai/testing/replay`](https://github.com/Sanoma-AI/sanoma/blob/main/packages/testing/README.md#replaying-a-vendors-api): `pnpm vitest run connectors/cloudflare` needs no account. The fixtures are **written from Cloudflare's API reference, not recorded**: no account was at hand when the connector was written. A recording replaces them (`SANOMA_LIVE=1 SANOMA_RECORD=1` on the features test), losing the account's id and subdomain, ids and tokens; until then, a reply the reference gets wrong is wrong here too. The upload's `containers` field (its `name`, `class_name` and `images`) is Wrangler's and not in the reference or the SDK's types, and the object's `ctx.container.images` and `start({ image, instance })` are the policy's: the live run is what checks them. The DNS records' fixtures (`records-*`) are written from the [DNS records reference](https://developers.cloudflare.com/api/resources/dns/subresources/records/) the same way, on `sanoma.work` with a set named `check` (`check-*.sanoma.work`), to be recorded on their first live run: Cloudflare's TXT content is quoted in them, which a read takes off. That Cloudflare shows a TXT record written unquoted with quotes is the reference's examples', not checked; a read compares it either way. The `sites` fixture's assets session and bucket upload are written from the [direct upload guide](https://developers.cloudflare.com/workers/static-assets/direct-upload/) and the SDK's types the same way, with the guide's example hash (sha256 over an asset's base64 and its extension, 32 hex digits) and each part's type from its extension; that Cloudflare takes them, and serves `/assets/*` before the Worker, is the live run's to check. The image's copy is tested against two small registries in this process (`test/registry.test.ts`), and the driver's call for its credentials over replies written from the SDK's types and the OCI distribution spec; that Cloudflare's registry takes the copy as written is what the live run checks. The driver tests only replay.

### Running it live

`test/live.ts`, run by hand, runs the Host and Wakeup kits against a real account, then prints how long a cold wake took (a request to a stopped container until it answers). It makes a Worker and a `durable_object` application named `sanoma-host-check` (`CLOUDFLARE_TEST_NAME` changes it), takes about an hour (each stop is Cloudflare's own ten quiet minutes), and deletes both at the end. It is what checks what the fixtures cannot: the copy and its pin by digest, the image's preparation, the upload's `containers[].images`, the application's body, the object's `start` with the `standard-1` instance type, and a deploy check's new image started by the object:

```sh
pnpm build
SANOMA_LIVE=1 CLOUDFLARE_API_TOKEN=... CLOUDFLARE_ACCOUNT_ID=... \
  CLOUDFLARE_TEST_CHECKOUT=~/src/host-check-company CLOUDFLARE_TEST_DATABASE_URL=postgresql://... \
  CLOUDFLARE_TEST_SOURCE_KEY_FILE=~/.ssh/host-check-company_ed25519 \
  node connectors/cloudflare/test/live.ts
```

The kits have not run on a real account yet: the connector's first real run was Sanoma's own back office (`sanoma-ops`, 2026-10-29), deployed from the app's Resources page. What it showed: the second upload above, the Host the proxy forwards, and a cold start of about six to eight minutes on `standard-1` (the clone, `pnpm install` and `sanoma serve` of a company with a public site, the app built at start). The runtime image since runs `sanoma worker` alone over a pnpm store baked into it, building nothing at start ([runtime image](../../packages/sanoma/README.md#hosting-it-yourself)): measured locally at half a CPU, 2026-11-04 (Cloudflare's own pull time not included), the checkout under a second, `pnpm install --frozen-lockfile --prefer-offline` 7–10 s for a lockfile the store matches and 14–30 s for one a `pnpm update --latest` behind, and the worker's `/healthz` 6–16 s after: 16–38 s, against `standard-1`'s half a vCPU.

It needs:

- a published runtime image, `ghcr.io/sanoma-ai/runtime:<version>` (the `sanoma` package's version), which apply copies into the account's registry; `CLOUDFLARE_TEST_IMAGE` names another;
- `CLOUDFLARE_TEST_CHECKOUT`: a clone of a company repository whose `origin` Cloudflare can clone and this machine can push to (each deploy check pushes an empty commit), holding the kits' company: [`connectors/docker/test/fixtures/company`](../docker/test/fixtures/company) with `sanoma` from npm, its config registering `wakeupCheckWorkflows` (the host checks' workflows and a tick every ten seconds);
- `CLOUDFLARE_TEST_SOURCE_KEY_FILE`, for a private repository: the private half of a read-only deploy key on it, passed as the host's `SANOMA_SOURCE_KEY` secret as go-live does (the private `Sanoma-AI/host-check-company` is that company, with such a key);
- `CLOUDFLARE_TEST_DATABASE_URL`: a Postgres both the container and this machine reach, empty, the company's;
- Postgres here for the operator that applies the host (`pnpm db:up`).

## Testing

`@sanoma-ai/connector-cloudflare/fake` is an in-memory Cloudflare account, the fake the connector carries: each sandbox run makes one of its own. Its registry is in memory too: a copy records the image under its reference there and pulls nothing. Its custom domains are in `state.domains` (hostname, Worker and zone), each zone's DNS records in `state.dns`, by the zone's name (a test adds one by hand there; a batch is all or nothing, and refuses a record identical to one the zone holds (its type, content and priority) or one beside a CNAME, as Cloudflare does), and it holds every zone asked for unless `fakeCloudflare({ zones })` names the ones it holds. A copy pins the image by a made-up digest, and a preparation answers ready for an image pinned in its registry. Its Workers answer on ports of this machine, one per Worker name, and run the package's own object code over a `ctx` in this process: storage in memory, an alarm on a timer (again after a throw), `ctx.container.images` from the upload's `containers[].images`, and a container that runs what `start` returns for the image (the one its pinned copy was copied from) and revision it was started at (by default a stub that answers `/healthz` and `/wake`); `start` refuses an image the upload did not name or an instance type that is not Cloudflare's. An upload answers with its version's id (its object's `CF_VERSION_METADATA.id`), and is live at once, or after `fakeCloudflare({ propagation: N })` more requests to the version before (workers.dev's 404 for a new Worker), as Cloudflare's takes a while to reach every location; it then restarts the object over its new bindings and images: a new image starts the container again at the next request, as the object finds its label changed. Its settings and content give the latest upload back (its bindings, compatibility date and flags, version tag and modules), and an upload with `keep_assets` serves the assets of the version before. Its assets upload session asks, in one bucket, for the hashes `state.assets` lacks, and an upload that redeems the completion jwt keeps each path's hash on the Worker (`state.scripts[name].assets`, beside its `main_module`, `modules`, compatibility date and flags and `tag`). Its Hyperdrive configs are in `state.hyperdrives`, their passwords left out, and its `DATABASE` binding's `connectionString` is the direct URL. Its Workers run the package's own `serve` over the upload's modules, written to a folder and `app/index.js` imported from there; the bundle the container's worker answers is `fakeCloudflare({ bundle })`'s, by default `stubAppBundle`, a plain ES module that answers pages and `/healthz` and serves `/assets/`, since the real bundle is built for `workerd` (`nodejs_compat`, WebAssembly) and Node cannot import it.

```ts
import { fakeCloudflare } from "@sanoma-ai/connector-cloudflare/fake";
import { inProcessHost } from "@sanoma-ai/testing/host";

const fake = fakeCloudflare({
  start: ({ revision, env }) => inProcessHost(config, databaseUrl)({ port: 0, revision, secrets: env }),
});
// ...apply a container, then:
await fake.stop("acme"); // as ten quiet minutes would: the next request starts it
await fake.fire(); // rings every armed alarm now
fake.wakes(); // each /wake the containers answered
await fake.close();
```

`test/host.test.ts` and `test/wakeup.test.ts` run the Host and Wakeup kits over the fake this way, the company's runtime in this process; `test/worker.test.ts` runs the object's code and `serve` over a stubbed `ctx`. Nothing here runs the Worker in `workerd`: [Miniflare](https://developers.cloudflare.com/workers/testing/miniflare/) would, which this package does not add.
