# Working on @sanoma-ai/connector-cloudflare

Follow the shared [connector conventions](../AGENTS.md).

- [README](README.md): the three types, [the Worker](README.md#the-worker), [the deploy](README.md#the-deploy), [the database](README.md#the-database), scale to zero, [DNS records](README.md#dns-records), credentials and errors.
- [Source map](src/AGENTS.md): definitions, the operations over `CloudflareApi` (the record sets' in `records.ts`), driver, the image's copy into the account's registry, fake, and the deploy's modules, bundle and assets.
- [Test map](test/AGENTS.md): the Worker's code, the driver over fixtures, features, both kits on the fake, and the live run.

`worker/` is the Worker script the package uploads, plain JavaScript: the Worker is the app. `index.js` binds `instance.js` to `cloudflare:workers` and imports the app bundle from `./app/index.js`, which the deploy uploads beside it (`no-app.js` on a Worker that never served an app). Keep `instance.js` free of imports so the fake runs it in Node, and keep `instance.d.ts` in step with its exports, which `src/` imports directly. The object answers its three routes alone (health, wake, the app bundle); a visitor's request is the app's, never the object's, and needs no container. A deploy is three steps in `put` (`src/ops.ts`): the bundle, one upload, the restart; keep them in that order and the restart last, so a plan of none can confirm a deploy by the restart alone. A visitor never gets a 503 or an error from a deploy: an upload before the bundle (a new image, a stale deployment) keeps serving the app deployed, and after every upload the deploy waits until the object answers with that version's `x-sanoma-deployment` before asking it anything; an earlier version's answer is "not yet", never "stale". The final upload's version tag is the app's revision, which a plan compares. A change of the Worker's bindings or routes changes `src/ops.ts` with it. The custom domains Sanoma may detach are the ones the Worker's own bindings record, `SANOMA_DOMAINS` (the sites') and `SANOMA_HOSTNAME` (the app's, which the state's `url` follows; `SANOMA_HOST_URL`, the wake path, stays the workers.dev URL): never detach one they do not name. Both the driver and the fake go through `containerOps` and `alarmOps` in `src/ops.ts` and `recordsOps` in `src/records.ts`: put behavior there, not in either. A record set owns only the records carrying its comment, `sanoma:<zone>/<name>`: never change or delete another, except adopting one identical to a declared record in type, name, content (and an MX record's priority) that is not proxied and carries no other set's mark.

Keep `configurationRevision` aligned across schema, plan/read, the reserved `SANOMA_CONFIG_REVISION` binding, container labels and startup health checks. It is non-secret metadata for environment-only rollouts; never derive a public label from secret values. See [The Worker](README.md#the-worker).

Keep reads and plans non-starting. Explicit host/container updates must await startup readiness even when the plan is unchanged; that path must not reupload secrets. See [The Worker](README.md#the-worker) for the revision and rotation contract.

The fixtures are written from Cloudflare's API reference, not recorded (README, [Testing the driver](README.md#testing-the-driver)), the `records-*` ones too until a live run on `sanoma.work` records them; a recording replaces them. Never put a token or an account id in a fixture.

Run `pnpm vitest run connectors/cloudflare` (the kits need Postgres, `pnpm db:up`) and `pnpm typecheck`. `test/live.ts` runs against a real account by hand only.
